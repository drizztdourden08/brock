# App structure

Where every piece of a Brock app's code goes, so the file you need is always in the same place. Screens, widgets and Tessera parts sit side by side under `src/`, each kind in one folder, and the folders Brock reads by convention are filled in by `brock sync` with no hand wiring. The folder rules every repo shares (one thing per file, component folders, token tiers) are in [contributing/structure.md](contributing/structure.md); this page is the map of a Brock app on top of them.

## One app

```
my-app/
  brock.config.ts                  product, targets, modules
  brock.workspace.mjs              the thread CLI: repo name, base branch, launch targets
  brock.scope                      the npm scope
  tessera.config.json              where Tessera parts live; $schema alone keeps src/<kind>; guide.parts names .brock/tessera-parts.ts
  package.json                     "type": "module": the managed configs pass import.meta.dirname
  pnpm-workspace.yaml, .npmrc, knip.json, .jscpd.json
  electron.vite.config.ts, electron-builder.config.cjs,
  eslint.config.mjs, stylelint.config.mjs, .markdownlint-cli2.mjs, tsconfig.json   managed by brock sync
  bin/<repo>.mjs                   the repo command
  release-notes/v<version>.md      the note of each release, in the release note standard (see below)
  electron/
    main.ts                        bootstrapApp(product, { modules, bootTasks, handlers: mainHandlers, services, dataDomains })
    preload.ts                     createPreloadBridge({ maps, namespaces })
    boot/<id>.task.ts              main boot tasks
    handlers/<subject>-handlers.ts one HandlerGroup per subject, exported as <subject>Handlers (.dev.ts: dev builds only)
    services/                      createAppServices(ctx), the graph bootstrapApp builds as ctx.services
    <subject>/                     main-side logic the handlers call (kebab-case functions)
  src/
    main.tsx                       <BrockApp screenTree widgets widgetKits titleBar tours modules bootTasks settings review />
    index.html, product.ts, theme.css
    settings.type.ts, settings.constants.ts, main.constants.ts
    ipc/contract.constants.ts      APP_CHANNELS = defineChannels({...}), and its maps for the preload
    ipc/contract.type.ts           the augmentation, from the declaration's types
    review/seed.ts                 fills the app with data before the review tour
    review/<id>.step.ts            the app's own review steps
    review/fixtures/               files copied into the app data folder before the seed runs
    screens/screens.config.ts      buckets, menu placement, home
    screens/<bucket>/<id>.<kind>.tsx, screens/<bucket>/<page>/<sub>.sub.tsx, screens/<id>.card.tsx, screens/<id>.layer.tsx, screens/<id>.base.tsx
    widgets/<id>.widget.tsx        one widget per file
    widgets/layout.ts              the default widget layout: defineLayoutPreset({ rows })
    widgets/<id>.widget.constants.ts that widget's constants
    widgets/<id>.kit.ts            a widget kit: default export its WidgetKitMeta; its widgets say kit: '<id>' in meta
    widgets/<id>.overlay.tsx       a kit overlay drawn over the main view: default export the component, meta { kit }
    title-bar/<id>.action.ts       one title bar item per file: a button, a dropdown menu, a status tag or a volume control
    title-bar/<id>.action.constants.ts that item's constants
    tours/<id>.tour.ts             one guided tour per file: defineTour({ id, title, steps, trigger? })
    tours/<id>.tour.constants.ts   that tour's constants, such as the selectors it lights
    boot/<id>.task.ts              renderer boot tasks
    views/<Name>/                  Tessera views: the screens' state-owning bodies
    compounds/<Name>/              Tessera compounds: one app concept drawn from Tessera parts
    composites/<Name>/, primitives/<Name>/   the rare app-only composite or primitive
    stores/use<Thing>Store.ts      zustand stores, with <thing>-store.type.ts beside them
    hooks/use<Thing>.ts            hooks shared by more than one view
    <subject>/                     renderer logic with no React (kebab-case functions)
  public/logos/                    generated by brock icons, or the app's own art
  build/installer/                 header.png and splash.png overrides, nothing else
  tests/<area>/<name>.keep.test.ts, tests/e2e/<name>.e2e.ts
  tests/COVERAGE.md, tests/launch-suite.md   the kept-test registry and the launch suite (launch-suite.md)
  tests/baselines/<platform>/<capture>.png   the review's screenshot baselines, written by --review-bless
  tests/baselines/baselines.json   their tolerance, threshold and masks, optional
  .brock/                          generated by brock sync, never edited
```

`electron/` and `src/` always sit side by side in the folder that holds `brock.config.ts`, and no setting points either one elsewhere. An app that keeps its main process and its renderer in two folders moves them together first ([upgrading-an-app.md](upgrading-an-app.md), Main and renderer in two folders).

## A workspace

An app with packages of its own is a pnpm workspace. Each app keeps its screens, widgets, views and boot tasks in its own `src`; the parts every app shares sit in one design package, and so do the views two or more apps use (a sign-in or an account page that a desktop app and a site both show, or that two sites show).

```
my-repo/
  pnpm-workspace.yaml, brock.workspace.mjs, brock.scope, tessera.config.json, lint configs
  release-notes/v<version>.md      the release notes, at the repo root
  .github/workflows/               managed by brock sync: ci.yml and release.yml for one app, ci-<app>.yml and release-<app>.yml each beside a workspace ci.yml for several
  apps/<app>/                      the layout above, without the root configs
  apps/<site>/                     a site, when one was added: see A site below
  packages/design/src/primitives, composites, compounds    shared Tessera parts
  packages/design/src/views        views two or more apps or sites use
  packages/design/stories          their gallery stories
  packages/<subject>/              domain packages: no React parts, no Electron
  tooling/<name>/                  repo scripts that are not part of an app
```

In a repo with `brock.workspace.mjs`, `brock sync` writes the workflows at the repo root, with `APP_DIR` set to the app, and `brock check` fails when they drift. One Brock app keeps `ci.yml` and `release.yml`, `v<version>` tags and `release-notes/` at the repo root. Several Brock apps get `ci-<app>.yml` and `release-<app>.yml` each, plus a workspace `ci.yml`; each sets `product.releaseTagPrefix` and keeps its notes in its own `release-notes/`, and a pull request builds and reviews only the apps it touches. A pnpm workspace without `brock.workspace.mjs` (Brock's own repo, whose `templates/app` is in its workspace) gets none.

`tessera.config.json` names the design package and its part folders, and gives each app its own `views`: `brock adopt` writes it that way (`apps.<app>.parts.views` is `<app>/src/views`), and prints the layout it found. When the design package has `src/views`, adopt also sets the root `parts.views` to it and lists it after each app's own folder (`["apps/desktop/src/views", "packages/design/src/views"]`), sites included, so every app reaches the shared views and `tessera new view` still writes into the app's own folder first. A view goes to the design package only once a second app uses it; until then it stays in the app.

## A site

Brock covers desktop, mobile and web versions of an app, and a mix of them in one repo, all drawn with Tessera. A fresh app is the app alone. `brock site add <name>` adds a site beside it: a separate web app, a single-page Vite app, at `apps/<name>` of the same repo (a community site, a store). It is not the `web` platform, which builds the Electron renderer for a browser; a site has its own pages and its own build.

```
apps/<name>/
  brock.site.ts                    OWNED       defineBrockSite({ site: { id, name, brand }, ports: { offset }, api?, build? })
  package.json                     OWNED ONCE  dev, build, preview (brock site ...), typecheck, lint
  vite.config.ts, tsconfig.json    MANAGED     brock sync writes them; brock check fails on drift
  src/index.html, src/main.tsx     OWNED ONCE  Tessera tokens, the brand palette, theme.css, TesseraProvider
  src/main.constants.ts            OWNED       the TesseraOverrides
  src/theme.css                    OWNED       the site's palette seeds
  src/views/<Site>Shell/           OWNED ONCE  SiteHeader, the routed page and SiteFooter (StoreShell for apps/store)
  src/views/<Site>Home/, <Site>SignIn/  OWNED ONCE  the first page and the sign-in page on the brand gradient
  src/hooks/useSitePath.ts         OWNED ONCE  the path router
  src/views/<Name>/                OWNED       the pages; views shared with another app sit in packages/design/src/views
  public/                          OWNED       served at the page root
.github/workflows/ci-<name>.yml    MANAGED     the site's CI, at the repo root
```

What `site add` does: it writes the files above, adds `apps/*` to `pnpm-workspace.yaml` when no glob covers the folder (a fresh app has `packages: []`), names the package `<scope>/<name>` from `brock.scope`, takes each dependency's spec from the root `package.json` (a relative `link:` moved to the site folder), else the catalog, adds the site to `tessera.config.json` (`apps.<dir>`, its views and theme) and to `knip.json` (`workspaces.<dir>`, moving the root entries to `workspaces["."]` the first time), and runs the site's sync. Run `pnpm install` after it.

- Port: `ports.offset` is a tool port (1 to 9) of the repo's port block: the first Brock app's `product.ports.base` (or the base its id derives), moved by the checkout's slot like the app's own ports, so each worktree's site has its own port. `site add` takes the lowest offset no other site or site API uses. `ports.base` sets a base of the site's own. `strictPort` is always on.
- API: `api` is a dev proxy for `/api` (or `api.path`), to a URL (`api: 'https://staging.example.com'`) or to a tool port of the same block and slot (`api: { portOffset: 2 }`), so a worktree's site talks to that worktree's API. The API can be anything listening there: Brock does not make or start it. `changeOrigin` and `stripPath` (drop the path before forwarding) are off by default. The same table serves `brock site preview`. Keep `src` and `public` free of a folder named like the proxy path (`src/api`): its files would go to the API; `site add` and `brock sync` name one.
- Shared offsets: the managed `tsconfig.json` allows `.ts` imports, so `brock.site.ts` can take its offsets from a constant the API shares (`import { TOOL_PORTS } from '../../ports.constants.ts'`, with the extension).
- Build options: `build.define` (globals replaced at build time, each a JSON value) and `tsconfig.compilerOptions` (merged over the managed `tsconfig.json`); `build.nodePolyfills` (`true` or the options of `vite-plugin-node-polyfills`, which the site installs) for code that needs `Buffer` or `process`; `build.aliases` (import prefixes to folders, relative to the site), added to the managed `tsconfig.json` paths too. Workspace packages need no alias: a site that lists `"@<scope>/<pkg>": "workspace:*"` imports it by name, and Vite serves files from every linked package.
- Tessera: `main.tsx` imports `tokens.css`, `palettes/<brand>.css` and `theme.css` and renders `<Site>Shell` inside `TesseraProvider`; the build sets `data-palette` on `<html>` from `site.brand`, the page title from `site.name`, and serves the brand's `icon.svg` from the installed Tessera as the favicon.
- Commands: `brock site dev`, `build` and `preview` in the site folder (the `dev`, `build` and `preview` scripts); `brock site list` prints every site with its port and API target. `brock sync` and `brock check` at the repo root, in the app or in the site cover the site's managed files.
- Lint and structure: the root `eslint .`, `brock prose`, `brock knip`, `jscpd .` and `brock structure` reach the site, which the site's own `lint` script completes with its typecheck and stylelint.
- CI: `ci-<name>.yml` runs on pull requests and from the Actions tab: a `changes` job (`brock affected apps/<name>`) and, only when the change touches the site, a `site` job that runs the site's `lint` and `brock site build` and keeps `dist` as an artifact.

The shell: a site reuses the app's parts and differs only in its framing. Its views are named after the site (`apps/store` gets `StoreShell`, `StoreHome` and `StoreSignIn`), so two sites never share a part name. `src/views/<Site>Shell` draws Tessera's `SiteHeader` (the brand mark and title as the link home, `SITE_LINKS`, and the signed-in person as a profile menu built by `profileAction`, the same `WindowTitleBarDropdownAction` the app title bar takes; a Sign in button in its place while signed out), the page, and `SiteFooter` (the small logo, a note, `FOOTER_LINKS`). `src/hooks/useSitePath` routes by path with the History API, so `navigate` changes the page with no reload; a new page is a view routed by its path in `<Site>Shell`. `src/views/<Site>SignIn` is a `Card` centred on the brand gradient, the splash's dark pair with the light end as the card's top edge; its button calls `onSignIn`, which the template wires to a placeholder person until the app hands it to its own sign-in. Every page inside the frame uses the app parts (`Card`, `SideNavLayout`, `SettingsPage`, `DataTable`, ...).

What Brock does not provide for a site, by decision: no server kit, no cloud functions, no hosting or deploy workflow, no sign-in, session or account layer. Those stay the app's own packages, and a site reaches them only through its `/api` proxy in development and through whatever host the app deploys `dist` to.

## Release notes

Every release has `release-notes/v<version>.md` at the repo root: `# <product.name> v<version>`, a one-paragraph summary, then `##` sections (New, Changes, View, Settings, Around the app, Platforms, Under the hood, Upgrading, Fixes, plus any a repo adds through `options.releaseNotes.sections` in `standards.config.mjs`) of dash bullets, each a plain sentence for users. `brock release-notes check [version]` holds a note to the standard; the full rules are `docs/release-notes.md` in `@drizztdourden08/standards`, which binds every repo, Brock app or not. A new app ships `release-notes/v0.1.0.md` as its first note.

A renderer file (anything in `src/`) imports a package that also holds Node code through its per-subject subpath export (`@my-app/hosts/<subject>`), never through the package barrel: the barrel re-exports the Node side too, and Vite then pulls modules such as `ssh2` or `node:child_process` into the renderer bundle. `brock structure` warns when a renderer file imports a workspace package's barrel that reaches a Node builtin through its re-exports, and names a subpath to use instead.

`brock structure` enforces the screen, widget, title bar and tour folders: an unknown screen suffix, a stray file or folder in `src/widgets`, a widget file without a default export, a `meta` key that is not a widget field, a widget id Brock already uses, a kit file without a default export or with a key that is not a kit field, an overlay without a default export or a `meta`, and a `meta.kit` that names no kit file are findings, and so are a file in `src/title-bar` that is not `<id>.action.ts`, a folder there, a title bar id that is not kebab-case, one with no default export and one Brock uses (`search`, `report-bug`, `brock-jobs`), and a file in `src/tours` that is neither `<id>.tour.ts` nor a constants file (`<id>.tour.constants.ts`, the one the constants lint rule names, or `<name>.constants.ts`), a folder there, a tour id that is not kebab-case, one with no default export and a `defineTour` whose literal `id` is not the file name.

A file whose header says `@kind data` holds data and nothing else: imports, types, and `const` declarations made of literals, arrays, objects, spreads, references to other values, constant arithmetic and `Object.freeze`, with `as const` and `satisfies` allowed. It may run past 200 lines, export several lists and name `UPPER_SNAKE` consts outside a `.constants.ts` file, which suits record files and generated tables. A function, an arrow, a call other than `Object.freeze`, a conditional, a getter, `let` or a statement in such a file is a `brock/data-only` error, so the kind exempts no code; a generated file that holds code keeps its own kind. Brock's ESLint config finds the data files by their header when it loads, so an editor picks a newly marked file up after an ESLint restart.

A file whose header says `@kind verbatim` is a data file whose string values are text reproduced word for word from an outside source, text the app must show exactly as it is: a licence text, a game's own dialogue table, the strings a protocol defines. The prose rules would flag that text (an exclamation mark, a stock phrase, a dash), and rewording it would change what the app shows. The kind is the exemption, and it is narrow and written down:

- The header names the source after the kind, `@source <short text>`; `brock/verbatim-source` fails a `@kind verbatim` header without one, and the exemption stays off until it has one.
- The file gets everything `@kind data` gets, `brock/data-only` included, so it holds no logic.
- `local/no-em-dash`, `local/no-smart-punctuation`, `local/no-slop-prose` and `local/no-tool-brand-words` skip its string values (string literals and the text of template literals). Identifiers, comments and the header are still read by every rule. Brock's ESLint config passes each such file to the standards factory as a `verbatimText` entry whose `why` is the source.
- `brock structure` lists every `@kind verbatim` file with its source, so a review sees what is exempt.

A UI string is never verbatim: it stays in an ordinary `@kind data` or `@kind constants` file and passes the prose rules. Keep a verbatim file to the reproduced text, and put the app's own labels for it elsewhere.

```ts
/* @layer shared-game @kind verbatim @source the town dialogue table of the original game, text bank 2 */
const TOWN_DIALOGUE = [
  { id: 0x10, text: 'Welcome, traveller! Rest by the fire.' },
  { id: 0x11, text: 'The bridge is out... take the ferry.' },
];

export { TOWN_DIALOGUE };
```

Each of these folders takes the constants file the constants lint rule names for a file in it, the file name with `.constants.ts` in place of its last extension: `<id>.widget.constants.ts` and `layout.constants.ts` in `src/widgets`, `<id>.action.constants.ts` in `src/title-bar`, `<id>.tour.constants.ts` in `src/tours` and `<id>.<kind>.constants.ts` (`home.hero.constants.ts`, `items.tab.constants.ts`) at any level of `src/screens`, plus `<name>.constants.ts` for constants several files there share. `brock sync` leaves them out of `.brock`. The module folders take `<id>.task.constants.ts` beside a boot task and `<id>.step.constants.ts` beside a review step (and the same for widget, title bar and tour files outside an app); `brock structure` reports any other doubled suffix, such as `<id>.page.constants.ts` in `src/review`.

## What loads at boot

Screens, widgets, a title bar button's handler and a tour's steps load when they are first used (see Lazy registries and the Suspense host in [architecture.md](architecture.md)); only their `meta` loads at boot. So keep a screen or widget file's `meta` to plain values and what they need (constants, icons, a `when` rule, small helpers), and never read the default-exported component from it, or the whole file loads at boot again. Code at the top level of a screen or widget file runs when that screen or widget first loads; anything that must run at boot belongs in a boot task. A settings page (`.settings.ts`) still loads at boot, since its sections feed the live settings search.

## A page that fills the window

A page scrolls as a whole by default: its header stays and its body scrolls under it. A page that holds a list beside an editor, such as Tessera's `ListDetail` or `ListDetailLayout`, sets `fill` in its meta instead, so a long editor scrolls on its own and the list stays in view:

```tsx
// src/screens/library/presets.page.tsx
export const meta: ScreenMeta = { title: 'Presets', icon: 'sliders-horizontal', fill: true };

const PresetsPage = () => <ListDetail list={list} selectedId={selectedId} onSelect={setSelectedId} detail={editor} dirty={dirty} />;
```

- The page takes the window height and its body does not scroll. `ListDetail` and `ListDetailLayout` fill it and scroll each pane themselves.
- The page's root fills the body: render the `ListDetail` at the root, or give the root you wrap it in `flex: 1` and `min-height: 0`.
- `fill` works on a page, on a sub page and, through `<page>.page.ts`, on a tab page. A hero page and a settings page ignore it.

## A shorter or taller hero

A hero takes the default Tessera `Hero` height, 288 to 408 px. A home with a few facts and actions sets `hero.size` in its meta instead:

```tsx
// src/screens/library/home.hero.tsx
export const meta: ScreenMeta = { title: 'Home', icon: 'house', hero: { size: 'compact' } };
```

- `'compact'` fits the hero to its content, with tighter padding and gaps; `'tall'` makes it 408 to 560 px; `'default'`, or no `hero` at all, keeps today's height.
- Brock passes it to Tessera's `Hero` as `size`. Under 720 px wide every size stacks; `default` and `tall` keep their height as a minimum and `compact` has none.
- `hero` works on a `.hero.tsx` only; other screens ignore it.

## A hero without art

In an app with a Tessera brand, a hero that renders no `Art` gets the brand mascot. A hero that wants no art at all renders `Art` with `kind="none"`, as `Backdrop` takes `kind="none"` for no backdrop:

```tsx
// src/screens/library/home.hero.tsx
const LibraryHome = (props: HeroProps) => {
  const { Title, Art } = props.slots;
  return (
    <>
      <Title>Library</Title>
      <Art kind="none" />
    </>
  );
};
```

- The hero draws no art, not even the brand mascot; the other slots fill the space as they do in an app with no brand.
- With no `Backdrop` either, Tessera's `Hero` sits the content at the top (`hero--bare`).
- The review's `hero` step checks that such a hero draws no art (`<bucket>-hero-art-none`).

## Settings groups an app shares with modules

A module's settings tab names its nav group with `group` (the label) and, for apps to target it, `groupId`. brock-display's Display tab has `group: 'App', groupId: 'app'`. An app that declares the same group on its settings bucket gets one group holding both:

```ts
// src/screens/screens.config.ts
buckets: [{ id: 'settings', title: 'Settings', icon: 'settings', menu: 'entry', groups: [{ id: 'app', label: 'App' }] }],
```

- A tab joins the group whose id is its `groupId`, else the group whose label is its `group` (trimmed, any case).
- Inside the group, the app's own pages come first, in their `meta.order`, then the tabs in the order they are listed: the app's `settings.tabs`, then each module's.
- A tab that matches no group starts one after the app's groups, and later tabs with the same id or label join it.
- The review's `buckets` step fails a hub whose nav shows two groups with the same label (`<bucket>-nav-groups`).

## A backdrop drawn by a component

`backdrop` on a bucket in `screens.config.ts` takes an image or a colour, since the config holds no JSX and imports nothing but `defineScreens`. A bucket whose page headers draw a scene of their own puts it in `src/screens/<bucket>/<bucket>.backdrop.tsx`, which default-exports a component:

```tsx
// src/screens/library/library.backdrop.tsx
import { StripedBackdrop } from '../../views/StripedBackdrop';

const LibraryBackdrop = () => <StripedBackdrop />;

export default LibraryBackdrop;
```

- Sync picks it up like a `.hero.tsx`. Its styles live with the view it draws (`src/views/StripedBackdrop/StripedBackdrop.css`), since `src/screens` holds no stylesheets. The component takes no props and fills the header behind every page of the bucket, inside Tessera's `BackdropLayer`.
- It loads with the bucket's pages: when the hub or one of its pages preloads (a bucket switch pill or a menu row on hover or focus, the home hub at boot), and otherwise the first time a page header of the bucket draws.
- A page's own `meta.backdrop` still wins, and `{ kind: 'none' }` there removes it for that page. Keep either the file or `backdrop` in `screens.config.ts`: `brock structure` reports a bucket with both.
- The file sits in its bucket folder and takes the bucket name; its constants go in `<bucket>.backdrop.constants.ts`.

## A small informational window

A card fills the window by default. A card with no tools, such as credits or a licence list, sets `size: 'info'` in its meta, so it opens like About: a small window sized to its content and centred, at most `--size-512` wide and at most the window's height.

```tsx
// src/screens/credits.card.tsx
export const meta: ScreenMeta = { title: 'Credits', icon: 'file-text', requiresProfile: false, size: 'info' };
```

- Brock passes it to Tessera's `ScreenWindow` as `size="info"`. The window's title bar names it, so the card has no page header; the card's content scrolls inside the window when it is taller.
- Under 560 px wide the window fills the screen, as every screen does.
- `size` works on a card. The built-in Credits screen, from `credits` on `BrockApp`, opens this way too. List entries one per line; an informational window is never wide.

## A window with a side nav

A tool window, such as a data inspector or a studio, often has a nav on the left and one pane per nav item on the right. Declare it with `defineWindow` in a card or layer file, and set `fill: true` in its meta so the window draws the nav and the pane edge to edge under one header. You never touch a Tessera layout:

```tsx
// src/screens/library.card.tsx
import { defineWindow } from '@drizztdourden08/brock-react';
import type { ScreenMeta } from '@drizztdourden08/brock-react';
import { ItemsPane } from '@app/views/Library/ItemsPane';
import { MapsPane } from '@app/views/Library/MapsPane';

export const meta: ScreenMeta = { title: 'Library', icon: 'library', fill: true };

export default defineWindow({
  groups: [
    {
      id: 'records',
      label: 'Records',
      items: [
        { id: 'items', label: 'Items', icon: 'package', render: () => <ItemsPane /> },
        { id: 'maps', label: 'Maps', icon: 'map', render: () => <MapsPane /> },
      ],
    },
  ],
});
```

- **Items.** `items` is a flat list; `groups` is the same list under group labels. Use either or both. Each item has an `id`, a `label`, an `icon` (an icon name), an optional `disabled`, an optional `badge` (a count or a short text, drawn as a pill on the nav row) and `render`. `render` gets the card props plus `active` (the item id) and `select(id)`, so a pane can send the user to another item.
- **Active item.** The first enabled item opens, or `initial` when set. The choice is remembered per screen while the app runs. Open a screen on an item with the `nav` param: `open('library', { nav: 'maps' })`.
- **Collapse.** The nav folds to its toggle on the window's own width: under 640 px it becomes a bar with a menu, and above it the user folds it with its toggle, remembered for the screen. `narrow: true` starts it folded. `label` names the nav for assistive tools.
- **Scroll.** A pane scrolls as a whole by default. A pane that holds a Tessera `ListDetailLayout` or `ListDetail` sets `scroll: 'none'` on the window, so the layout scrolls its own panes, and its root fills the pane like a `fill` page.
- **Header.** `fill: true` on a card gives the window the one header with the icon and title and the close button, and no padding or scroll wrapper around the body. A card without it is unchanged.
- **Bare.** `bare: true` on a card makes it look exactly like the Home hub window: no title row, the hub's padding, the corner close and lock, no screen switcher, movable, and the shared hub window storage key (`HUB_WINDOW_KEY`, exported from `brock-react`), so it opens where the hubs sit and moving it moves them all. It wins over `fill` and `size`. Use it for a card that must read as a hub. The card title and icon show in a small chip at the top left corner, on the line of the close button; a hub does not draw it, as its switch names it.
- `defineWindow` throws when the window has no items, repeats an id, has only disabled items or names an unknown `initial`, so a mistake shows when the file loads.

A window is a plain card, so the menu, the shortcut, `requiresProfile`, `when` and `keywords` in its meta work as on any card.

## Menu order and overrides

Brock builds the title bar menu on its own: Home, Profiles, Settings and the app entries the screens give, then the sections (Widgets, Help, Advanced), then module entries, and Credits, About and Quit as the last group. An app changes that menu entry by entry, in two places. They merge in this order: what Brock detects, then the screen's own `meta.menu`, then `product.menu` in `brock.config.ts`, which wins field by field.

```ts
// brock.config.ts
product: {
  // ...
  menu: {
    entries: {
      settings: { label: 'Preferences' },
      'bucket:library': { after: 'settings' },
      'keyboard-shortcuts': { parent: null, group: 'end', before: 'about' },
      'screen:glossary': { inMenu: false },
      'bucket:tools:notes': { hidden: true },
    },
  },
},
```

```tsx
// src/screens/tools/ruler.page.tsx: out of the Tools submenu, just before Library
export const meta: ScreenMeta = { title: 'Ruler', menu: { parent: null, before: 'bucket:library' } };
```

Each entry takes these fields:

| Field | What it does |
| --- | --- |
| `inMenu` | `inMenu: false` leaves the entry out of the menu only: the search palette, its route, its shortcut and `open` still reach it. `inMenu: true` brings back an entry a screen's meta took out. A submenu all of whose entries are out of the menu or moved away goes too. |
| `hidden` | `hidden: true` takes the entry out of the menu, the search palette, the keyboard shortcuts and the shortcuts dialog, for its route and every route under it (hiding a bucket hides its pages). Code can still open it with `open(route)`. `hidden: false` undoes a screen's own `hidden`. To hide a screen from everything, routes included, use `when`, `hosts` or `devOnly` on it. |
| `label` | Renames the entry, in the menu and in the search palette. |
| `group` | Moves a top-level entry to another group: `'main'` (Home, Profiles, Settings, app entries), `'sections'`, `'modules'` or `'end'` (Credits, About, Quit). On an entry inside a submenu it lifts the entry out into that group. |
| `order` | Sorts the entry in its list like CSS `order`: every entry counts as 0, a lower number comes first, and ties keep the detected order. `order: -1` puts an entry first, `order: 1` last. |
| `before`, `after` | Puts the entry right before or after the entry with that key, in that entry's list, whatever its group or submenu. They apply after `order`, and win over `parent` and `group`. |
| `parent` | Files the entry in the submenu with that key. `parent: null` lifts it out to the top level, into `group` or the group of the submenu it left. |

Widgets and kits take `meta.menu: { parent, group, order }` in their `<id>.widget.tsx` or `<id>.kit.ts` file. A `devOnly` widget or kit lands in Widgets > Developer (`widgets-developer`), which shows only while developer tools are on. When a widget, a kit or Developer names a `parent` that no entry has, in its meta or here, that submenu is made inside Widgets, labelled from its key (`audio-tools` reads Audio tools), and `entries['audio-tools']` renames it. [architecture.md](architecture.md), The Widgets menu, has the details.

`meta.menu` takes the same object on a page, a tab page's `<page>.page.ts` or a card; the string forms (`false`, `'entry'`, a path) work as before. A `label` in `meta.menu` renames the entry where Brock detects it, which `meta.title` alone would not when the menu needs a shorter name. A page of an `entry` or `hidden` bucket has no menu entry of its own; `meta.menu` with a `parent`, `group`, `before` or `after` gives it one.

The keys:

| Entry | Key |
| --- | --- |
| Home, Profiles, Settings | `home`, `profiles`, `settings` |
| Credits, About, Quit | `credits`, `about`, `quit` |
| Widgets, Help, Advanced and any other section | `section:widgets`, `section:help`, `section:advanced`, `section:<id>` |
| A widget, Reset layout | `widget-<id>`, `widgets-reset-layout` |
| A widget kit, its Open kit and Reset kit layout rows | `kit-<id>`, `kit-<id>-open`, `kit-<id>-reset` |
| The Developer submenu of Widgets | `widgets-developer` |
| Take the tour, one tour of several | `take-the-tour`, `tour:<id>` |
| Keyboard shortcuts, Report a bug, Dev Console | `keyboard-shortcuts`, `report-bug`, `dev-console` |
| A bucket, a page of a bucket | `bucket:<bucket>`, `bucket:<bucket>:<page>` |
| A card | `screen:<id>` |
| A submenu made by a `meta.menu` path | `menu:/<label>/<label>`, lower case |
| A module entry or an app `menu` prop entry | the `key` it gives, such as `input-tester` for the input module |
| View | `view`: every field but `parent`, since View stays at the top level |
| Pin on top, Full screen, while View is hidden | `window-pin`, `window-fullscreen`: every field but `parent`, plus `activeLabel` |

The title bar draws View, the sub-menu with Pin on top and Full screen, so `view` works through Tessera's `WindowTitleBar`. Its `label` renames it. `hidden: true` or `inMenu: false` leaves it out of the menu. `group`, `order`, `before` and `after` place it like any entry, and other entries can name `view` in `before` and `after`. Left untouched, View keeps the bar's own place above Credits, About and Quit, and with `group` or `order` alone it starts at the end of the module entries. On a narrow window the bar tucks its pin and full screen buttons away into View. With View hidden, Tessera's title bar lists a tucked pin and full screen button in the main menu itself, first in the bar's own group above Credits, About and Quit, so they stay reachable. Pin and full screen are plain actions with no check mark: the label says what a pick does (Pin window on top or Unpin window, Fullscreen or Exit fullscreen). `window-pin` and `window-fullscreen` change these two rows through the bar's `tucked` prop. `label` renames the row in both states, and `activeLabel`, taken by these two keys only, is its text while the window is pinned or in full screen. `group`, `order`, `before` and `after` place it as they place View, and other entries can name these keys in `before` and `after`. `hidden: true` or `inMenu: false` leaves the row out, so on a narrow window that button is out of reach. The keys only work while View is hidden: while View is shown it holds the pin and full screen, and these keys change nothing.

`brock check` reports a field it does not know or a value of the wrong type, a `bucket:` or `screen:` key no file of `src/screens` gives, an entry that names itself, `before` and `after` together, a `before` and `after` loop, a `parent` on `view` and an `activeLabel` on any key but `window-pin` and `window-fullscreen`. It warns, without failing, when `view`, `window-pin` and `window-fullscreen` are all hidden or out of the menu, since a narrow window then has no way to pin or go full screen, and when `window-pin` or `window-fullscreen` is set while View is shown, since it then has no effect. A development launch reports the rest once each in the log as a warning: a key no entry has (with the keys that look like it), a `parent` that is not a submenu or sits inside the entry, and the loop. Nothing throws: an override that cannot apply is skipped and the entry stays where Brock put it. An entry whose key is also a title bar action's id (Report a bug, Check for updates) leaves the drawn menu while the bar shows that action, and the bar's own part of the menu lists it instead.

With no active profile, an entry that opens a screen needing a profile shows disabled with "Pick or create a profile first", as Home does, wherever an override put it. The review checks the drawn menu against these overrides: each overridden entry gets a `menu-entry-<key>` check (out of the menu, or drawn at its place between its neighbours), each `hidden` entry a `search-hidden-<key>` check that the palette does not list it, and its built-in, section and last-group checks follow the effective menu.

## Product icons

`product.icons` in `brock.config.ts` names the app's brand art. `brand` picks a Tessera brand, which `brock icons` copies into `public/logos/` and `build/icons/`; `rim` (`'light'` or `'dark'`) picks its rimmed set. `wordmark` is the app's name drawn as an image, an SVG or PNG under `public/`, given as the path the page loads it from, like the logos:

```ts
// brock.config.ts
product: defineProduct({
  // ...
  icons: { brand: 'my-brand', wordmark: './logos/wordmark.svg' },
  // or with a variant for the dark splash ground:
  // icons: { wordmark: { src: './logos/wordmark.svg', dark: './logos/wordmark-dark.svg' } },
  // or pixel art, scaled with hard pixel edges:
  // icons: { wordmark: { src: './logos/wordmark.png', rendering: 'pixelated' } },
}),
```

- With a wordmark, the boot splash, its failure screen, the window's failure splash (`BootFailureSplash`), the installer's Setup splash (`brock package`) and the About window show the image in place of the name text. Without one, they show the name as before.
- `dark` is the variant for the splash's dark gradient, the way the splash mark comes from Tessera's dark ground set. The three splashes draw `dark`, and About, on the app surface, draws `src`. A plain path is used for both.
- The image keeps the name as its accessible name: the splash page, the window's failure splash and About put it in the heading with the name as its `alt` text.
- Any width fits, never cut and always centred, keeping its proportions. The splashes fit it at most `--size-48` high and `--size-384` wide, in a box only as high as the picture at that width, so a very wide wordmark leaves no empty band (`48` by `384` pixels on the Setup splash, narrower when the splash is or the window is). About fits it to the width of its card, up to `--size-448`, with its height following its proportions up to `--size-48`. Draw it on a transparent ground with the name filling the art's height; a very wide wordmark draws smaller.
- Ship it at least 48 px high (96 for sharp high density screens). The splashes draw it at most `--size-48` high and never scale a smooth picture up, so a PNG, or an SVG with a `height` under 48, draws at its own smaller height. `brock check` and `brock sync` warn, without failing, when `src` or `dark` is shorter; pixel art with `rendering: 'pixelated'` is exempt, since it scales up to fill the row.
- `rendering` is `'auto'` by default: the image scales smoothly, which suits most logos. Set `rendering: 'pixelated'` only for pixel art, so About and the three splashes scale it with hard pixel edges (`image-rendering: pixelated`) instead of blurring it. Any other value fails `defineProduct`.
- Give the dark variant at least 3:1 against both ends of the dark gradient, the large text contrast, so the name reads at its splash size. The status line, the detail and the version keep Tessera's tested text colours, so the rest of the splash still holds WCAG AA.
- `defineProduct` refuses a file that is not `.svg` or `.png` and a path with `..`; `brock package` stops when the dark variant is not under `public/`. `brock icons` leaves the file alone, and `public/logos/wordmark*` is not one of the generated logos, so it is committed.

## How the template and Brock compare

Fixed on this branch:

- The template has `src/widgets/notes.widget.tsx`, `src/widgets/layout.ts` (Notes beside the main view), `.brock/widgets.ts` and `widgets={appWidgets}` with `widgetLayout={appWidgetLayout}` in `src/main.tsx`; its README lists the widgets and the Tessera part folders.

## Recommendations

What this branch leaves alone, and why:

- **Module renderer parts.** `updater` (`UpdateDialog`), `input` (`DeviceCard`, `InputTester`, `StickCalibrationPanel`, `TriggerCalibrationPanel`, the loose `InputTesterScreen.tsx`) and `display` (`DisplaySettingsTab`) keep component folders straight in `src/renderer/`, and `port-kit` has a generic `src/renderer/components/`. Sorting them into `compounds/` and `views/` changes their public import paths and brings them under the usage-file check, so it is a module release of its own.
- **`brock-react` `src/shell/`.** `About`, `ScreenRail` and `TitleBar` are PascalCase folders whose component moved to Tessera; only constants, types and behavior remain. Renaming them touches exported names.
- **Stores, hooks and views are not checked.** `brock structure` does not yet look for stores outside `src/stores` or components outside the Tessera part folders; a check would flag most existing apps at once, so it should land with a migration that lists the moves.
- **Tests in the template.** The template ships no `tests/` folder or test script, so the `tests/<area>/<name>.keep.test.ts` rule is only written down here.

# Brock architecture

Brock is the base-app foundation for Electron + React desktop apps that share the Tessera design system. It is delivered as packages plus a builder: an app installs the packages it needs, and `create-brock` generates the thin skeleton around them. Fixes arrive through `pnpm update` and `brock sync`, never through a git merge.

## Packages

Dependency direction: `lint-config` (dev) <- everything. `core` <- `electron`, `react`, `build`. `react` peer-depends on Tessera, React and zustand. Modules depend on `core`, and on `electron` or `react` for the side they touch. Tessera never depends on Brock.

Every package but `lint-config`, `build` and `create-brock` ships TypeScript source (like Tessera): the consumer's Vite compiles it. The three tooling packages are plain `.mjs`, runnable by Node with no build step.

## The one augmentation point

`@drizztdourden08/brock-core/augment` declares every open interface: `InvokeContract`, `SendContract`, `EventContract`, `IpcNamespaces`, `AppServices`, `Capabilities`, `PlatformPorts`, `ShowFlags`, `ProfileExtension`, `ProfileCreateExtension`, `ProfilePatchExtension`. A module or an app adds members with `declare module '@drizztdourden08/brock-core/augment' { interface InvokeContract { ... } }`. Runtime maps cannot be augmented, so Brock exports `BASE_INVOKE_MAP` and friends and the app composes `{ ...BASE_INVOKE_MAP, ...MY_MAP }` for the preload.

## Modules

A module is an npm package with a manifest at `package.json#brock` (`BrockModuleManifest` in core):

```json
{ "brock": { "id": "updater", "description": "...", "main": "./src/main/index.ts", "preload": "./src/preload/index.ts", "renderer": "./src/renderer/index.ts", "automationFlags": [], "dataDirs": [], "peers": ["velopack"] } }
```

`peers` names packages the app must declare itself, usually a native addon that loads from the app's `node_modules` at runtime. `brock add` installs each one the app lacks, at the module's own version range.

A module with an Android side is also a Capacitor plugin: an `android/` Gradle library in the package and `package.json#capacitor.android.src`, so `cap sync` wires it into the app's Gradle project like any plugin (see Platforms). `brock.android.sdkPackages` names the SDK packages its build needs (the input module's NDK and CMake), which `<app> doctor android` checks. Its renderer side keeps one API: the module's accessor (`inputApi()`, `displayApi()`) returns the preload namespace on the desktop and, on Android, an object of the same type built over the plugin (`nativePlugin` and `listenNative` from brock-core), which `exposeHostNamespace` from brock-react also puts on `window.api.<id>`. App code never branches on the host.

Each subpath exports one object:

- `main`: a `MainModule` (brock-electron): `{ id, onBoot?(product), register(ctx), onWindow?(win, ctx), onWillQuit?(ctx), bootTasks? }`. `onBoot` runs before anything else in `bootstrapApp`, which is where the updater runs the Velopack hooks.
- `preload`: a `PreloadNamespace` (brock-electron): `{ id, build(tools) }` returning the nested `window.api.<id>` object.
- `renderer`: a `RendererModule` (brock-react): `{ id, screens?, settingsTabs?, menu?, Provider?, titleBarActions?, ports? }`.

`brock.config.ts` lists module ids. `brock sync` reads each manifest and regenerates `.brock/modules.main.ts`, `.brock/modules.preload.ts` and `.brock/modules.renderer.ts`, which import the module objects and export them as arrays. The app's own `electron/main.ts`, `electron/preload.ts` and `src/main.tsx` import those arrays. `brock add <id | package>` installs the package (the built-in registry maps `updater`, `secrets`, `input`, `display`, `port-kit`, `tools`, `catalog` to their package names; anything else is an npm spec), appends the id to `brock.config.ts` and runs sync. App code is never edited by the tool.

`electron/` and `src/` are fixed paths beside `brock.config.ts`: the scanners, the managed configs and the checks all read them there, so an app that splits main and renderer across two folders moves them into one ([upgrading-an-app.md](upgrading-an-app.md)); there are no path settings.

Managed files are one-liners regenerated by `brock sync`; `brock check` fails CI on drift. Owned-once files are written at create and never touched again; a breaking skeleton change ships a migration.

`brock migrate` refuses an app with no `package.json#brock.version` (its own, else its workspace root's) and points to `brock adopt`, which pins the version it adopts, so no migration ever runs over an app that was never on Brock; `--tessera-from` alone still runs. It runs the Brock migrations after `--from`, then replays Tessera's `RENAMES.json` over the code the app owns (its `src`, `electron` and `tests`) and over every workspace package that depends on Tessera (its `package.json` names it, or its `node_modules` holds it), such as `packages/design` beside `apps/desktop`, whatever folder the workspace globs put it in; a package that does not use Tessera is left alone. It replays each release after `--tessera-from`, else `package.json#brock.tessera`, else the 0.3.0 baseline, up to the installed Tessera, plus its `next` release when Tessera is linked to main, then pins `brock.tessera` to the installed version. Renames touch only names imported from Tessera, props of object literals whose declared or contextual type is the Tessera type a `props` key names (asked of the TypeScript checker, only for literals that hold such a prop; a `props` key ending in `*` makes every prop with that prefix a to-do, on JSX attributes and typed literals, unless an exact key names it or the installed Tessera's props type still takes it), whole custom-property tokens and bounded class names; in a `<Name>.usage.ts`, the part each `avoidWhen` entry names in `use` and the code of `example` (its Tessera imports, their references and the moves) follow the component renames too, and no other string there; after them, each release's `moves` point an import or re-export of a moved part at its new entry point (the root import never moves); a note in place of a name becomes a numbered to-do in the same report the upgrade verb reads. The rules are in `packages/build/README.md`, Tessera renames.

`brock migrate --tessera-from-copy <folder> --map <file> [--alias <alias>]` converts an app that holds its own copy of the design system (`src/upgrade/tessera-copy/`). The command holds no table of any one copy: the map file gives the folders of the copy and their Tessera entries, the copy's stylesheets, the props a copy component gains and a rename overlay. Named imports of the copy take the Tessera entry of their folder, every `RENAMES.json` release after the map's `from` replays over them, and each imported name is checked against the installed Tessera's entries. The steps are in [upgrading-an-app.md](upgrading-an-app.md).

`<repo> upgrade` works on app folders, not on the repo root: the root when it holds `brock.config.ts`, else every workspace package that does (`apps/desktop` in a monorepo). It bumps the Brock ranges of the root, of each app (with its `brock.version` pin) and of every other workspace package that names Brock, plus the Brock entries of the `pnpm-workspace.yaml` catalog. `brock sync` and `brock migrate` run in each app, from that app's own `brock.version` and `brock.tessera` (else the root's) as read in the main checkout; then `pnpm install --frozen-lockfile` at the root and `brock check` in each app, as CI does; the gate scripts (`lint`, `typecheck`, `lint:md`, `structure`, `test`) run at the root and in each app, then `brock gate` in each app; each app gets its own `.brock/upgrade-report.md`. The steps are in `packages/thread/README.md`, Upgrading Brock.

`brock knip` adds a preprocessor (`packages/build/src/knip-brock-dependencies.mjs`) that drops an app's unused-dependency issue for a package one of its bundled Brock or workspace packages needs at runtime (the `dependencies` and `peerDependencies` of every package the electron-vite config bundles from source, which the app must declare). Knip always reads `package.json#main` (`dist/electron/main.js`) when it exists and no config setting stops it, and the sources never import those packages, so without the preprocessor the result changed after a build. Now a fresh worktree and a built one lint the same. The command launches knip itself, with the config standards' `knipConfigFor` builds, because knip 5 fails on a second `--preprocessor` and the standards runner already passes one; the same preprocessor also drops the hints about the paths it adds to `ignore` because git ignores them.

`brock.config.ts` uses erasable TypeScript only (annotations, `satisfies`), because the `brock` CLI imports it under Node's type stripping, where relative imports need extensions and only `.mjs` packages resolve.

## Main process

```ts
bootstrapApp(product: ProductConfig, options: BootstrapOptions): void

interface BootstrapOptions {
  modules?: MainModule[];
  handlers?: HandlerGroup[];             // { id, register(ctx), devOnly? }, appended to the base set; mainHandlers from .brock/handlers.main.ts
  services?: (ctx: MainContext) => AppServices | Promise<AppServices>;  // built once, exposed as ctx.services
  automationFlags?: string[];            // app flags the launch guard counts
  dataDomains?: DataDomainDef[];         // the app's folders under Data/: ctx.storage, storage:getSummary, the Storage page
  profileHooks?: ProfileStoreHooks;
  rendererFlags?: (argv: string[]) => string[];   // extra --startup-* args
  onReady?: (ctx: MainContext) => void | Promise<void>;  // after paths, before the window
  onWindow?: (win: BrowserWindow, ctx: MainContext) => void;
  onWillQuit?: (ctx: MainContext) => void;
  bootTasks?: MainBootTask[];            // .brock/boot.main.ts
  fileGuard?: (request: { kind, path }, ctx) => boolean | string | void | Promise<...>;  // asked before each write of the base file:* handlers
  paths?: { preload?: string; renderer?: string; splash?: string; splashPreload?: string };  // defaults under dist/electron: ../preload/preload.mjs, ../renderer/index.html, ../renderer/splash.html, ../preload/splash-preload.mjs
  screenshotTimeoutMs?: number;          // how long --screenshot waits before its watchdog captures and exits 2 (default 20 s, or the boot watchdog when longer)
}

interface MainContext {
  product: ProductConfig;
  isDev: boolean;
  flags: AutomationFlags;                // core createAutomationFlags(base + modules + app)
  instance: { name: string | null; profile: string | null };
  paths: { userData: (...seg: string[]) => string; data: (...seg: string[]) => string };
  files: FileStore;                      // Node FileStore rooted at Data/; trash(path) moves a path to the system trash
  profiles: ProfileStore;
  storage: DataDomains;                  // list(), def(id), domain(id): DomainFiles, usage(id)
  job: StartJob;                         // job(id, steps, { title?, cancellable?, visible?, forwardLog?, onDuplicate? }) -> JobHandle
  jobs: JobRegistry;                     // list(), cancel(id), dismiss(id)
  window: () => BrowserWindow | null;
  handle, on, emit;                      // typed against the augmented contracts; take a channel name or a defineChannels entry
  services: AppServices;                 // the app's services (see below)
  log: (message: string, level?: 'info' | 'warn' | 'error') => void;
}
```

App services: `services` builds the app's own service graph (stores, catalogs, process managers) once, at the start of the `modules` boot task, after the paths and data folders exist and before the base handlers, module `register`, the app handlers and `onReady`. `ctx.services` forwards to the built object, so a copy of the context (a boot task's) sees it too; reading it before the build, or with no `services` option, throws and says which. Its type is the open `AppServices` interface: `declare module '@drizztdourden08/brock-core/augment' { interface AppServices extends ReturnType<typeof createAppServices> {} }`. On `will-quit`, after the modules' and the app's `onWillQuit`, a `dispose()` on the services runs once; a failing or rejected dispose is logged. A handler group reads `ctx.services.sessions` in place of a per-context memo.

App handlers by file name: each `electron/handlers/<subject>-handlers.ts` exports one `HandlerGroup` named `<subject>Handlers` (`engine-handlers.ts` exports `engineHandlers`). `brock sync` lists them, sorted by file name, in `.brock/handlers.main.ts` as `mainHandlers`, and `electron/main.ts` passes `handlers: mainHandlers`. Other files in the folder (helpers, an old `index.ts`) are not listed.

Dev-only handler groups: `electron/handlers/<subject>-handlers.dev.ts` (`dataset-handlers.dev.ts` exporting `datasetHandlers`) exists in development builds only, for tools such as an editor that writes the repo's own dataset. Sync lists these in `.brock/handlers.main.dev.ts` as `devHandlers`, which `mainHandlers` spreads after the others, and writes that file only while one exists. A production build (`brock build`, so `brock package`, `brock start` and `launch --prod`) loads `.brock/*.dev.ts` as empty lists through `devOnlyPlugin`, so no dev-only code reaches `dist/`, and stops when another file imports a `.dev` file itself. It matches a file against the app root as given and its real path, since Vite passes real paths and the app folder may be a link, a junction or a short Windows name. `HandlerGroup.devOnly` is the runtime gate beside it: the group ships, and is skipped when the app is packaged.

Boot order: `--os-integration=register|unregister` (writes or removes the link and file type keys, then exits) -> Velopack hooks (updater module) -> portable mode -> `--user-data` -> `app.setName(product.id)` -> the single-instance lock and the open sources (see Links, files and custom schemes) -> crash forensics -> app identity (AppUserModelId `product.appId` on every Windows launch, `<appId>.instance.<name>` for a named instance) -> privileged schemes (`product.schemes` + modules) -> whenReady: paths, data dirs (`product.dataDirs` + modules), session log rotation, the splash window, then the main boot tasks (see Boot) -> quit hooks.

Base handlers: window, app, dialog, file, document, shell, storage, data domains, data transfer, jobs, profiles, config, sessions, uiViews, diagnostics, network, session log, test:screenshot. `network:lanAddresses` (`getLanAddresses` in `BASE_INVOKE_MAP`) returns `lanAddresses()`: every non-internal interface address, IPv4 first, as `{ interfaceName, address, family, cidr }`. Main code calls `lanAddresses()` from `@drizztdourden08/brock-electron/main` directly. `diagnostics:getSystem` (`getSystemDiagnostics`) returns the host facts for a bug report; `diagnostics:getProcesses` (`getProcessDiagnostics`) returns `ProcessDiagnostics`: every process of `app.getAppMetrics()` (`pid`, `type`, `name`, `cpuPercent`, `workingSetBytes`, `privateBytes`, and `window`: the Brock window a renderer process draws, `main` or a widget id, else `null`), the main process `process.memoryUsage()`, `uptimeSeconds`, `windowCount`, `widgetWindows` (`id`, `visible`, `sync`, `cluster`), `ipcCalls` (every invoke and send main has handled through `handle` and `on`), the runtime versions, the GPU feature status and `memoryTotalBytes`, the system memory. The performance widget polls it.

File writes from the renderer: the base `file:*` handlers (`file:writeBytes`, `file:writeText`, `file:remove`, `file:mkdir`, `file:trash`) ask `fileGuard` first, with `{ kind, path }` (`kind` is `writeBytes`, `writeText`, `remove`, `mkdir` or `trash`, `path` relative to `Data/`). A guard that answers `false` refuses the write; one that answers a string refuses it with that reason, as `The app refused to <kind> "<path>": <reason>`; anything else lets it through. Reads are never asked, and main code writing through `ctx.files` is not guarded. `FileStore.trash(path)` (optional on the port) moves a file or folder under `Data/` to the system trash (`shell.trashItem` in main, `file:trash` and `fileTrash` from the renderer) and skips a missing path; the web host has none. `window:setAudioMuted(muted)` and `window:isAudioMuted` (`setAudioMuted`, `isAudioMuted`) mute and read the app window's audio, also as the optional `setAudioMuted` and `isAudioMuted` of the window port; `--muted` still only forwards a startup flag.

`@drizztdourden08/brock-electron/node` is the same code with no Electron import: `initPaths`, `getUserDataPath`, `getLegacyPath`, `ensureDataDirectories`, `resolveDataPath`, `readJsonFile`, `writeJsonFile` and `createNodeFileStore` (its `trash` only when given `trashItem`), so a Vitest test of main-side code points the data folder at a temporary folder (`initPaths(tmp)`) and runs it under plain Node.

Window rules are fixed: the app window is created with `show: false` at its restored bounds and is never shown or resized before the reveal. An automation launch (`flags.isHeadlessLaunch()`) is hidden: every window it opens (splash, app, widget windows, the cluster backdrop) is created with `show: false`, `focusable: false` and placed off every monitor, and is never shown natively. `keepOffScreen` replaces `show`, `showInactive`, `hide`, `minimize`, `maximize`, `focus` and the matching getters on the instance with a logical state that emits the same events, so the reveal, the widget layout and the screenshots work while `IsWindowVisible` stays false, nothing flashes in the taskbar and nothing takes focus. A window that is never shown gets no frames from the OS (a hidden window drew about 2 per second), so the windows of a hidden launch use offscreen rendering (`webPreferences.offscreen`), which paints at 60 frames a second without a native window on screen; screenshots read that surface. A hidden launch turns hardware acceleration off before the app is ready, so those frames are drawn on the CPU and need no GPU (a GPU-less CI runner crashed the GPU process on the accelerated path). WebGL still draws: the launch adds `enable-unsafe-swiftshader`, so a WebGL canvas renders on SwiftShader, the CPU renderer Chromium ships, with the same pixels on every host. `--gpu` keeps hardware acceleration in a hidden launch, for a heavy WebGL check on a machine that has a GPU. `--visible` is the only way to show a window. `--muted` and `--sound` are forwarded to the renderer as `--startup-muted` / `--startup-sound`, never applied to the webContents.

`openExternal(url)` from `@drizztdourden08/brock-electron/main` opens a link in the system browser through the same allow list as a link the renderer opens: `security.externalProtocols` of `bootstrapApp` (default `http:`, `https:`, `mailto:`), set before any window exists. A link with another protocol, or one that does not parse, is refused, logged as a warning and resolves `false`. App main code calls it instead of Electron's `shell.openExternal`. The app window and each widget window cancel any navigation that leaves the page, so a file dropped outside a drop target never replaces the app: a reload, the same origin and a hash or query change stay, a link with an allowed protocol goes to `openExternal`, and the rest is dropped; `setWindowOpenHandler` denies every new window the same way.

`openFolder(path)` and `revealPath(path)` from `@drizztdourden08/brock-electron/main` show a folder or file of the machine, outside the data domains too, and resolve a `Result`. `openFolder` opens a folder in the system file manager (`shell.openPath`); it refuses a file, since opening a file runs its default program, which for an executable is the program itself. `revealPath` shows a file or a folder selected in its parent folder (`shell.showItemInFolder`). Both refuse a path that is not absolute or does not exist, with the reason as the `error`. The renderer reaches them over `shell:openFolder` and `shell:revealPath` (`openFolder`, `revealPath` in `BASE_INVOKE_MAP`), wrapped by the platform's `filePicker.openFolder` and `filePicker.revealPath`.

### Document files

`Data/` holds the app's own state. A document the user keeps where they choose (a sprite, a project, a save) lives at a user path, and the renderer reaches it through the document service. Main owns the dialogs and the disk; the renderer gets paths and bytes.

| Renderer (`usePlatform().documents`, optional) | Channel (`window.api`) | Answer |
|---|---|---|
| `open(options?)` | `document:open` (`documentOpen`) | the absolute path picked, or `null` on cancel |
| `saveAs(options?)` | `document:saveAs` (`documentSaveAs`) | the absolute path chosen, or `null` on cancel |
| `read(path)`, `readText(path)` | `document:read`, `document:readText` | bytes, or text |
| `write(path, data)`, `writeText(path, text)` | `document:write`, `document:writeText` | resolves when the file is replaced |

`options` is `{ title?, filters?: [{ name, extensions }], defaultPath? }`. Extensions carry no leading dot (one is stripped if given); with no valid filter the dialog shows All Files. `defaultPath` is only where the dialog starts. The web host has no `documents` port, so a page checks for it.

A write is atomic. Main writes a temp file beside the target (`<name>.<id>.tmp`), flushes it to disk, then renames it over the target, so a crash mid-save leaves the old document whole. A failed write removes the temp file and rejects. On Windows a rename can be refused while an antivirus scan or an indexer holds the target; it is retried a few times (EPERM, EBUSY, EACCES) before giving up. Writes to one path run in order. The same `writeAtomic` backs the data domains.

The path rule: the renderer may read or write only a path in main's document allowlist. A path joins it in two ways: the user picks it in an Open or Save As dialog in this session (main adds the exact file the dialog returned), or the app's main code lists it with `ctx.documents.allow(path)`, for example the file an `ctx.onOpen` request carried from the OS. Anything else, a relative path, a path with a NUL, or a neighbour file in the same folder, is refused with an error that names the path. The check is on the resolved absolute path (case-insensitive on Windows), per file, never per folder, and the list is in memory, so a new session starts empty. A `defaultPath` in the options grants nothing. A compromised renderer therefore cannot read or overwrite a file the user never chose. A recent files list is the app's to keep: it allowlists a stored path again with `ctx.documents.allow` only after the user chooses it from that list.

### Data domains

`dataDomains` lists the app's folders under `Data/`: `{ domain, label, dir, description?, cleanOlderThanDays?, clearable?, portable? }`. `dir` is a path relative to `Data/` that stays inside it; two domains with one id, an empty `dir` or a `dir` that leaves `Data/` stop the boot. Main code reads and writes a domain through `ctx.storage.domain(id)`, a `DomainFiles`:

```ts
interface DomainFiles {
  domain: string;
  dir(): string;                         // the absolute folder
  path(rel?: string): string;            // an absolute path inside it
  exists(rel), readJson<T>(rel, fallback: T), writeJson(rel, value), readText(rel), writeText(rel, text),
  readBytes(rel): Promise<Uint8Array | null>, writeBytes(rel, data), list(dir?): Promise<DomainEntry[]>, remove(rel), size(rel?): Promise<number>;
}
```

Every path is relative to the domain folder; an absolute path, a drive letter or a `..` that leaves the folder rejects, and a file call on the folder itself rejects. Writes create the parent folders and go through a temp file of their own (`<file>.<uuid>.tmp`, removed when the write fails) and a rename, so a crash never leaves half a JSON file. Writes to one file run one at a time in the order they were called, so two writes at once both land and the last call wins. `list` returns each entry with its total size (a folder's files summed) and its newest change, `size` sums a path, and a missing file reads as `null` or the fallback. The renderer gets the same calls over the `domain:*` channels (`domainReadJson`, `domainWriteJson`, `domainReadBytes`, `domainWriteBytes`, `domainList`, `domainRemove`, `domainSize` in `BASE_INVOKE_MAP`), wrapped by `dataDomain(id)` in brock-react.

`storage:getSummary` and `storage:getDomainUsage` (one domain) walk the folders with one recursive `readdir` and stat the files 32 at a time, the domains side by side, so a large sessions folder no longer stats one file after another. The storage channels besides it: `storage:listDomains`, `storage:revealDomain` (creates and opens the folder), `storage:clearDomain` (removes everything in it unless `clearable: false`), `storage:cleanDomain(domain, days)` (removes each top-level entry whose newest file is older than `days`; a file the OS holds open is skipped), `storage:exportDomains(domains, 'zip' | 'folder')`, `storage:pickImport(format)` and `storage:applyImport(token, domains, mode?)`, `mode` being `'replace'` (the default) or `'merge'`.

Export asks main for a target with the system dialog (a `<app>-data-<date>.zip` or a new `<app>-data-<date>` folder), then copies each chosen domain under `<domain>/` with a `brock-export.json` manifest (`format: 'brock-data'`, `version`, `app`, `appVersion`, `exportedAt`, each domain's label, file count and size). The zip is written one file at a time, deflated when that makes it smaller, with each file's modified time; past 65535 files, or past 4 GB for an entry, an offset or the directory, it carries the zip64 records (the zip64 extra field per entry, the zip64 end record and its locator), which the reader follows too, so a zip export has no practical limit, like a folder export. The writer takes those limits as an optional `{ count, bytes }` (65535 and 4 GB by default), so a test can cross them with a few small files. Import picks a zip or a folder, reads the manifest and returns a plan with a token and each domain marked `known` when the app declares it; `applyImport` then writes the export's copy into each chosen known domain, checking every entry path stays inside the domain and every zip entry's checksum, and gives each file the modified time it was exported with. Replace clears the domain first. Merge keeps what is there and, when both have a file at the same path, keeps the newer one: the domain's file stays when it was modified at least 2 s after the exported one (a zip stamps times to 2 s); the result counts the files written (`files`) and the ones kept (`kept`). Domains with `portable: false` are left out of the export choice. Both run as the jobs `brock-data-export` and `brock-data-import` (`DATA_EXPORT_JOB`, `DATA_IMPORT_JOB` in brock-core), one step per domain, so the job dialog shows them.

### Long jobs

`ctx.job(id, steps, options?)` starts a job and returns its `JobHandle`: `step(id, line?)` makes a step current and marks the one before done, `progress(fraction, line?)` sets the share of the current step, `line(text)`, `log(message, level?)`, `skip(id)`, `setCancellable(on)` (turns cancel off past a point of no return, or back on; the snapshot's `cancellable` follows and the job dialog hides Cancel), `done(line?)`, `fail(error)`, `signal` (an `AbortSignal` that fires on cancel), `started` (a promise that resolves once the job runs, at once unless it was queued), `ended` (a promise of the final state: `done`, `failed` or `cancelled`) and `run(work)`, which calls `done` when `work` resolves and `fail` when it throws. A step is `{ id, label, weight? }`; the job's `progress` is the done weight plus the current step's share over the total. Main sends the whole `JobSnapshot` (`id`, `title`, `state`: `running`, `done`, `failed` or `cancelled`, the steps with their state, `currentStep`, `progress`, `stepProgress`, `line`, `error`, the last 1000 log lines, `startedAt`, `endedAt`, `cancellable`, `visible`) on `job:update`, at once for a step, an error or the end and at most every 100 ms for progress and log lines. `job:list` returns every job main still holds, `job:cancel` aborts a cancellable running job, and `job:dismiss` forgets a finished one. The options are `title` (the id by default), `cancellable` (true by default), `visible`, `forwardLog` and `onDuplicate`. `visible: false` makes a quiet job: it runs and reports like any other, its snapshot carries `visible: false`, and the renderer keeps it out of the title bar item and the job dialog, so many small jobs don't make the title bar flicker while a page can still follow one with `useJob`; a quiet job clears itself 30 s after it ends, failed or cancelled too, since nothing on screen lets the user close it. `forwardLog: true` also writes each of the job's log lines (its `fail` error included) to the app log as `[job <id>] <message>` at the line's level: through `ctx.log` in main (the `main` channel and the console), to the `app` channel for a renderer job. The job's own log still goes when the job is dismissed; the app log keeps the lines. `onDuplicate` says what starting an id that is still running does: `throw` (the default) throws "already running"; `queue` returns a handle at once and starts the job under the same id when the running one ends, however it ends, after any jobs queued before it (its `run(work)` waits for that, and reports made before it starts are dropped, so await `started` before reporting by hand); `parallel` starts it under the first free `<id>-2`, `<id>-3` and so on, keeping the id as the default title; `join` returns a handle on the running job (same id and signal, reports go to that job), whose `run(work)` does not run `work` but resolves with the running job's own `run` result, or, for a job driven by hand, when it ends (rejecting when it failed or was cancelled). A finished job under the id is replaced, whatever the policy. The registry and the handle live in brock-core (`createJobRegistry(emit, now?, sink?)`, where `sink(jobId, line)` gets the lines of the `forwardLog` jobs, from `@drizztdourden08/brock-core/jobs`, with the `JobHandle`, `StartJob` and `JobRegistry` types, which brock-electron re-exports), so the renderer runs the same jobs with no main process: see Jobs under Renderer.

### Links, files and custom schemes

The product declares what the OS hands the app, and Brock registers it at install and routes it at run time:

```ts
product: {
  schemes: [{ scheme: 'app-media', dir: 'media' }],        // served from Data/media, never seen by the OS
  protocols: [{ scheme: 'my-app', name: 'My App' }],        // deep links: my-app://install/abc
  fileAssociations: [{ ext: 'mypack', name: 'Content Pack', description: 'A pack of levels for My App', progId: 'MyApp.Pack', mimeType: 'application/x-mypack', icon: 'file-icons/mypack' }],
}
```

- `schemes` are privileged before ready, as before; one with `dir` is answered after ready by `serveDirectoryScheme` over `Data/<dir>` (Electron's `protocol.handle`, a path that leaves the folder answers 403). A scheme with no `dir` is the app's to handle. `defineProduct` refuses a scheme that is not a bare lower case name, one the browser owns (`http`, `file`, ...), a `dir` that is absolute or climbs out with `..`, an extension written with a dot, a ProgId not shaped like `MyApp.Document`, and any entry listed twice.
- Windows: the updater module's Velopack hooks write the keys under `HKCU\Software\Classes` after install and after each update, and remove them before uninstall, before the app's own hooks: each protocol gets `URL Protocol` and `shell\open\command` (`"<exe>" "%1"`), each extension points at its ProgId and lists it under `OpenWithProgids`, and the ProgId carries the name, the `description` as its `InfoTip` when the file type has one, the icon (`resources/file-icons/<ext>.ico`, which the builder config ships from `build/<icon>.ico`, else the exe) and the open command. Uninstall removes the protocol keys, the ProgIds and the `OpenWithProgids` values, never an extension another program claims. A portable copy runs no Velopack hook, so the installer stub, after unpacking one, runs `<exe> --os-integration=register` when the product declares a protocol or a file type (`BROCK_REGISTERS_OS`). `registerOsIntegration` and `unregisterOsIntegration` are exported for an app that writes its own hooks.
- macOS: the builder config passes `protocols` and `fileAssociations` to electron-builder, which writes `CFBundleURLTypes` and `CFBundleDocumentTypes` into Info.plist.
- Linux: the same config puts `x-scheme-handler/<scheme>` and each file type's mime type (`application/x-<ext>` when none is given) in the deb's `.desktop` file, and electron-builder installs the mime XML, each type's comment being its `description`, else its `name`; the managed `deb-postinst.sh` then runs `update-mime-database` and `update-desktop-database`. The Velopack AppImage has no installer, so on each packaged launch from an AppImage main writes `~/.local/share/applications/<id>.desktop` and `~/.local/share/mime/packages/<id>.xml` when their text changed, and refreshes both databases.
- Routing: requests are parsed from argv at launch (a non-flag argument whose scheme is a declared protocol, or whose extension is declared, resolved against the working folder), from a second launch, and on macOS from `open-url` and `open-file`. Each becomes an `OpenRequest`: `{ kind: 'url', url, scheme, source }` or `{ kind: 'file', path, ext, source }`, `source` being `launch` or `running`. An app that declares a protocol or a file type takes the single-instance lock (`singleInstance` of `bootstrapApp` forces it on or off); a second launch quits before crash forensics opens the log and hands its argv to the first, which brings its window forward. A named instance and an automation launch never take the lock.
- Delivery waits for the reveal. Then each request goes to every main handler (`ctx.onOpen(handler)`, which returns the unsubscribe, and `bootstrapApp({ onOpen(request, ctx) })`) and to the renderer: the first `app:takeOpens` call returns what arrived before it, and later ones come on `app:open`. `BrockApp` drains both into `appOpen`, which holds requests until a handler exists and hands them to every handler that subscribes before the next task, so two screens mounted together both see a launch request; a screen subscribes with `useAppOpen(handler)` or `appOpen.on(handler)`.

### Content catalogue

The `catalog` module (`@drizztdourden08/brock-catalog`) is a generic content catalogue client, for any app that installs items from its own catalogue (presets, themes, levels): `configureCatalog(ctx, config)` gives it the app's endpoint, schema validators, routes and one installer per container, and it serves the reads over `catalog:*`, runs each install as the job `catalog-install:<id>` through `ctx.job` (grant, download, verify, unpack; cancel is turned off once the download is in; the size and sha256 must match the grant before anything is unpacked; an update installs before it releases the old copy through the app's `onRelease`, and what the installer removes goes to the system trash unless `removeTo: 'delete'`), keeps the installed record in `Data/catalog/installed.json` for the renderer's installed guard (`useCatalogInstalled`, `installedByName`) and for `readInstalledRecords`, which reads it with no context, gives app code `isCatalogInstalling(itemId, jobs)` and `catalogJobId`, and parses install links of `config.linkScheme`. The app declares the scheme in `product.protocols` (see Links, files and custom schemes); the module subscribes to `ctx.onOpen` and takes every `url` request of that scheme, from the launch argv, a second launch or macOS `open-url`. `getCatalog(ctx).links.deliverUrl(url)` stays for a link that reaches the app another way, such as one pasted into it. What an item is, where it lands and what uses it stay in the app. The details are in `packages/modules/catalog/README.md`.

## Boot

The splash window is the only loading screen. Nothing loads inside the app window before it appears.

1. On ready, main opens the splash: no frame, no border, no rounded corners, no shadow, not resizable, centred on the display the app will open on. It shows the gradient, the mark without its tile, the app name (or the app's wordmark image, see below), a status line, a thin bar on the bottom edge and the version.
2. Main runs its boot tasks. `modules` registers the base handlers, module `register`, app handlers and `onReady`. `window-state` runs after it and creates the hidden app window at its saved bounds. Module and app main tasks run after `modules`.
3. The renderer runs its boot tasks: `profiles`, `settings`, `fonts`, `images` (the brand logos decoded, and both `product.icons.wordmark` images when the app sets one, so About draws its wordmark at once), module and app tasks, then `first-frame`, which waits for every other task and resolves once the home screen has painted.
4. Both sides report weighted progress, the running label and a detail line. Main joins them and relays one bar to the splash.
5. When every task resolved and the first frame arrived, the splash fades from 1 to 0 while the app window shows at 0 and fades to 1 over the same 220 ms. Then the splash is destroyed. Widget windows restored from the saved layout during boot are created hidden and join this reveal (see Widget windows). A hold added to the reveal while it waits for others is waited for too.

A task is `defineBootTask({ label, weight?, after?, timeoutMs?, run })`. The id comes from the file name: `src/boot/<id>.task.ts` runs in the renderer, `electron/boot/<id>.task.ts` in main. `brock sync`, `brock build` and `brock dev` write the lists to `.brock/boot.renderer.ts` and `.brock/boot.main.ts`. Modules add tasks through `bootTasks` on `MainModule` and `RendererModule`. `run` receives `report(fraction, detail?)`, an `AbortSignal` and the side's context: the main context in main, `{ product, profile, platform, openExternal }` in the renderer, where `platform` is the resolved `Platform` (its ports: `filePicker`, `files`, `storage`, `window`, `device`, and `capabilities`), so a task that registers a search action can open the file picker or a link. The runner in brock-core starts a task once everything in its `after` list is done, runs independent tasks together, aborts a task at its timeout (default 20 s) and stops on the first failure.

Profile hydration resets every session store (`createSessionStore`) when the active profile changes; on boot that happens after `profiles` picks the profile and before `settings` resolves. A renderer task that fills a session store must therefore run `after: ['settings']`, or the reset wipes what it wrote. In development the renderer boot warns in the app log when that reset finds a session store already filled, naming the app and module tasks that can run before `settings`. The warning comes from the boot runner, not from `defineBootTask`, since only the runner sees the whole task graph and the moment of the reset.

A failed or timed out task stops the boot on the splash with the error and Retry, Open logs and Quit. Retry reloads the app window when only a renderer task failed, and relaunches the app otherwise. The watchdog turns 8 s of silence from the renderer (120 s in development, where the dev server can take long to serve the first page) into the same error screen; the renderer sends a heartbeat every second while its tasks run, and main also counts the app window starting to load, its `dom-ready` and its `did-finish-load` as signs of life. `product.boot.devWatchdogMs` and `product.boot.watchdogMs` in `brock.config.ts` set the two, and the `BROCK_BOOT_WATCHDOG_MS` environment variable overrides whichever applies. Only the watchdog's own failure is undone: when the renderer answers after it fired (a heartbeat, progress or `boot:ready`), main clears the failure, the splash goes back to the progress, and a `boot:ready` reveals the app as usual. Automation launches (`--review`, `--screenshot`) still end on the first failure. The app window never shows half loaded. The splash page is static HTML built from Tessera's `splash.css` kit (`ts-splash`, `ts-stage`, `ts-mark`, `ts-title`, `ts-status`, `ts-detail`, `ts-actions`, `ts-button`, `ts-progress ts-progress--edge`, `ts-version`; a failed start adds `ts-status--danger` and `ts-progress--danger` and shows the error in `ts-detail`), and Brock's `splash-page.css` keeps only the failure layout and the entrance of the mark and the name: no background, no text colour and no shadow, so Tessera paints its dark gradient (`--c-gradient-dark-from` to `--c-gradient-dark-to` of the palette) under its tested text, which holds WCAG AA on it (MIGRATION 171 and 180). The mark is `public/logos/mark.svg`, which `brock icons` copies from Tessera's dark ground set (`brand/dark-ground/<brand>.svg`) for an app with a Tessera brand, so it reads on the dark ground (MIGRATION 176). When the window is already showing (a renderer task fails after the reveal, or in the browser), the window draws the same splash with Tessera's `Splash` (`BootFailureSplash`): the app name, the mark (`product.logos.mark`, the same dark ground file), `<task> failed` (or `took too long`) as the failed status, the error as its detail, a full danger bar, the version, and the actions Retry (reloads the window), Open logs (the `debug` folder, through `storage.revealLogs` and `debug:revealLogs`) and Quit (closes the window); a host without `revealLogs` leaves Open logs out, and one without window chrome leaves Quit out. The splash covers the window as a fixed layer, the app root is `inert` under it so keys never reach the shell, and the screens are not drawn. Brock adds no style of its own to it, so both splashes paint the same dark ground. The splash plugin puts the look on the app page too (a `<style data-brock-look>` with the `--look-*` properties), so the two splashes share any `--look-dark-from` and `--look-dark-to` and the angle. With `product.icons.wordmark`, both splashes show its dark ground image (`wordmark.dark`, which is `wordmark.src` unless the app gives a variant) in place of the name text, at most `--size-48` high and `--size-384` wide. The splash page writes `<h1 class="ts-title"><img class="ts-wordmark" alt="<name>">`, sized by Tessera's `splash.css` (`ts-wordmark`, narrowing with the title box), and `BootFailureSplash` passes `wordmark.dark` to Tessera's `Splash` as `wordmark`, which draws the same image with the name as its alt text (MIGRATION 240). Brock adds no wordmark rule of its own to either. Since Tessera 0.42 (MIGRATION 259) the box keeps the height of the picture up to `--size-48`: a very wide wordmark draws a box only as high as the picture at its width, with no empty band, and a smooth picture under 48 px high draws at its own height, never scaled up, so `brock check` warns about one (app-structure.md, Product icons). With `wordmark.rendering: 'pixelated'` the splash page adds Tessera's `ts-wordmark--pixelated` to the image and `BootFailureSplash` passes `wordmarkPixelated` to `Splash`, which adds the same class: the sprite scales up with hard pixel edges to fill the `--size-384` row, its height following its proportions up to `--size-48`.

The look comes from `resolveLook(product, sources)` in brock-core: `product.look = { gradient: [from, to, via?], angle? }` first, then the Tessera brand gradient (`brands.<brand>.gradient` and `angle` in the Tessera package `tokens.json`), then a gradient derived from the palette seeds (`--p-primary` from the app theme, `theme.css` of `tessera.config.json` or `src/theme.css`, else from the brand palette `palettes/<brand>.css`, else Tessera's default palette, into `--p-black`). The build resolves it and writes `splash.html`: static HTML with `data-palette` set to the brand, Tessera's token stylesheets, the brand palette, the app theme, two inlined font faces, the look as custom properties (`--look-from`, `--look-via`, `--look-to` and `--look-angle`, which the installer's downloader window still paints across its top, and `--look-dark-from` and `--look-dark-to` only for an app with colours of its own: `product.look`, or palette seeds in its theme that do not set `--p-gradient-dark-from` or `--p-gradient-dark-to` too; `darkPair` in brock-core darkens the two ends of its look toward black until the palette's `--c-text-dim` holds 4.5:1 on each, and an app on a Tessera brand or palette gets the tested tokens) and the page stylesheet (`packages/build/src/splash/splash-page.css`, tokens only). The page talks to main through the splash preload (`window.brockSplash`). An app that ships `src/splash.html` replaces the generated page.

`--screenshot=<name>` writes `Data/screenshots/<name>.png` of the app window and quits, once the window is revealed and every screenshot hold the renderer took is released. A watchdog bounds the wait: after 20 s or the boot watchdog, whichever is longer (so 120 s on a dev launch, whose first page can take that long, or `product.boot.devWatchdogMs`), or `screenshotTimeoutMs` of `bootstrapApp`, or `--screenshot-timeout=<seconds>` on the command line (a value that is not a positive count of seconds logs a warning and keeps the default), it captures what the window shows, logs why it fired (the window never revealed, or how many holds were still open) and exits with code 2, so a script or CI run sees the hang instead of a picture taken too early; a boot failure still exits 1. A lazy load (`lazyComponent`, a lazy title bar item, a lazy tour) holds too, from its start until it settles and a frame has painted, and so does a `LazyHost` fallback while it is drawn, so the capture never shows a loading spinner. A widget asked to open holds from that call, not from when its lazy import starts: `widgets.open`, `widgets.toggle`, `widgets.force` (and the forced widgets again on a profile switch), `widgetKits.open`, `widgetKits.toggle` and `widgetKits.openWidget` each hold until the widget's `WidgetBody` mounts, and a kit opened that way holds until each of its overlays' `KitOverlay` mounts, so a widget forced just before the capture is pictured drawn, not as a spinner or an empty body; the body's own lazy load and fallback holds take over from there. Such a hold lets go by itself on the next frame when the widget did not open, after 60 frames when it is open but its body never mounts (a tab behind another, a context gate), and after 5 s at most, which is also how long a forced id that no widget has registered yet can hold. The renderer reports 0 only once two frames have passed with no new hold and every image on the page that is not `loading="lazy"` has loaded (or failed, or waited 5 s) and finished its fade-in. Main adds up the holds of each window (the app window and every widget window, dropping a window's holds when it closes) and captures only once the total has stayed at 0 for 50 ms, waiting again when a hold comes back in that time. A hold is the app saying it is not ready to be pictured yet, such as a game view whose first frame has not drawn: `holdScreenshot()` from brock-react returns its release, and `useScreenshotHold(holding)` holds while `holding` is true; the renderer reports the count of open holds to main (`capture:holds`). Take the hold before the boot ends (in a renderer boot task, or in a part the first frame draws), since main reads the count when the window is revealed. The picture is taken from the window's surface through the debugger (`Page.captureScreenshot`), which gives the current frame for a headless window placed off every monitor, where `capturePage` returns a stale one; when the debugger is taken (DevTools open) or fails, it falls back to `capturePage`. `test:screenshot` captures the same way. The review's own captures (`review:capture`, `review:captureWidget`, `review:captureGroup`) wait for the same holds, stable for 50 ms the same way, up to 10 s, and the review's `settle` before each capture also waits for the page's images to load and fade in; a hold still open then fails a `capture-holds` check for that step and the capture goes ahead.

`--screenshot-splash=<name>` writes `Data/screenshots/<name>.png` of the splash mid-boot, and `<name>-failed.png` when the boot stops, then quits unless `--review` or `--screenshot` also runs. A `--review` run captures the splash on its own, as step 00 of the report.

## Preload

```ts
createPreloadBridge({
  maps: { invoke: INVOKE_MAP, send: SEND_MAP, events: EVENT_MAP },
  namespaces?: PreloadNamespace[],       // module and app nested objects
  helpers?: Record<string, unknown>,     // extra non-IPC values
  exposeAs?: string,                     // default 'api'
  debugGlobal?: { name: string; values: Record<string, string | null> },
}): void
```

The bridge adds `isDev`, `os`, `getFilePath`, `startup` (`fresh`, `automation`, `muted`, `sound`, `flags`) and `instance` (`name`, `profile`), parsed from the `--startup-*` flags main forwards through `additionalArguments`.

[ipc.md](ipc.md) walks one app invoke channel and one event channel from the declaration to the renderer call. `defineChannels({ engineStatus: invoke<() => Promise<EngineStatus>>()('ap:engine:status'), onProgress: event<(p: number) => void>()('ap:engine:progress') })` in brock-core is the one declaration: its `maps` feed the preload, `InvokeContractOf`, `SendContractOf` and `EventContractOf` of its type feed the augmentation, main's `handle`, `on` and `emit` take an entry in place of the channel name, and brock-react's `channelApi(APP_CHANNELS)` types the renderer calls by method name. The builders are curried (`invoke<Signature>()('channel')`) because TypeScript cannot infer the channel literal once the signature is given explicitly. Channels written in the augmentation, a map and a handler keep working.

## Renderer

```tsx
<BrockApp<S>
  product={product}
  settings={{ defaults: DEFAULT_SETTINGS }}
  screenTree={screenTree}         // from .brock/screens.ts
  widgets={appWidgets}            // from .brock/widgets.ts
  widgetKits={appWidgetKits}      // from .brock/widget-kits.ts
  modules={rendererModules}
/>
```

An app not yet on the convention still passes `screens`, `home` (the base layer once a profile is active), `menu`, `homeScreen` and `credits`, and `settings.tabs`. Both can be given: the `screens` and `menu` props are added beside the generated ones.

- `defineScreen({ id, title, icon?, render(ctx), layer?: 'fullscreen' | 'own', size?: 'fill' | 'info', keepMounted?, devOnly?, group?, shortcut?, requiresProfile?, subtitle?(ctx), extra?(ctx), floating?(ctx) })`. `icon` is an icon name, as in menu entries and `ScreenMeta`, or an element. A fullscreen screen sits in the reference frame: a 90% card over a scrim (with a base screen under it, `ScreenHost` draws `screen-host__scrim`, Tessera's `--c-scrim`, over the base layer while the screen or hub is open, so the base content no longer shows through around the card or under the bucket switch), one header with title, subtitle, `extra` and the close button, `floating` overhanging the top edge, a 0.2 s entrance. `size: 'info'` (a card's `meta.size`) opens it instead as a small window sized to its content and centred, at most `--size-512` wide, with no page header and its content scrolling inside: Tessera's `ScreenWindow` `size="info"` (MIGRATION 230), the size About gets from `InfoScreen`. Built-in screens: `profiles` (list, create, delete; the setup screen when no profile exists), `settings` (the hub over `settings.tabs`), `about`, and `credits` when the app gives credits, which opens with `size: 'info'`.
- `defineHub` makes a fullscreen screen too (its `HubDef` takes `nav` as a bucket does, see Screens by convention), and the hub switch is its `floating` part when two hubs or more exist. A hub window has no title row (Tessera's `ScreenWindow` `titleRow={false}` with `movable`, MIGRATION 261): the hub title is the dialog's `aria-label`, Escape closes it, and a round X sits on the top right corner with a lock beside it. Locked, the window is the centred card; unlocked, the user drags it by its top band or the arrow keys and resizes it by its edges. All hubs share one window. `ScreenHost` passes `ScreenLayer` the `free` key `brock.hub` for every hub, which becomes the `storageKey`, so the lock and the rect live in one place (`brock.hub:locked` and `brock.hub:rect` in `localStorage`): the window keeps its position, size and lock whichever hub is shown, and a closed window reopens where it was left, whichever hub opens it. Every hub layer also takes the same React key (`layerKeyOf`), so switching hubs keeps the same `ScreenWindow` mounted instead of remounting it; the hub content under it is keyed by hub id, so each hub still starts with its own state. The window has no Back button: Escape, the hub switch, Alt+Left and the mouse Back button cover going back. The save status and the active profile tag (shown when two profiles or more exist) sit in the floating switch area, to the right of the hub switch (`HubSwitch` `status`), and take no row. The hub's `subtitle` and `extra` are not passed to the window, as a window with no title row drops them. Plain screens keep the title row.
- Home: `product.homeScreen` (default `settings`) is the target of the Home menu entry, and of Escape when nothing is open and there is no closed window to reopen. The base screen (`home`, from `src/screens/<id>.base.tsx` or the legacy prop) is what shows when nothing is open; Escape on it reopens the window closed last, or opens the home screen over it. With no active profile and a home screen that needs one, Escape with nothing open opens the profiles route instead (`profiles`, or `product.profilesRoute`), Escape on that route (at its top level) keeps it open instead of closing it to an empty window, and the Home menu entry shows as disabled with the reason, Pick or create a profile first, so no path is a dead end.
- Menu order: Home, Profiles, Settings (unless it is home), app entries, sections, module entries, Credits, About, Quit, each built-in with an icon. Credits, About and Quit form the last group of the menu, in that order, so the View sub-menu and the title bar actions the bar adds come before them; the review's `menu-ends` check reads the end of the open menu. `MenuItem.section` files an entry under a submenu (`widgets`, `advanced`, or a new one named after the id); `devOnly` entries and the built-in Dev Console need developer tools (development, the `developerToolsEnabled` setting, or the app's own switch; see Developer tools). An app submenu whose label is the label of a section in the menu (an `Advanced` placed by `meta.menu: 'Advanced'`, in any case) joins that section instead of standing beside it, so the menu never shows two Advanced; its entries keep their order, ahead of the module and built-in ones. `MenuItem.useDisabled`, a hook returning a boolean, disables an entry while it returns `true` (a module's Save state while nothing runs); the shell calls every such hook of the app and module menus each render, in their fixed order, so a module menu stays a fixed list. A static `disabled: true` still wins.
- Menu overrides: `product.menu.entries` (`{ <key>: { inMenu?, hidden?, label?, activeLabel?, group?, order?, before?, after?, parent? } }`, `ProductMenuEntry` in brock-core; `activeLabel` is for `window-pin` and `window-fullscreen` only) and the same object in a screen's `meta.menu` change the detected menu per entry key ([app-structure.md](app-structure.md), Menu order and overrides, lists the keys and the fields). `useShellMenu` builds the four groups (`main`, `sections`, `modules`, `end`) with `menuGroups`, then `resolveMenu` (brock-react `menu/`) plants them as one list per group and per submenu, plants the sub-menus a widget, kit or Developer entry names as its `parent` when no entry has that key (`growParents`, see The Widgets menu), merges each entry's own fields with the config's, renames, moves by `parent` and `group`, sorts by `order` (stable, 0 by default) and places by `before` and `after` in anchor order, skipping a loop. It returns the entries, with the ones out of the menu kept and flagged (`inMenu: false` or `hidden: true`), the issues and one record per overridden entry. The title bar gets `visibleMenu(entries)`, without both; the search palette gets `searchableMenu(entries)`, without the `hidden` ones only. `useMenuHiddenRoutes` puts the routes of `hidden` entries (and of everything under a hidden submenu) in `useMenuHiddenStore`, which the search index adds to its hidden routes and `shortcutTarget` and the shortcuts dialog skip, prefix-wise, so a hidden bucket hides its pages; `open(route)` still works. Entries the resolver leaves in the `end` group carry `group: 'end'`, which is how `titleBarGroups` splits the last group off (`LAST_GROUP_KEYS` still covers a hand-made menu without it). The View sub-menu is Tessera's (`WindowTitleBar` `view`, Tessera 0.37.4). Brock renames it through `TesseraProvider`'s `strings.windows.view`. A `view` override that places or hides it plants a marker entry keyed `view` at the end of the `modules` group (`barMarkers`, `BAR_MARKERS`), which moves like any entry; a `window-pin` or `window-fullscreen` override with `group`, `order`, `before` or `after` plants a marker of that key the same way. A marker that lands in a submenu is dropped with an issue. `searchableMenu`, `buildMenu` and the review's menu leave the markers out, and while View is hidden the review's `menu` step reads the drawn panel without the tucked rows (`withoutTuckedRows`), whose place depends on the window width. `titleBarGroups` takes them out of the drawn menu and returns each one's group (`menu` or `menu-end`) and its index there, counted with separators and without the other markers, as `view={{ group, position }}` and `tucked` places. `viewHidden(product.menu)` gives `view={false}`. With View hidden, Tessera lists a tucked pin and full screen button in the main menu itself (`window-title-bar-pin` and `window-title-bar-fullscreen`, first in the bar's own group by default), as actions with no check mark; Brock adds no entry for them. `AppTitleBar` passes `tucked={tuckedRows(product.menu, places)}` alongside `view={false}` only: `label`, `activeLabel` and `hidden` (from `hidden` or `inMenu: false`) come from the config, `group` and `position` from the markers (MIGRATION 244). An `activeLabel` on any other key is dropped with an issue. The pin state sits in `usePinStore`. Issues go to the log once each in development (`reportMenuIssues`), and `brock check` checks the config's shape and its `bucket:` and `screen:` keys (`menuConfigProblems`), and warns when View and both tucked rows are out of the menu, or when `window-pin` or `window-fullscreen` is set while View is shown (`menuConfigWarnings`). With no active profile, `lockProfileEntries` disables every entry whose route resolves to a screen with `requiresProfile` not `false`, with the Home reason. The review's `menu` step reads the drawn panels with `readMenuPanel` and reports `menu-entry-<key>` per record (`menuOverrideChecks`), the `search` step reports `search-hidden-<key>` per `hidden` record (`hiddenSearchChecks`), `menuExpectation` takes the overridden keys, the View label and whether View is hidden, and the `buckets` step leaves hidden screens out of its `<id>-in-menu` checks.
- `useNavigation()`: `{ active, params, open(id, params?), close(), back() }`, backed by a zustand store so non-React code can call `nav.open`, `nav.back()`, `nav.up(params)` and `nav.escape()`. Escape follows Tessera's escape stack (`useEscapeStack`, MIGRATION 211): every surface registers a level, from the innermost `drag`, then `popover`, `menu`, `dialog`, down to `screen`, and one listener on the document closes only the innermost one. A Tessera dialog (the confirm dialog, the bug report, the shortcuts help, the update dialog), a menu, a popover, a confirm ask, the tour and the search palette (Tessera's `CommandPalette`, registered at `dialog` while open: a row's question at `popover` cancels first, then an Escape in the search box clears its text, then the palette closes; Brock keeps no Escape listener of its own for it) close there. Brock's shell listener sits on the root element, so it runs after the key's own handlers and before Tessera's document listener, and it takes Escape only while nothing above `screen` is on the stack and no inner control consumed the key with `preventDefault`. It then goes in order: an escape layer registered with Brock's `useEscapeLayer` (a surface tracked in a store), the dialog store, the open screen, then reopen the window closed last, then open home, and marks the key handled so the `ScreenWindow` frame, which registers at `screen` with its `onClose` since Tessera 0.29, does not close the screen a second time. A popped widget window runs the same listener on its own document, with no screen or home to close. On the open screen Escape closes the window in one press, from any page or sub-page; it never goes up to the hub home first (Back, Alt+Left and the mouse Back button walk the history). With nothing open, Escape reopens the window closed last (`nav.reopen()`) as it was: its page, tab or sub-page (`closed: { active, params, history }` in the store, kept in the saved navigation so a restart can reopen it too), its page history, and the scroll offsets of its scroll areas (`screens/scroll`: `ScreenHost` marks each screen's root, reads the scrolled elements by their place in it when the screen closes or another opens, and puts the offsets back on the frames after a reopen, once the content is tall enough). The last closed window has to be allowed still (dev-only, profile and `show` rules); otherwise Escape opens home. Escape inside a concealed title bar the keyboard revealed (Tessera's `window-title-bar--concealed`) is left to the bar, which hands focus back, so leaving it reopens nothing. Escape in a non-empty text field clears the field first; the next Escape goes down that order.
- History: the store keeps a page history per screen (`history[<hub>]`, 50 steps at most). Opening another page of the open hub pushes the page it leaves; opening the page already shown pushes nothing. Back walks it: the Back button drawn before the window title while there is a step to go back to (a hub window has no title row and draws none, see `defineHub`; for any other screen `ScreenLayer` passes `back`, Tessera's `BackAction` `{ onSelect, label }`, to `ScreenWindow`, whose `WindowHeader` draws an arrow before the title and outside the heading, so the screen dialog keeps the title alone as its name; `label` is the page Back goes to, the screen title, so the arrow reads Back to Tools), Alt+Left and the mouse Back button (button 3). Switching to another hub keeps each hub's page and history, and opening a hub by its bare id (the hub switch, the hub's menu entry) brings it back on the page it was left on, while the Home entry (and Escape with nothing open and no closed window to reopen) always opens the home hub on its home page (`nav.home(id)`, `open(id, params, { fresh: true })`, a menu item with `fresh: true`); an explicit route (`open('game/saves')`) goes to that page. Closing a hub drops its history from `history` and remembers its page; the history comes back only through Escape's reopen. `useCanGoBack()` reads whether Back would do something.
- Unsaved changes: `useUnsavedChanges(dirty, message?)` guards the page while `dirty` is true and returns `release()`, which a save calls before it navigates so the guard lets it through. Any navigation away (open, back, up, close, Escape, the hub switch) first asks `confirmAction` with Tessera's words, Unsaved changes with Discard and Keep editing (`common.unsavedTitle`, `common.discard`, `common.keepEditing`), and Quit lists the message among the before-quit messages. `leaveGuards.add(() => boolean)` registers a guard from outside React.
- Screen state: `useScreenState(key, initial)` returns `[value, set]` (set takes a value or an updater) from one zustand store, `useScreenStateStore`, scoped to the screen or page it is called in: the screen id, or `<hub>/<page>` (`<hub>/<page>/<tab>` on a tab, `<hub>/<page>/<sub>` on a sub-page) inside a hub, through `ScreenStateScope`. The state outlives the screen, so a page opened again shows what it showed. `screenPersistence` keeps it per profile in `ui-views.json`, through the same `profileViews.patch` the widgets use, under `profile:<id>.screens`: `{ nav: { active, params, history, remembered }, state: { <scope>: { <key>: value } } }`. A malformed scope is dropped on load. A tab page remembers its last tab there, under the hub scope as `tab:<page>`, and opens on it when the route names no tab; a route that names a tab still wins. When the profile loads, the saved open screen, its page and history come back over the startup state (nothing open, the profiles screen, or the home hub on its home page with no history); a screen the app no longer has is dropped; an automation launch keeps the screen state but not the navigation.
- Screen focus is Tessera's: `ScreenLayer` moves focus into a screen when it opens (to its title), keeps Tab inside, makes every sibling in its parent `inert` and gives focus back to the opener when it closes, so Brock has no focus or inert code of its own. The layers' positioned parent is the screen host (`.brock-app__screens`, inside the main view of the dock); the title bar and the widget dock sit outside it, so both stay usable while a screen is open. The review checks it on every screen (`<id>-focus-in`, `<id>-page-inert`, `<id>-title-bar-usable`, `<id>-dock-usable`). Every screen and every widget (docked or popped out) renders inside `RenderErrorBoundary` (Tessera's `ErrorBoundary`): a throw shows "This page hit an error" (or "<widget> hit an error") as Tessera's LoadError box (the raw error behind Details, Retry draws the part again and logs it), then Reload page, Go home and Report a bug, and logs the error, instead of blanking the app. Since Tessera 0.24 `ScreenWindow` is a `screen-window` inline-size container (MIGRATION 199), so an element positioned against the viewport inside a screen now positions against the window: the layers that must cover the whole app window (the boot failure splash, the tour layer, the window guide, the job host, the palette and the toasts) render in the app shell beside the screen host, or portal out as Tessera's tour layer and toasts do, never inside a screen, and the dock drop hints belong to the `DockLayout` around the main view. A screen's error boundary is in flow, so it fills the window it belongs to. Screen content that follows the window's width uses `@container screen-window`, not a media query. A `ScreenPage` header that runs out of room moves its strip, then its actions, under the title instead of cutting the title, and a `StageScreen` toolbar wraps under its heading; Brock hides neither for a narrow window.
- `useProfiles()`: `{ profiles, active, select, create, remove, removeConfirmed, refresh, lastProfileId }` over the platform `FileStore` and `createProfileStore`. `setLast` is skipped on an automation launch. `remove(profile)` asks the delete confirm first; `removeConfirmed(profile)` removes at once and resolves `true`, or `false` when the app kept the profile. Removing the active profile activates the most recently used profile left (`select`, so it becomes the last profile too) and leaves the user on the screen they are on; only when no profile is left does it open the profiles route. Removing another profile changes neither the active profile nor the screen. `profiles.onBeforeRemove(profile)` on `BrockApp` runs before every removal, after the confirm: it may be async, and returning `false` (or throwing, which is logged) keeps the profile, so an app stops the work tied to that profile, such as a running session, or refuses while it runs. `profileRemoval.add(fn)` registers one from outside React and returns the remove call.
- `useSettings<S>()`: `{ settings, patch, hydrated }` from `createSettingsStore<S>({ defaults, load, save, normalise?, transformPatch? })`, one per profile, debounced save to `config.json`. `settings.normalise(settings, stored)` on `BrockApp` runs once a profile hydrates, on the defaults merged with what was stored (and that stored object, or null), and returns the settings the app runs with, so a value an older version wrote (an out-of-range number, a renamed option) is mended before anything reads it; it is saved with the next change. `settings.transformPatch(patch, settings)` runs on every `patch` before it is applied, saved or seen by the `effects`, so a change can bring a related one with it (full screen turning borderless off). The store keeps `saveStatus` (`idle`, `saving`, `saved`, `failed`), `saveError` and `savedAt`, and `retrySave()` writes a failed save again. The settings and hub headers show Saved after a write, or Not saved with Retry; a failed write also raises a danger toast with a Retry action (Tessera's toast `action`) that calls `retrySave()`. `toast(message, { variant, duration, action })` takes the same `action` for any toast.
- Paths on the machine: `usePlatform().filePicker` has `pickPath(options?)` and `pathOf(file)` and, on Electron, `openFolder(path)` and `revealPath(path)` (each resolves a `Result`; see Main process). They are optional, and the web host has none, so a page draws an Open folder or Reveal action only when the one it calls is there. A settings `path` control passes `revealPath` to Tessera's `PathInput` as `onReveal`, so it draws Reveal on Electron; a reveal that fails raises a danger toast with the reason.
- Startup is the `profiles` boot task: pinned instance profile (fail loudly if missing) -> single profile -> last profile -> the `profiles` screen.
- The app names its profiles route: `product.profilesRoute` (a route such as `'data/profiles'`, a hub page that draws Brock's `ProfilesScreen` or its own list) makes `profiles` a route alias to it, so the Profiles menu entry, the `profiles` boot task (no profile, an unknown pinned profile, several profiles and no last one), `useProfiles().remove` of the last profile, Escape with no profile and any `open('profiles')` land there, and Brock's own `profiles` screen is not registered. `ProfilesScreen` closes the hub after a pick when it is open on that route, as it closes its own screen, and a restored navigation takes over from it at startup. Unset, nothing changes. A hub that holds that page usually also sets `requiresProfile: false` on its bucket (see Screens by convention), so it opens on a first run. `useBootStore` holds the renderer boot phase; the review tour starts when it is `ready`.
- Logos come from `product.logos`: `app` (default `./logos/icon-32.png` with `icons.brand`, the 32 px icon that keeps the rim crisp at the title bar's 20 px; `./logos/icon-256.png` without one) in the title bar and the about screen, `mark` (default `./logos/mark.svg`, the mark without its tile, in its look for the dark gradient with a Tessera brand: `brock icons` copies `brand/dark-ground/<brand>.svg`, which for Brock is the charcoal mark with a white outline) on the splash and the failure splash, `instance` (default `./logos/icon-bot.svg`) for a named instance's window icon. The title bar draws `logos.app` for every launch and marks a named instance with the instance badge alone. The title bar hides in `borderless` and `fullscreen` window modes, read from the `windowMode` setting.
- `product.icons.rim` (`'light'` or `'dark'`) picks Tessera's rimmed icon set, `brand/<rim>-rim/<brand>/` and `brand/<rim>-rim/<brand>.svg`: the same layout as the plain set, with a thin outline in the rim colour that follows the silhouette, never tiled, so a dark mark reads on a dark title bar, taskbar or splash. `defineProduct` sets `'light'` when `icons.brand` is `'brock'` (Brock uses the light rim on dark surfaces) and no rim for other brands. `brock icons` copies `public/logos` and `build/icons` from that tree, so the window icon, the title bar logo and the bot variant carry the rim (the splash mark is the dark ground mark, which carries what Tessera draws for the dark ground, such as Brock's fine light rim); the installer's downloader reads its mark from it, and the Setup splash takes the dark ground mark like the boot splash; the About panel draws the bare mark with `rim`.
- `product.icons.wordmark` is the app's name as an image under `public/` (an `.svg` or `.png`, a path like the logos), either a path or `{ src, dark?, rendering? }`; `defineProduct` resolves it to `{ src, dark }`, `dark` defaulting to `src`, plus `rendering: 'pixelated'` when the app sets it. `rendering` is `'auto'` (the default, smooth scaling) or `'pixelated'` (hard pixel edges, for pixel art), and `defineProduct` refuses any other value. With `'pixelated'`, About, the splash page (Tessera's `ts-wordmark--pixelated` on its image), the window's failure splash (`wordmarkPixelated` on Tessera's `Splash`) and the Setup splash (`image-rendering="optimizeSpeed"`, nearest neighbour in resvg) scale it with `image-rendering: pixelated`; without it nothing changes. The boot splash, the window's failure splash and the Setup splash draw `dark` in place of the name, and About draws `src` as its heading (app-structure.md, Product icons). Unset, every one of them shows the name as text. `brock check` and `brock sync` warn, without failing, when a smooth `src` or `dark` picture is under 48 px high, read from the PNG header or the root `height` of an SVG (`wordmarkHeightWarnings` in brock-build's `installer/`), since the splashes draw it at its own height; an SVG sized only by its `viewBox` and a pixelated wordmark are not checked.

- `RendererModule { id; screens?; settingsTabs?; menu?; Provider?; volume?: VolumeSource; titleBarActions?: TitleBarActionSource[]; searchActions?: SearchAction[]; widgets?: WidgetDef[]; bootTasks?: RendererBootTask[]; beforeQuit?: BeforeQuit; tours?: TourDef[]; ports?: Partial<Record<HostShell, Partial<PortCreators>>> }`. Ports are merged into the host factory with `withPorts`.
- Hosts: `getPlatform()` picks one of three factories by `detectHost()`: `electron` (the preload's `window.api`), `capacitor` (a native Capacitor shell, Android or iOS) and `web` (a browser), and merges the `ports` the modules give for that host (`ports.electron`, `ports.capacitor`, `ports.web`) over it. The web host reads the browser it runs in: a coarse pointer with a narrow viewport (`(pointer: coarse)` and at most 767 px wide, or at most 500 px high for a phone held sideways) reports `formFactor: 'mobile'`, and a coarse pointer reports `input: 'touch'`; elsewhere it stays `desktop` and `pointer`. `PlatformProvider` listens to both media queries and swaps in a platform with the new `info` when they change, so `usePlatform()`, `getPlatform()`, `when` rules, mobile-only settings tabs, the `platform-mobile` class and the search index follow a phone's browser as they do a Capacitor app. The Capacitor host is a mobile touch platform (`formFactor: 'mobile'`, `input: 'touch'`, `os` from `Capacitor.getPlatform()`) over the app's installed Capacitor plugins, reached by name with `nativePlugin`, so brock-react depends on none: `files` keeps the app's files in the app data folder through `Filesystem` (`Directory.Data`, so profiles and settings persist), `storage` reports that folder and sums each data domain the app declares to the renderer (`<BrockApp dataDomains>`, the same list `bootstrapApp` takes on the desktop) for the Storage page, `filePicker` picks through the WebView's file input, filtered by `extensions` (`pickFile({ extensions, anyType: true })` opens it unfiltered, for an extension Android has no type for and would grey out; the app then checks the name it gets; Electron and the browser honour `anyType` the same way. `anyType` also takes a host or form factor, `'mobile'`, `'desktop'`, `'electron'`, `'capacitor'` or `'web'`, or a map of them such as `{ mobile: true }`, to drop the filter only there; a host key wins over the form factor key, and `anyTypeFor(anyType, info)` from brock-core resolves it. The browser host reads the form factor when the picker opens, so `'mobile'` drops the filter in the Capacitor shell and in a phone's browser) and saves to `Documents`, `device` drives `App` (pause, the back button) and `Haptics` and `KeepAwake` when installed, and reports the edge of the back gesture: the managed Android `MainActivity` dispatches `brock:back` with `detail` `left` or `right` (the swipe edge, `left` for the button), `onBackButton` hands it to every listener, and with no listener the app exits as Capacitor's own back does, and `window.close` exits through `App.exitApp`. A missing `Filesystem` plugin makes the file port throw with the package to add. The capability `titleBar` (true on Electron and Capacitor, false in a browser; optional, so a custom platform factory that leaves it out reads as true) draws the app's title bar with its menu and actions; `windowChrome` (Electron only) adds the window buttons: without it the shell passes `controls={false}` to Tessera's `WindowTitleBar`, so on a phone the bar shows with the title, the menu and the actions and no window control at all, close included, and the space of the controls box closes up. `product.window.titleBar.mobile: false` leaves the bar out on a mobile form factor only, for an app that draws its own phone chrome; the desktop keeps it.
- Logging: `BrockApp` writes the app log (the log bus every `RendererModule.logChannels` channel, the IPC bridge and `bus.error` feed) to `Data/debug/session.log` through `debug:appendSessionLog`, as `[<ISO time>] [<level>] [<channel>] <message>` lines, in batches a second after the first line or at 50 lines, and at once on `pagehide` and `beforeunload`; main rotates the file to `session-1.log` at each start. A popped widget window does not write it, since the main window relays its log there. `sessionLog={false}` turns it off. In every window `BrockApp` also catches what nothing else did: an uncaught error (`window` `error`, with its file, line, column and stack) and an unhandled promise rejection go to the app log as errors, so they reach the session log, the Logs widget and the bug report. `catchGlobalErrors(bus, target)` and `writeSessionLog(bus, append, target)` are exported for an app that runs its own log bus.
- `beforeQuit` on `BrockApp` or a `RendererModule` returns a message (or nothing). When one does, Quit and the title bar close button show a confirm with every message before the window closes. `quitGuards.add(fn)` registers one from anywhere and returns the remove call; `requestQuit(quit)` runs the check.
- `titleBarActions` is how a module puts something in the title bar, since brock-react cannot import a module. Each entry is a Tessera `WindowTitleBarAction` (`{ id, label, icon, onSelect, bar?: 'button' | 'status' | 'menu', status?, tone?, shortcut? }`), or a hook that returns one (`TitleBarActionHook`) when it reads state. `BrockApp` puts `STANDARD_TITLE_BAR_ACTIONS` (Search with Ctrl+K in the primary tone with a twinkle, and Report a bug in the danger tone with a ping) first, then the actions of every module in load order, and resolves the hooks in that fixed order every render. `WindowTitleBar` draws each `button` action as an icon button and each `status` action as a pill while its `status` is set, and lists every action in the hamburger too, with `status` as the subtitle, beside a View sub-menu holding the pin and full screen. As the bar narrows the buttons fold away (last declared first), then the pin, then the pills, then full screen, then the title, and the logo shrinks. An action whose `id` is the key of a menu entry replaces that entry in the hamburger, so Report a bug and Check for updates are listed once; the palette still searches the full menu. Brock puts the trailing Quit in a group of its own, so the bar's group sits just above it. The updater contributes `useUpdateAction`: Check for updates, a `status` pill reading "Update available" while a found update waits, which opens the dialog.
- An app puts items of its own in the title bar without a module: `src/title-bar/<id>.action.ts` default-exports `defineTitleBarItem(spec)`, or a hook from `src/hooks` that returns a spec or `null`. `brock sync` (and the renderer Vite plugin, `brock dev` and `brock build`) writes `.brock/title-bar.ts`, `appTitleBar = titleBarFromFiles([{ id, source, order? }])`, the items that export an `order` (`export const order = 2`, or `order` in `meta: TitleBarItemMeta`) first by that order and the rest after by id, which `src/main.tsx` passes as `<BrockApp titleBar={appTitleBar}>` (a `button` spec whose `label`, `icon`, `shortcut`, `tone` and `effect` are literals becomes `lazyTitleBarButton(look, load)`: the bar draws it at boot and its file, with `onSelect`, loads on the first click; a hook, a menu, a status or a computed label is imported as before); an app off the convention passes the same list by hand. A spec is `{ kind: 'button', label, icon, onSelect, shortcut?, tone?, effect? }`, `{ kind: 'menu', label, icon, items: MenuEntry[], tone?, effect? }` or `{ kind: 'menu', label, icon, groups: [{ label?, items }], tone?, effect? }` (a Tessera title bar dropdown, `bar: 'dropdown'` with `groups`: a ghost button that opens its menu under it, with the group labels shown there, and a sub-menu with a separator between the groups once it folds into the main menu) or `{ kind: 'status', label, icon, status: string | null, tone?, effect?, pulse?, onSelect? }` (a status tag drawn while `status` is set), or `{ kind: 'volume', label, value, muted, onChange(value), onMuteToggle(), shortcut? }` (see Volume below). `tone` and `effect` take the values Brock's own Search and Report a bug items use: a Tessera `StatusTone` and an `IconEffect` (`'twinkle'`, `'ping'`, ... or `{ kind, every?, color?, ... }`); a dropdown takes them too (Tessera 0.20 draws its icon through `TitleBarActionIcon`, on the bar and on its sub-menu item once it folds, MIGRATION 179). Restrictions: app items come after Search, Report a bug, the job status and every module action, in that fixed order; an app item whose id one of those holds is dropped with a warning in the app log, and `brock structure` rejects `search`, `report-bug` and `brock-jobs` as file ids; the window controls stay Tessera's. App items fold like the others: buttons and dropdowns first, then the pin, then status tags, and every item stays in the hamburger. `pulse` on a status gives its text a pulsing dot (the job status pulses while a job runs). Every bar button shows Tessera's tooltip with its label and shortcut. `brock structure` reports a file in `src/title-bar` that is neither `<id>.action.ts` nor a constants file (`<id>.action.constants.ts`, the one the constants lint rule names, or `<name>.constants.ts`, both skipped by sync), a folder, an id that is not kebab-case and a file with no default export.

Every app gets the standard features below. `StandardOverlays` mounts the overlays in one place inside `AppShell`: `<StandardOverlays menu={fullMenu} actions={merged.searchActions} />`: the confirm dialog, the palette, the bug report dialog and the toasts. Beside it `AppShell` mounts `JobHost` (the job dialog). A popped widget window mounts `<StandardOverlays />` too, without the palette, and registers the same escape layers, so `confirmAction`, `toast` and the bug report work there. The widgets are not an overlay: `AppShell` renders `WidgetHost` with the screen host as its `main` view, so docked widgets take room from the home or game view instead of covering it.

- Search palette: Ctrl+K (Cmd+K on macOS) or the Search title bar action opens it; Escape or the scrim closes it. Ctrl+K always opens the palette; inside an open hub its results come in two groups, In <hub> first and Everywhere else after, and with an empty query it lists the hub's pages before the screens. It searches the one index described under Search, with the one ranking the hub search uses. A boolean field gets an inline toggle, and Ctrl+Enter flips it from the keyboard. A menu entry with `confirm`, such as Widgets > Reset layout, carries a compact `ConfirmIconButton` (`size="xs"`) in its row's `action` slot: pressing it, the row or Enter asks with the check and the X, kept in the palette store's `asking` (the button reports its own question through `onAsk` and `onCancel`, MIGRATION 192); the check runs the entry and closes the palette, and the X or Escape cancels, runs the entry's `onCancel` and leaves the palette open (the palette catches that Escape in the capture phase, ahead of its input, which would close it; any other Escape closes the palette through its input or the escape stack). Picking a result opens its bucket, page and tab, then scrolls to the row, flashes it and focuses its control; when the row does not appear within 1.5 s, a toast says "Could not find <item> on this page". An app or module adds actions with `RendererModule.searchActions`, `registerSearchActions(actions)` (returns the unregister call) or `useSearchActions(actions)`. `palette.open()`, `palette.close()` and `usePaletteOpen()` drive it from outside.
- Walking mascot: while a screen window (a hub, a page or any `ScreenWindow`) is open, the app's brand mascot walks along the bottom edge of that window. It is Tessera's `MascotStage` with one actor from `MASCOT_AUTONOMY_RULES` (`autonomy: true`), so it idles, wanders and naps on its own, and Tessera's own `motion: 'system'` keeps it still under reduced motion. Brock adds no sprite, state or timing of its own: `WindowMascot` (`packages/react/src/brand/WindowMascot/`) sits in `ScreenLayer`, measures the window's card and draws the stage in a fixed layer over it through `Portal` (`overlay`), `inert` and `aria-hidden`, so it takes no pointer events or focus and stays above the palette's scrim. It is gone with the window; a window that is not shown draws none. The mascot is the one `brandMascot(product.icons.brand)` gives (the same choice `useBrandMascot()` makes), and an app whose brand has no mascot draws nothing. When the palette opens, the mascot's autonomy pauses, it walks with `moveTo` to the side of the palette (left of it facing it, or right of it when the left has no room, kept inside the window), plays `point`, and a Tessera `Callout` above it shows the search hint; it follows the palette while it grows and goes back to its own autonomy when the palette closes. `product.mascot` in `brock.config.ts` is the whole config: `mascot: false` turns the walker off (the palette and the hero keep their mascots), and `mascot: { searchHint: 'Find a game' }` replaces the default hint, `Type to search pages, settings and actions.`. The review's `mascot` step opens a window, checks the mascot stands along its bottom edge (`mascot-window`, `mascot-window-bottom`) and captures `mascot-window`, opens the palette and checks it stands beside it with the hint (`mascot-beside-palette`, `mascot-search-hint`) and captures `mascot-palette`, then checks it goes with the window (`mascot-gone`); an app with `mascot: false` or a brand without a mascot checks `mascot-off` instead.
- Bug report: `bugReport.open()` or the Report a bug title bar action opens a dialog for a title and a description. Brock owns the dialog and the payload, `BugReportPayload` in brock-core: `title`, `description`, `app` (`id`, `name`, `version`), `createdAt`, and `diagnostics` when they are attached: the debug text (app version, runtime, platform, recent log lines, and the host facts from `diagnostics:getSystem`), the same host facts as `system`, and the last 200 log lines as `{ at, channel, level, message }`, every message through `redactSecrets`. Where the payload goes is the first of: the app's renderer transport (`<BrockApp bugReport={{ transport, label? }} />`), the app's main transport (`bootstrapApp(product, { bugReport: { transport(payload, ctx), label? } })`, reached over `bugReport:transport`, `bugReport:send` and `bugReport:retry`), a prefilled GitHub issue on `product.repo`, the clipboard. A transport is `(payload) => Promise<Result<BugReportReceipt>>`, the receipt being `{ message?, url?, id?, links?, retry? }`; the primary button carries its `label` (`Send report` by default) and spins while it runs. On success the toast shows the receipt's message, with Open when it has a `url`; on failure, or when the transport throws, the dialog stays open with the error above the buttons and the text kept, so Send tries again. A main transport that needs files calls `writeDebugZip(target, ctx.paths.data('debug'), payload, extras)` from brock-electron: `report.json`, every `.log`, `.txt` and `.json` file of `Data/debug` under `logs/`, then the app's own `{ name, data }` entries (saves, settings, capture sessions); `collectDebugFiles(dir)` lists those log files alone. The GitHub issue needs no token.
  - Optional fields: a transport opts into a contact email and attachments with `contact: true` and `attachments: true | { maxFiles?, maxBytes? }` beside its `transport` (in `bugReport` of `BrockApp` or of `bootstrapApp`; main reports them through `bugReport:transport`). The dialog then shows a Contact email field and an Attachments drop zone (files the user drops or picks, 5 files and 10 MB in all by default; a file past the cap is refused with a message). The payload carries `contact` when filled and `attachments` as `{ name, type, size, data: Uint8Array }[]`; the GitHub issue and the clipboard never get either, since an issue is public. `writeDebugZip` stores each attachment under `attachments/` and keeps only its name, type and size in `report.json`.
  - Renderer extras: `useBugReportExtras(source)` or `bugReport.setExtras(source)` registers a function that returns a JSON-safe object (or a promise of one). The dialog calls it when it opens, so it sees the app as the user left it, and the payload carries the answer as `extras`, through a renderer or a main transport alike. A source that throws leaves `extras` out and the report still goes.
  - Fallback to GitHub: a main transport can declare `available(ctx)`; while it answers false (signed out, offline) `bugReport:transport` reports no transport, so the dialog targets the GitHub issue on `product.repo` (else the clipboard) from the start. When a transport fails on send and the product has a `repo`, the error carries Open a GitHub issue instead, which opens the prefilled issue with the same title, text and diagnostics.
  - After sending: `afterSend: 'view'` beside a transport's `contact` and `attachments` (in either `bugReport`) keeps the dialog open once the report went out and shows the receipt in it: the message, the report id, Open when it has a `url`, and Close. The default, `'toast'`, closes the dialog and raises the toast with the message. The GitHub issue and the clipboard always toast.
  - Prefilled title: `bugReport.open({ title })` opens the dialog with that title in the field, and `bugReport.setDefaultTitle(title)` keeps one for the next open, from whatever opens it (an error screen setting `Import failed` before the user presses Report a bug). Either is cleared when the dialog closes, so the next report starts empty; `setDefaultTitle(null)` drops one that was never used. `bugReport.hasDefaultTitle()` says whether the title waiting for the next open came from `setDefaultTitle` (the store's `prefillIsDefault`), not from `open({ title })`. The review's bug-report step checks both (`bug-report-prefill`, `bug-report-prefill-cleared`): after its own prefilled open and close, the next plain open must no longer show the review's title, and must start empty only when the app sets no default title (an app may set one each time the dialog opens).
  - App section: `section` in `bugReport` of `BrockApp` is a component the dialog renders below the attachments, inside the app's own providers, for a picker or a note of the app's own. It gets `setExtras(extras | null)` and `disabled` (true while the report is sending); what it sets is merged over the renderer extras into the payload's `extras` and dropped when the dialog closes. `transport` is optional there, so an app whose transport lives in main can still give a section; a `bugReport` without `transport` leaves the target to main, the GitHub issue or the clipboard, and its `label`, `contact`, `attachments`, `afterSend` and `identity` then have no effect.
  - Signed-in identity: `identity` beside a transport (a string in `BrockApp`'s `bugReport`, `identity(ctx)` returning a string, null or a promise of one in `bootstrapApp`'s, asked on each open and reported through `bugReport:transport`) shows "Reporting as <identity>" in place of the Contact email field, and the payload carries no `contact`. A blank answer, or an `identity(ctx)` that throws (logged), shows the contact field as before.
  - Links: a receipt's `links`, `{ label, url }[]`, each get a button beside Close in the receipt view, opened with `openExternal`. The single `url` still works: it shows as Open ahead of the links unless one of them has the same address. A toast carries the first of them as its action.
  - Retry: a receipt with `retry`, `() => Promise<Result<BugReportReceipt>>`, means the report went out but a part of it did not (an upload, say). The receipt view then shows its message as a warning with Retry upload, even with `afterSend: 'toast'`. A successful retry replaces the receipt (its message, links, and a further `retry` or none); a failed one shows the error under it and keeps the button. A main transport returns `retry` the same way: main holds the function (the latest one only), sends the renderer a `retryId` in its place (`BugReportReceiptWire`), and the renderer's Retry upload runs it over `bugReport:retry`; an id main no longer holds answers "This report can no longer be retried."
- About: Version, Runtime, Engine and Platform rows, and Copy debug info with the same debug text (`useDebugText`). The screen is Tessera's `InfoScreen` (no page header, only the window title bar; the screen declares `header: 'none'`) holding Brock's `AboutPanel`, which shows the logo and the app name, with the legal text in its footer. When `product.icons.brand` is a Tessera brand whose name is the product name, `AboutPanel` draws that brand's app icon and wordmark, or its bare mark with the `product.icons.rim` rim when it has one; any other app shows `product.logos.app` and its name. With `product.icons.wordmark`, the heading is that image (`wordmark.src`, the name as its `alt` text) in place of the name or the brand wordmark (`AboutPanel` `wordmark`). The panel then takes the full width it is given, up to `--size-448`, the heading stretches across it, and the image fills that width with its height following its proportions up to `--size-48`, centred, so a wordmark of any width fits the card and is never cut. The image frame takes no width of its own from the picture, so it cannot push the heading or the panel wider than the card. `wordmark.rendering: 'pixelated'` passes `pixelated` to Tessera's `Image` (`AboutPanel` `wordmarkRendering`). Every Tessera copy button writes through `writeClipboard`, which `BrockApp` gives `TesseraProvider` as `overrides.writeText`; the `AboutPanel` copy button is Tessera's `CopyButton` with its label shown, spinning while the debug text is gathered, and the Performance widget copies its snapshot through one too.
- Title bar: `WindowTitleBar` draws the hamburger and the menu from `MenuGroup[]`. Brock keeps its own `MenuEntry` model and converts it at the edge with `toMenuGroups(menu, { openScreen })`: `key` becomes `id`, `screen`, `bucket`, `page`, `tab` and `onClick` become `onSelect`, `'separator'` becomes `{ separator: true }`, and a bucket's or a page's `shortcut` shows beside its entry (display only; `Mod` reads as Ctrl). An empty menu hides the hamburger. `product.window.titleBar.controls` (`fullscreen`, `pin`, `minimize`, `maximize`, each `true` by default) turns title bar buttons off; close always stays. With `maximize: false` the main window is created `maximizable: false`, and with `fullscreen: false` it is `fullscreenable: false` and Alt+Enter and the fullscreen IPC do nothing. It sits beside `product.widgets.mainLabel` in `brock.config.ts`.
- Toasts: `toast(message, { variant?, duration?, action? })` works from anywhere and returns an id for `dismissToast(id)`. Both are thin wrappers over Tessera's one `toast()` queue: the same message and variant raised again joins the toast already queued, with a count such as ×3, and a toast leaves after Tessera's 5 s unless it sets `duration` (0 stays). `ToastHost` is one Tessera `ToastStack` at the bottom right with `max={3}`; the rest wait their turn, and a second stack draws nothing.
- Widgets: `defineWidget({ id, label, render, ... })` describes a tool panel for the Tessera `WidgetManager` v2, which draws a `DockLayout` split tree around the main view: panes docked on an edge or tabbed together, widgets floating over the main view, and widgets in their own OS window. The dock names the main view `product.widgets.mainLabel` (default `Main`); the saved layout key stays `main`. Widgets come from the app's `src/widgets` files (see Widgets by convention), `RendererModule.widgets`, the `widgets` prop of `BrockApp` or `WidgetHost`, or `registerWidgets(defs)`. The layout is `{ v: 2, dock, floating, popped, frame, poppedMemory? }`; a stored layout goes through `migrateLayout` on load, so the flat layouts of earlier builds keep working. A docked pane makes room unless it says `makeRoom: false`: since Tessera 0.42 (MIGRATION 258) `migrateLayout` sets `makeRoom: true` on every docked pane of a saved layout or saved kit view that lacks it, the panes of a layout preset or a kit layout are built making room, and only a pane the user turned into an overlay stays one, its main view widening only on its side. The layout (the dock, the floating rects, the popped windows with their bounds, sync and links, and `poppedMemory`) and each widget's `useWidgetPref` values are kept per profile in `ui-views.json` through the `uiViews` IPC, under `profile:<id>` as `widgetLayout` and `widgetPrefs`; other subtrees of the same entry (the screens' `screens`) are left as they are, since every write merges into the profile's entry. Brock writes `ui-views.json` by key, never as a whole file: the renderer sends only the keys it changed (`uiViews:patch`, `patchUiViews`, a key set to `null` removed), and main merges them into the file on disk one write after another, so a key someone else wrote since the renderer read the file survives. The keys starting with `profile:` are Brock's. An app keeps its own view state in the same file under keys of its own with `uiViews` from brock-react: `uiViews.read(key, fallback)`, `uiViews.write(key, value)` and `uiViews.remove(key)`, written 250 ms later or on `uiViews.flush()`; a `profile:` key throws. `uiViews:save` still writes the whole file for an older caller. On the Capacitor host, which has no main process, the renderer reads and writes `ui-views.json` itself through the platform file store, so the views survive a restart on the phone. A profile is read when it becomes active and its widgets come back as it left them, after a restart and after a profile switch; writes are debounced 250 ms and flushed on `beforeunload` and `pagehide`, and a saved widget entry that is not an object is dropped. `useWidgetState(key, initial)` is `useState` for the widget it is drawn in: `WidgetBody` gives every widget body, docked or popped, and its options panel the widget id (`useWidgetId()`), and the value is stored with that widget's prefs, so it is relayed to its popped window and outlives an unmount under a screen; it takes a value or an updater, and the value must survive JSON. `useWidgetStateReady()` is true once the active profile's saved values have arrived. Widget contexts come from one registry, `useContextsStore`: named contexts, each `{ active, data? }`. The app and modules set them through `contexts.set('session', { active, data })` (`contexts.get`, `contexts.isActive` and `contexts.clear` beside it) or `useSetAppContext('session', active, data?)` in a component, which sets it while mounted and makes it inactive when it unmounts; `useAppContext('session')` reads one (inactive when never set). A widget names the context it needs with `context: 'session'` in its definition or file `meta`, which makes it `context-only` unless it sets `defaultVisibility`; app widgets and module widgets work the same way. `WidgetHost` passes Tessera's `WidgetManager` and its gates (`WidgetGates`, which also decide the popped windows) `contextActive={(definition) => …}`, kept stable with `useCallback` until a context changes, which answers from the registry for the context the definition names (a widget with no `context` follows `default`, which is active unless something sets it); Tessera then leaves every widget whose frame shows `context-only` out while its context is inactive, docked, floating and popped (the popped gate closes the window, which keeps its place and reopens there), and Brock hides none itself (Tessera 0.20, MIGRATION 179). The user's Always shown in the widget options still wins. A widget can also stay on screen and be disabled: `widgetDisabled` on `BrockApp` (or `WidgetHost`) is a hook, called every render, that returns `(id) => ({ message, settingId }) | null`; `WidgetHost` hands it to Tessera's `WidgetManager` as `resolveDisabled`, which covers a docked or floating widget with its `DisabledOverlay`, the message and a button to the setting that turns it on. `settingId` is a route with an optional row after `#` (`game/engine#engine.autoStart`): the button opens the route and scrolls to the row as a search hit does. A popped widget window shows the same state: `WidgetWindow` runs the same hook through the dock's resolver and passes Tessera's `Widget` `disabled` (the message as the reason) and `onOpenSettings`, which sends the target to main (`widget:openSetting`, `openWidgetSetting`); main brings the app window forward and relays it (`widget:settingTarget`, `onWidgetSettingTarget`), and the app window opens the route and the row there. The hook runs in the widget window, so it reads what is relayed there, such as the settings. The registry is relayed to popped windows like the prefs (`contexts` slice), so `useAppContext` reads the same contexts there; the data must survive structured clone, and the registry is not saved. A review launch counts every context as active (`contextActive` is `true`). `BrockApp`'s and `WidgetHost`'s `widgetContext`, a hook returning a boolean, is deprecated: it still works, driving the `default` context, and the `widget-context-registry` migration (0.22.0) lists each use as a to-do. A profile with no saved layout starts from the app's layout preset (`widgetLayout`, see Widgets by convention), and every widget whose definition sets `defaultOpen` that the preset does not place opens on its `defaultSide`; `widgets.reset()` puts the layout back to that default, closing every other widget and window. `useWidgetMenuEntries()` returns checkable items for a Widgets menu, sorted by the definition's `order`, then by label, and ends with Reset layout (`rotate-ccw`), a Tessera `DropdownMenu` item of `kind: 'confirm'`: the first click turns the entry into Click again to reset layout in the danger tone and keeps the menu open, the second click calls `widgets.reset()`, and Escape, leaving the entry or 4 s puts it back (a menu entry with `confirm: true` takes Tessera's words, `confirm: '<question>'` its own, in the title bar menu and in a title bar dropdown, and its `onCancel` runs when the question closes without the second click; the palette's Reset layout entry runs at once); `widgets.open(id)`, `widgets.close(id)`, `widgets.toggle(id)` and `widgets.popOut(id)` work outside React. `widgets.force(ids)` forces widgets, for a command line baseline or an end-to-end run on a fresh profile: each id opens (a kit widget opens its kit), now or as soon as its definition is registered, and again after each profile loads, and a forced widget skips the context gate and the developer tools gate, docked, floating and popped (`WidgetGates.forcedIds` and `WidgetManager`'s `startupForcedWidgetIds`); a forced kit widget also lets its kit past the kit's `devOnly` and `requires` gates. The list replaces the previous one, and `widgets.force([])` ends forcing (the widgets stay open). An app reads its own flag, such as a `--widgets=` argument, and passes the ids. The built-in `logs` widget is a filterable, searchable view of the log bus. The built-in `performance` widget (closed by default, listed in the Widgets menu for everyone, since a bug report needs it most when developer tools are off) is drawn with Tessera's chart parts: a row of `StatTile`s (frame rate, CPU, memory, event loop lag), each with the latest value, its change since the previous sample with a trend arrow, and a `Sparkline` of the last 60 samples; `Gauge`s for the app's CPU, its share of system memory and the JS heap against its limit, each with warning and danger zones; a `StackedBar` of memory by process (main, renderer, GPU, utility, widget windows, other) with a legend; an Activity list of long tasks since the widget opened and the errors and warnings since start; and a collapsed Details section with every reading as `StatRow`s. A container query lays it out: two tiles a row and the panels stacked when docked (280 to 360 px), four tiles a row and the gauges beside memory and activity from 560 px; the gauges take the largest size that fits. The readings come from the renderer (frame rate and frame time from `requestAnimationFrame`, long tasks from a `longtask` `PerformanceObserver`, event loop lag from a 100 ms timer's drift, the JS heap where `performance.memory` exists, the DOM node count), from `diagnostics:getProcesses` (every process with its CPU, working set and window, the main process memory, uptime, window count, each widget window with its sync and how many windows it is snapped with, IPC calls per second from a counter in brock-electron's `handle` and `on`, the Electron, Chrome and Node versions, GPU compositing, the system memory) and from the app (version, screen and route, profile, open widgets, modules, warnings and errors counted by the app log bus). Its options panel sets the refresh (0.5, 1, 2 or 5 s, saved with `useWidgetPref`) and the sections shown (Renderer, Processes, App); a hidden section is neither drawn nor sampled. Sampling runs only while the widget is on screen (an `IntersectionObserver` on its root, plus the page visibility), so a closed, tabbed-away or minimized widget costs nothing; each sample is one state update and the chart parts change attributes on the same elements. The widget body is Tessera's slim `ScrollArea`, so the widget adds no scroll box of its own. Copy snapshot puts every reading on the clipboard as text for a bug report.
- Widget focus: a mouse click on a widget's button, tab or slider would give it the keyboard focus, and then the arrows, Enter and Space drive that control instead of the app. `product.widgets.keepFocusWithApp` (default `true`; the `keepFocusWithApp` prop of `WidgetHost`) keeps the keyboard with the app: `WidgetHost` calls `useWidgetsNeverFocus` once, which listens on the main window's document in the capture phase. It covers the docked and floating widgets (`[data-widget-id]`, `[data-pane-id]`, `[data-floating-id]`), the lines between dock panes (`.dock-divider`, Tab stops since Tessera 0.30, so a drag on one leaves the focus with the app while Tab still reaches it) and the widget options panel (the panel Tessera's `WidgetOptions` opens and each of its sub-panels, all marked `[data-widget-options]`; a sub-panel is also matched through its row's `aria-controls`); the main view and every other menu are untouched, so an app menu keeps its keyboard navigation. Only focus a pointer caused is dropped: the guard remembers whether the last input was a pointer press (and whether it was inside the widgets) or a key. A press on a control inside the widgets (`button`, a link, a tab, a switch, a checkbox, a menu row) has its `mousedown` default prevented, so the focus stays where it was and the click still fires; a press on plain widget text keeps its default, so the text stays selectable. Focus that lands inside the widgets after a press inside them, such as a panel focusing its first row or a menu handing the focus back to its trigger, is blurred on `focusin` and once more after the click handlers ran (a `click` listener in the bubble phase), which also covers a window that has no focus and so gets no `focusin`. Text fields (`input` with no type, `text`, `search`, `number`, `email`, `url`, `tel`, `password`, `textarea`, `contenteditable`) keep the focus. A slider or a native `select` keeps it for the press and loses it on the pointer release or on `change`. Tab, Shift+Tab, the tour and the search palette moving the focus into a widget are not a press inside the widgets, so that focus stays and the focus ring shows as usual, and a slider changed with the arrow keys keeps it. A popped widget window is its own window where the widget is the whole app, so the guard does not run there. `widgets: { keepFocusWithApp: false }` in `brock.config.ts` turns it off, for an app whose widgets are meant to be driven from the keyboard after a click.
- Widget windows: a definition with `popOut: true` may leave the app for a frameless window of its own (the pop out button, the options panel, or a drag past the window edge, which opens the window under the cursor). brock-electron owns those windows end to end (`packages/electron/src/main/widgets`); Tessera only draws `DockLayout` and `Widget`. A popped window is synced with the main window by default: on Windows the app window owns it, so it never falls behind the app, and it hides, shows, minimizes, restores and raises with the app without taking the focus, and stays visible when another app takes the focus. A synced window has no taskbar entry unless its definition sets `taskbar: true`. Turning the per-widget `sync` option off ("Sync with main window" in the options panel) makes the window independent: its own taskbar entry, its own minimize, and the app no longer raises it. `sync` is saved with the popped entry, and a synced window also mirrors the app's own always-on-top. The pin is a separate choice of two: a normal window or always on top. The widget window passes `pin` and `onPinChange` to Tessera's `Widget`, which draws its pin menu in the title bar (the current choice as its icon, lit while on top, and a menu of both choices with a line on each), and to `WidgetOptions`, which draws the Pin row with the same two choices. The former `with-app` pin was the same thing as sync, so a saved `with-app` pin opens as `off` with `sync` on, and the corrected entry goes back to the layout. On `will-move` a dragged widget window snaps within 14 px to the app and to the other widget windows, from the cursor and the grab offset so a scaled display never grows the window; a plain drag is left to the OS, and on the tick a window crosses into a display of another scale the OS moves it alone. The app snaps the same way to the widget windows. A snap kept on release links the two windows. A snap cluster is every window that touches the dragged one, directly or through other windows, the app included: two windows touch when they have flush edges, within 1 DIP, that overlap, or share a corner. It is computed from the window bounds when a move or a resize starts, so a window touching two others belongs with both, joined with the saved links, which keep a cluster together while the app is maximized or minimized and are restored with the layout; nobody picks it. Dragging any window of a cluster moves the whole cluster rigidly: only the dragged window snaps, to windows outside the cluster, and a window or cluster it is dropped against joins it. Holding Ctrl while moving drags that window alone: it leaves its cluster, its links break (a window that was linked to it relinks to another window it is still flush with, if any) and it can snap elsewhere. A window that touches no other and has no link moves alone. A change of the app's size made by code, not by a drag, tows the windows linked to the edge that moved, and along the edge they keep their place while they still touch it. Every move, towed or not, reports its bounds, the reports are flushed when the app closes or quits, and the link is saved with the layout and restored when the window reopens. When a display is added, removed or changes, a window whose title strip is out of every work area comes back into the nearest one. Snapping also lines up corners: a window landing on an edge lines its other side up with the corners and edges of the windows around, within the same 14 px, and two windows meeting corner to corner snap without a link. On `will-resize` only the dragged edge moves: it snaps to the matching edges of the neighbours (left and right edges to left and right edges, top and bottom to top and bottom), so windows line up into a grid, and the edges on the dragged line at drag start are locked to it and follow, never below a window's minimum size (a window at its minimum stops the whole line): each facing edge across the seam that overlaps a window already reached along the line, and each edge on the same side, lined up within 1 DIP, that meets a window already reached end to end or overlaps it. Two widgets stacked with their left edges lined up therefore resize those edges together, two widgets stacked against the app's left edge both follow the app's edge, either widget's right edge moves the app's edge and the other widget's, and a widget's bottom lined up with the app's bottom moves the app's bottom. An edge that does not line up is left alone, and once Ctrl has moved an edge off the line it no longer follows. A resize never moves a cluster, and there is no proportional scaling outside a cluster maximize or full screen. The app's aspect lock (`window:setAspectRatioLock`) applies to the app window alone: it is enforced on the main window's `will-resize`, a widget window never inherits it, and while it is set the app keeps its proportions and is never bent by a widget's shared or lined-up edge. Holding Ctrl while resizing turns snapping off and resizes only the dragged window; main reads Ctrl from the `before-input-event` and `input-event` of every Brock window, so a key or mouse event in any of them updates it. A Ctrl release main never receives cannot leave Ctrl held: on Windows the move and resize loop takes the keyboard, so a release during a drag never reaches the window, and a release while another app has the focus, or with the cursor only over title strips and borders (which are not client area), sends no event either. So main forgets Ctrl when a move or a resize ends (`moved` and `resized`; on macOS, where `moved` comes on every step, only when a resize ends) and when no Brock window has the focus 50 ms after one loses it. Ctrl still held for the next drag is read again from the key repeat or a mouse event in a Brock window. A window moved alone with Ctrl rejoins on its next plain drag, and the other windows keep moving together and snapping. Electron gives no way to read the key state itself, and Brock adds no native dependency for it. The window being moved or resized, a widget window or the app, draws a guide over its own content with the mode, whether snapping is on, and the rules: touching windows move together, Ctrl moves one window alone, edges lined up with or touching the dragged edge move with it, an app with a locked aspect ratio keeps its shape, and Ctrl resizes one window alone without snapping. `widget:guide` goes to that window only, with `pointer`, the cursor (`screen.getCursorScreenPoint()`) in that window's client pixels, read again on every `will-move` and `will-resize`, so `WindowGuideOverlay` draws its card beside the cursor; the window that held the guide before gets a closed state, and the guide hides when the drag ends. A cluster acts as one window. Maximize scales every member's bounds proportionally from the cluster's bounding box into the work area of the display the cluster is mostly on (where a minimum size stops the scale, the shared edges are repacked so every member stays inside the area, in order and still flush), and restore puts back each member's exact bounds; full screen does the same into the display's full bounds, opens a frameless, non-focusable black backdrop window behind the members, holds them above other windows while one of them has the focus, and sends each renderer a `square` flag, which `BrockApp` passes as Tessera's `square` to the open screen's `ScreenLayer` and the widget window to its `Widget`, so they drop their radius and border; minimize and restore apply to every member. The app's own maximize, full screen and minimize controls, and Electron's maximize and minimize events, go through the cluster when the app is in one. Closing a widget closes that widget alone, and closing the app closes it as before (the widget windows close and stay in the layout). There are no manual window groups: a `group` left in a saved popped entry is dropped when the layout loads, and the old `config/window-group.json` is deleted at start. The popped window passes `dragRegion` to Tessera's `Widget`, so its title strip takes `data-app-region="drag"` and its buttons `no-drag`: Tessera's tokens make the strip the window drag region, keep every control in it clickable and lift it while a popup is open, so a click on the strip closes an open menu; Brock has no `-webkit-app-region` rule of its own. Its options are `Widget.options`, a `WidgetOptions` that opens in Tessera's `ControlMenu` from the gear, with the drag shortcuts as a `ShortcutList` sub-panel; the review opens it by remounting it with `defaultOpen`. Tessera draws the controls: the popped options panel passes `sync` and `onSyncChange` to `WidgetOptions` (the "Sync with main window" switch), and the guide is Tessera's `WindowGuideOverlay` with Brock's own hints (`defaultHints={false}`), drawn by `WindowGuide` in the app shell and in each widget window. A button of Brock's own in a widget title bar goes through `Widget`'s `titleBarActions` or `WidgetManager`'s `widgetActions(id)`, never a portal into `.widget__titlebar-actions`, and is `size="xs"`, 20 px (`--control-h-xs`), like Tessera's own pop out, pin, options and close buttons there (Tessera 0.24, MIGRATION 198); Brock draws none today, and the window title bar keeps its `sm` actions, 28 px. `--widget-btn-d` and `--menu-trigger-width` are gone; Brock's CSS used neither. The context-only and frame `show` gates apply to popped widgets too: a hidden one closes its window, keeps its place in the layout and reopens where it was. Turning developer tools off closes a popped `devOnly` widget instead (see Developer tools). Dragging a window back in: while the cursor is on the dragged window and over the app content, and no other widget window lies above the app there, the window turns translucent and the app draws the dock drop hints; a release there docks it (the release is kept until the dock answers, so no render can lose it). Each window carries a sequence number so a late close never docks a widget popped again since, and closing the window itself (Alt+F4) closes the widget. Pop in docks the widget back into the pane it left, at the same place among that pane's tabs, while that pane still exists (Brock remembers it for the session when the widget pops out); otherwise it docks at `defaultSide`. The window loads the same renderer with `?widget=<id>`, where `BrockApp` draws only that widget in `Widget mode="out"`; `useWindowKind()` returns `{ kind: 'main' }` or `{ kind: 'widget', id }`, and `widgetWindowId()` the id or null, for code that must know where it runs; the main window relays the widget frames, the widget prefs, the active profile with the settings, and the log as increments to it (`widget:publish`, `widget:relay`), and app state the app shares: `shareWithWidgets(store, { kind, pick, delay? })`, called in the main window (a renderer boot task is the place, since a widget window runs none, and it does nothing there), keeps `pick(state)` as the slice `kind`, publishes it 200 ms after a change (`delay`, 0 for at once) while a widget is popped, sends it when a window asks for its snapshot and again on a profile switch, skips a change that leaves the picked fields the same (a shallow compare), and returns the unsubscribe. `useWidgetSlice(kind, fallback?)` reads the slice in either window (the main window keeps its own copy), so a widget reads it the same way docked or popped; the slice must be structured-clone safe. The frames and prefs relay is two `shareWithWidgets` calls, and a pref or a setting changed in the widget window goes back to the main window (`widget:setPrefs`, `widget:patchSettings`), which saves it with the profile as if the widget were docked. At launch, widget windows the main renderer restores from the saved layout before the app window is revealed are created hidden and held: each one adds a boot hold that resolves when it is ready to show (or after 1.5 s), and when the app window is presented (`bootEvents` `presenting`, right after the window shows at opacity 0) every held window shows in the same tick with `showInactive` at opacity 0 and fades to 1 over the same 220 ms (`fadeWindow`, `REVEAL_MS`). A held window that is parked or hidden with the app stays hidden, synced windows stay owned by the app window, and none takes the focus. A widget window that becomes ready during that fade fades in too; one opened after the launch shows at once. On an automation launch (`--no-focus`) a widget window opens off screen, cannot take the focus and stays behind; `--muted` mutes it. The IPC contract lives in brock-core, `ipc/widget-contract.type.ts`.
- Keyboard shortcuts: the Advanced menu entry or Ctrl+/ opens a dialog listing the framework shortcuts (Ctrl+K, Escape, Alt+Enter, Ctrl+/) and every screen and page shortcut, drawn as one Tessera `ShortcutList` with a group per heading. `shortcutsHelp.open()` opens it from code.
- The menu files the `useWidgetMenuEntries()` items under Widgets and adds Keyboard shortcuts and Report a bug to Advanced, and Take the tour to Help when an app or module entry uses the `help` section, else to Advanced (see Tours by convention). The palette, the bug report dialog and the shortcuts dialog are escape layers, so Escape closes them before anything else.
- `STANDARD_TITLE_BAR_ACTIONS` (Search, Report a bug) come before the module actions, then the app's `src/title-bar` items.
- Volume: `useVolumeStore` (brock-react) holds the app's sound level, `{ value, muted, setValue(value), setMuted(muted), toggleMute() }`, with `value` from 0 to 1. Raising the level unmutes, and unmuting from 0 brings back the last level heard. Brock plays nothing: an app with sound reads the store (`useVolumeStore((s) => (s.muted ? 0 : s.value))`, or `useVolumeStore.subscribe` outside React) and applies it to its own audio. By default the store is saved per profile in `ui-views.json` under `profile:<id>` as `volume` (`{ value, muted }`, written 250 ms after a change like the widget layout, read when a profile becomes active, full volume and unmuted for a new profile). An app that keeps the level in its own state passes a binding instead, `volume` on `BrockApp` or on a `RendererModule` (the `BrockApp` prop wins, then the first module that gives one): `{ get(): { value, muted }, set(next), subscribe(listener) }`, or `volumeFromSettings({ value: 'audio.master', muted: 'audio.muted', max?: 100 })`, which reads and patches the profile's settings at those keys (a dotted key reaches into a nested object, `max` is the stored value of full volume, 1 by default). With a binding the store mirrors it both ways and saves nothing: a change made in settings shows in the title bar, and a click in the title bar patches the settings. Define the binding outside render, since a new one rebinds. `volumeTitleBarItem({ label?, shortcut? })` returns the hook for a `volume` item bound to the store, so `src/title-bar/volume.action.ts` is `export default volumeTitleBarItem();`. A `volume` item becomes Tessera's volume bar item (`bar: 'volume'`, Tessera 0.41) through `volumeBarAction`: `{ id, label, value, muted, onChange, onMutedChange, min: 0, max: 1, step: 0.01, shortcut }`, where `onMutedChange(next)` calls `onMuteToggle` only when `next` differs from `muted`. On the bar it is a 28 px `VolumeControl` whose speaker follows the level (Tessera's `VolumeIcon`), with a slider in a popover that opens on hover or focus; a click on the speaker mutes and unmutes, and its tooltip reads Mute or Unmute. Once it folds, the main menu holds a Mute or Unmute row (`<id>-mute`) and a slider row named by `label` (`<id>-level`). Tessera draws the Mute and Unmute labels from its own `common.mute` and `common.unmute`; the item takes no labels of its own (migration `volume-item-labels`, 0.59.0).
- Developer tools: `useDeveloperTools()` says whether they are on. By default a development run turns them on, and the `developerToolsEnabled` setting does in any build. An app with a switch of its own passes `developerTools` on `BrockApp`, the same shape as the volume binding: `{ get(): boolean, set(on), subscribe(listener) }`, or `developerToolsFromSettings('<key>')`, which reads and patches that key of the profile's settings (`'tools.developer'` reaches into a nested object). The binding is then the one switch, in a development run too, and `developerToolsEnabled` no longer counts. Define it outside render, since a new one rebinds. `bindDeveloperTools(binding)` binds outside React and returns the unbind, which gives back the binding it replaced (the review binds one of its own this way for its checks); `developerTools.bound()` and `developerTools.set(on)` read and flip a bound switch. Off hides every `devOnly` entry, Widgets > Developer and the dev-only screens. When developer tools turn off in the same profile, with its settings loaded, `WidgetHost` also closes what is open of them (`closeDeveloperWidgets`): every `devOnly` widget, docked, floating or popped (its window closes), the open `devOnly` kit with its popped windows, and the `devOnly` members open in a kit that is not dev-only. A forced widget stays. Turning them on again brings the entries back and leaves the closed widgets closed.
- Full screen: the title bar follows Tessera's `WindowTitleBar`. In full screen, and in a borderless or full screen `windowMode` (`concealed`), it is out of the layout and hidden above the top edge; it slides in whole while the pointer is within the top 40 px, and a tap of Alt reveals it with focus on its first control (Escape there hands focus back). `brock-app__content` is its own stacking context (`isolation: isolate`), so no docked or floating widget and no z-index in the app content covers the revealed bar. A headless run lays full screen out off screen at the display size (`headlessFullscreen` in brock-electron), so the review never takes over the real screen. The review's `fullscreen` step checks that the bar is fully hidden in full screen (`fullscreen-bar-hidden`, captured as `fullscreen`), fully drawn and uncovered at the top edge with a docked widget open (`fullscreen-bar-reveal`, `fullscreen-revealed`), hidden again once the pointer leaves (`fullscreen-bar-leaves`), revealed with focus by Alt (`fullscreen-bar-keyboard`, `fullscreen-keyboard`) and back in the layout after full screen (`fullscreen-bar-restored`).
- Jobs: `JobHost` fills a store from `job:list` and `job:update`. `jobs.open(id)` shows the job dialog for a job (it shows once the first snapshot arrives), `jobs.hide()`, `jobs.cancel(id)` and `jobs.dismiss(id)` work from anywhere. `jobs.start(id, steps, options?)` starts a job in the renderer itself and returns the same `JobHandle` as `ctx.job`, on every host (Electron, Capacitor, a browser): its snapshots go straight into the store, so the job dialog and the title bar item show it like a main process job, `jobs.cancel` fires its `signal` and `jobs.dismiss` forgets it; an id that names neither goes to main. A renderer job and a main job should not share an id, and `useJob(id)` returns `{ job, step, shown, open, hide, cancel, dismiss }`: `job` is the snapshot (`state`, `progress`, `line`, `error` and the rest) or `null` when the store holds no such job, and `step` the current step (`{ id, label, weight, state }`) or `null`, for a main job or a renderer job alike, quiet or not, so a page can show a job's progress inline. `jobs.start` takes the same options as `ctx.job`, and a renderer job's `forwardLog` lines go to the app log. `JobDialog` (exported for an app that draws it elsewhere) maps the job snapshot onto Tessera's `JobDialog` and `TaskProgress`, and sets `data-job-id="<job id>"` on the dialog element for tests (through Tessera's dialog `data` prop): the bar with the percent, the line beside the state word, a `Stepper` of the steps (a failed step in the error look; a done job ticks every step through Stepper `complete`, with no extra Done step), the error in a danger `Callout` and the log folded under Show log, with Cancel (when cancellable) and Hide while it runs and Close after. Hide sends it to the title bar: a built-in status item (`brock-jobs`, after Search and Report a bug) shows the newest visible job that is not on screen, "<title>: <current step label> 42%" in the info tone while it runs ("<title> 42%" when no step is current), then done, failed or cancelled in the success, danger or warning tone, and opens the dialog again when picked; closing a finished job dismisses it. A quiet job (`visible: false`) never shows there or in the dialog, even when `jobs.open` names it. A job that succeeded clears its tag by itself 30 s after it finished (counted from `endedAt`, so a job already done when the app learns of it goes sooner), unless its dialog is open then, in which case it goes once the dialog is hidden; a failed or cancelled job keeps its tag until it is opened and closed.
- Settings row actions: a settings item takes `actions: SettingAction[]` (`{ id?, label, icon?, tone?, disabled?, confirm?, onSelect }`), drawn through SettingsRow `actions` in the row's end area: after the control when the item has one, in its place when it has none. `tone` is a Tessera `ButtonVariant`, named as in Tessera's `ActionData`: `tone: 'danger'` gives the row its danger tone and the dialog of a string `confirm` its danger look, and `SettingActions` draws its buttons in the tone (`secondary` when unset). `variant` is the deprecated name of `tone` and still works until 0.27, with `tone` winning when both are set; the 0.26.0 migration `setting-action-tone` rewrites `variant` to `tone` in the actions of an `actions` list and in objects typed `SettingAction`. `confirm` is a short question (`'Forget it?'`) that the row asks in place, with confirm and cancel and focus on cancel, or `confirmAction` options for a dialog. `onSelect(settings)` gets the current settings, `disabled` is a boolean or `(settings) => boolean`, and a throw becomes a danger toast naming the action. An item drawn by `renderControl` or a linked toggle keeps `SettingActions` under its control in the same row; `SettingActions` also draws the buttons on a custom page, with their loading state while `onSelect` runs. A row action runs through the page's action runner (`useActionRunner`, one per `SettingsLayout` and Storage page), which keeps which action is busy, keyed by the row and the action; the row passes it as the SettingsRow action `loading`, so Tessera draws the busy button (a spinner, `aria-busy` and no clicks) until `onSelect` settles. Nothing else is turned off while it runs.
- Storage page: `StoragePage` (props: `domains?`, the ids to show, all by default) is the built-in page over the data domains. An app adds it to a bucket with a page file, `src/screens/<bucket>/storage.page.tsx` default-exporting `() => <StoragePage />` with its `meta`. It draws Tessera `SettingsSection`s: Overview (the data folder path and the total, Open folder), Folders (each domain's size and item count as it arrives, one `storage:getDomainUsage` per domain, with Open folder, one Older than N days action per `cleanOlderThanDays` entry and Clear unless `clearable: false`, both confirmed with Cancel focused), and Export and import (the portable domains to export as a toggle group, Export to zip, Export to folder, Import zip, Import folder; an import names the domains and its file count and asks Merge (the default) or Replace with `confirmChoice`, a confirm dialog with a radio group, before it starts, and the toast counts the newer files Merge kept). Every result is a toast and the export and import open the job dialog. When the data folder cannot be read, a LoadError box says so above the sections, with the raw error behind Details and Retry, which reads the folder again. Each domain is a search entry while the page is open. On a phone (the Capacitor host) the page is a summary: the data folder and each declared domain's size and item count from `platform.storage.getSummary()`, with no folder, clean, clear, export or import action. In the browser the page says storage needs the desktop app.

Small helpers every app gets from brock-react, one per file:

- `useScreenState`, `useUnsavedChanges`, `useCanGoBack`, `usePageSearch` and `PageActions`, described above and under Screens by convention.

- `confirmAction({ title, message, confirmLabel?, cancelLabel?, variant? })` shows the shell's confirm dialog, Tessera's `Dialog`, and resolves `true` on confirm, `false` on cancel or Escape. A second call cancels the first. A `danger` dialog starts on Cancel and any other on its confirm button; Tessera's dialog keeps Tab inside and gives focus back on close.
- `confirmDelete({ what, consequence, confirmLabel? })` is `confirmAction` with the title "Delete <what>?", the consequence as the message, a red Delete button, starting on Cancel. It replaces the callback-style `dialogs.confirmDelete`, which stays deprecated and now also focuses Cancel.
- `useNow(intervalMs, active = true)` returns `Date.now()` and ticks while `active`.
- `useCopyText(resetMs = 2000)` returns `{ copied, error, copy(text) }`; `copied` goes back to false after `resetMs`.
- `useKeyedGuard()` runs async work under a key: `guard(key, work)` marks the key busy, clears its old error and records a new one when the work throws. `isBusy(key?)`, `errorOf(key)` and `clearError(key?)` read and reset it, and `lastError` is the most recent error still set, for a view with one alert. The state lives in the pure `keyedGuardReducer`.
- `hostApi<M>()` returns `window.api` or null. `M` names the app's own maps (`{ invoke?, send?, events? }`, `typeof APP_INVOKE_MAP` and so on) and adds their methods to the base ones; without it the type is the base `IpcApi`. `requireHostApi<M>()` throws instead of returning null. Brock declares no global `Window.api` and never reads it through the global `Window` type, so an app that declares its own `window.api` (`declare global { interface Window { api: AppApi } }`) does not break the brock-react source its typecheck reads; the members an app adds to `window.api` beside its maps are typed by augmenting `IpcNamespaces` in `@drizztdourden08/brock-core/augment`.
- `SearchAnchor` (`anchor`, `className?`, `children`) marks where a search hit on a custom page lands, so a page never writes `data-search-anchor` by hand.
- `redactSecrets(line)` (brock-core) masks bearer and basic credentials, `key=value` pairs whose key names a token, secret, password or key, credentials inside a URL, and known token shapes (GitHub, GitLab, npm, Slack, `sk-` keys, Google, AWS, JWT). The debug text and the bug report run every log line through it.

Tessera is imported as `@drizztdourden08/tessera/*`; `tokens.css` first, then `.brock/palette.css`, then the app's `theme.css`. `brock sync` writes `.brock/palette.css` with the import of the one Tessera palette of `product.icons.brand` (into the `ds.palette` layer; empty when Tessera has no palette for the brand), and `BrockApp` sets `data-palette` on the document root to `product.icons.brand`, so the app shows its brand's colours and an unlayered `theme.css` seed still wins. The installer takes its neutrals from `tokens.json` `palettes.<brand>.dark` while `theme.css` sets no seeds, else from `theme.dark`.

## Screens by convention

A screen is a file. Its folder and its suffix decide what it is, and one config file lists the buckets.

```
src/screens/
  screens.config.ts           defineScreens({ buckets, home, settings? })
  game/                       a bucket: one hub, one pill in the bucket switch
    home.hero.tsx             the hub home, drawn in the hero frame
    game.backdrop.tsx         the backdrop behind every page header of the bucket
    saves.page.tsx            a page in the bucket's own group
    saves/                    the sub-pages of saves
      edit.sub.tsx            a sub-page with a route (meta.path ':id/edit')
    video/                    a nav group, labelled from config groups
      display.settings.ts     a settings page from sections
    tracker/                  a page with tabs beside its title
      items.tab.tsx
      map.tab.tsx
    tracker.page.ts           the tracker page's meta (icon, order)
    controls.custom.tsx       a custom page: standard frame, free content
  credits.card.tsx            a card screen, outside the buckets
  session.base.tsx            the base screen, drawn under every hub (one per app)
  playfield.layer.tsx         a full-bleed screen that draws its own layer
```

| Suffix | What Brock draws | The file default-exports |
|---|---|---|
| `.hero.tsx` | the bucket hub home | a component taking `HeroProps` |
| `<bucket>.backdrop.tsx` | the backdrop behind every page header of the bucket | a component with no props |
| `.page.tsx` | a hub page in the section nav | a component taking `PageProps` |
| `<page>/<tab>.tab.tsx` | one tab of that page, beside the page title | a component taking `PageProps` |
| `<page>.page.ts` | nothing: the meta of the tab page in the `<page>/` folder beside it | only `meta: ScreenMeta` |
| `.settings.ts` | a settings page with search and reset | `Section[]`, or `(settings) => Section[]` |
| `.custom.tsx` | a hub page whose content is built by hand | a component taking `PageProps`, and `searchEntries` |
| `.card.tsx` | a card screen with header and close | a component taking `CardProps`, or `defineWindow({ ... })` for a window with a side nav |
| `.layer.tsx` | nothing: the screen draws its own layer | a component taking `CardProps` |
| `.base.tsx` | the base screen, under every hub, with no frame | a component taking `BaseProps` |
| `<page>/<sub>.sub.tsx` | a sub-page of that page, with Back in its header | a component taking `SubPageProps` |

A dev-only screen has `.dev` before its extension: `inspector.page.dev.tsx`, `editor.card.dev.tsx`, `<page>/<tab>.tab.dev.tsx`, `<page>/<sub>.sub.dev.tsx`, `.settings.dev.ts`, `.custom.dev.tsx`, `.layer.dev.tsx` (a hero, a bucket backdrop, the base screen and a page meta file cannot be). It is the screen of its kind in a development build, and absent from a production build: sync lists it in `.brock/screens.dev.ts` (`devScreens` and `devSearchSeeds`, spread into `.brock/screens.ts` and `.brock/search.ts`), which a production build loads as empty lists, like the dev-only handler groups (see Main process), so neither its code nor its search entries ship. `brock structure` reports a bucket whose every screen is dev-only and a shipped tab or sub-page whose page is dev-only, which a production build would leave broken; its constants file is `<id>.<kind>.dev.constants.ts` or `<name>.constants.ts`. `meta.devOnly` stays the runtime gate: the screen ships and shows while developer tools are on.

A file may also export `meta: ScreenMeta` (`title`, `icon`, `order`, `menuOrder`, `shortcut`, `devOnly`, `requiresProfile`, `keywords`, `menu`, `header`, `path`, `fill`, `keepMounted`, `hosts`, `when`, `backdrop`, `hero`, `bare`). `hero.size` on a `.hero.tsx` is `'compact'`, `'default'` or `'tall'`: the hero frame passes it to Tessera's `Hero` as `size` ([app-structure.md](app-structure.md), A shorter or taller hero). `fill: true` on a page, a sub page or a tab page's `<page>.page.ts` makes the page take the window height: `HubPageFrame` passes `scroll={false}` to Tessera's `ScreenPage` or `SettingsPage`, so the body is a fixed flex column and a `ListDetail` or `ListDetailLayout` in it scrolls its list and its editor on their own ([app-structure.md](app-structure.md)). `fill: true` on a card or layer gives its window the one header and a body with no padding or scroll wrapper, for a window built with `defineWindow` ([app-structure.md](app-structure.md), A window with a side nav). `bare: true` on a card gives it the hub window: `ScreenHost` treats it like a hub (`isHubWindow`), so `ScreenLayer` gets `free: HUB_WINDOW_KEY` (no title row, movable, the one hub rect and lock, no Back button), the card has `header: 'own'` and no `floating` hub switch. `HUB_WINDOW_KEY` is exported from `brock-react`. Without a title the label comes from the file name. Pages sort by `order`, then by label. A tab page has no file of its own, so its meta sits in `<page>.page.ts` beside the folder: its `title`, `icon`, `order`, `shortcut`, `devOnly` and `keywords` name and place the page in the nav and the search index, and each tab file's own `meta` names that tab. Without the file the page is the folder name in title case with a list icon. The tabs draw in the page header beside the title, Tessera's `SettingsPage` `tabs`, the same strip a settings page uses for its section anchors.

```ts
interface BucketDef { id; title; icon: IconName; menu: 'entry' | 'submenu' | 'hidden'; groups?: { id; label }[]; shortcut?; hosts?: HostShell[]; when?(ctx: ShowContext): boolean; nav?: 'auto' | 'always' | false; backdrop?: PageBackdrop; requiresProfile?: boolean }
type PageBackdrop = Backdrop | { kind: 'none' }   // Tessera's { kind: 'node' | 'image' | 'color', ... }
interface HeroMeta { size?: HeroSize }   // Tessera's 'compact' | 'default' | 'tall'
interface ScreensConfig { buckets: BucketDef[]; home: string; settings?: { bucket: string; page?: string } }
type ScreenMenu = false | 'entry' | string | ProductMenuEntry   // { inMenu?, hidden?, label?, group?, order?, before?, after?, parent? }
interface PageHeaderMeta { primary?: { label; icon?; open: string }; search?: { placeholder? } }
type BaseProps = CardProps
interface CardProps { params; profile; open(target, params?); close() }
interface PageProps extends CardProps { bucket: BucketDef; page: string; tab: string | null; openSub(sub, params?) }
interface SubPageProps extends PageProps { sub: string; subParams: Record<string, string>; back() }
interface HeroProps extends PageProps { slots: { Title; Eyebrow; Backdrop; Shade; Art; Actions; Tools; Facts; Aside; Panel } }
```

- `brock sync` scans `src/screens` and writes `.brock/screens.ts` and `.brock/search.ts`. The first imports each file's `meta` and hands its component over as `lazyComponent(() => import(<file>))`, so no screen code loads at boot (see Lazy registries and the Suspense host), and calls `buildScreenTree(config, entries, searchIndex)`. A settings page stays eager: its sections feed the live settings search. The renderer Vite plugin writes both again when the build starts and whenever a file under `src/screens` is added, renamed, changed or deleted, so `brock dev` reloads with the new registry. `brock check` fails when either file drifts.
- `buildScreenTree` makes one hub per bucket, in config order. The hero is the hub home; a bucket without one opens on its first page. Pages in the bucket folder form the bucket's own group, named after the bucket; group folders follow in the order of `groups`, then any other group by name. Custom pages sit in the nav like any page. Card and layer files become screens; settings files become settings tabs. A generated hub has its search on, and its side nav stays open or folded per hub (`storageKey` `brock.hub.<id>.nav-open`).
- Header backdrop: `backdrop` on a bucket (or a `defineHub` def) draws behind the header of every page of the hub, and `backdrop` in a page's `meta` (a `HubPage` field) overrides it for that page and its sub-pages. A bucket can instead hold `src/screens/<bucket>/<bucket>.backdrop.tsx`, which default-exports a component that becomes the bucket's backdrop as `{ kind: 'node' }`, since `screens.config.ts` can hold no JSX and import nothing but `defineScreens`: sync lists it as a `backdrop` entry loaded with `lazyComponent`, and `buildScreenTree` draws it inside a `Suspense` with no fallback, and `withBackdropPreload` joins its `preload` to the hub home's and to every page, tab and sub-page of the bucket, so it loads wherever they preload: the hub screen (a bucket switch pill, the boot preload), a menu row or hub nav entry on hover or focus. Opened with nothing preloaded, it loads beside the page and the header draws without it until then (the review's settle waits for that load). The file wins over the config `backdrop`, and a page's `meta.backdrop` still wins over both; `brock structure` reports a bucket that has both the file and the config field, a backdrop file not named after its bucket or outside its bucket folder, and a bucket folder that holds nothing else. Its constants go in `<bucket>.backdrop.constants.ts`. It is Tessera's `Backdrop`: `{ kind: 'node', node }`, `{ kind: 'image', src, fit?, position?, tileSize?, color?, pixelated? }`, `{ kind: 'color', color }` (a CSS colour, or a token name such as `'--c-secondary'`), or `{ kind: 'none' }` for no art. `HubPageFrame` draws it with Tessera's `BackdropLayer` (`backdrop-node.ts`; an image or a colour gets the layer's `backdropStyle`, a node fills the layer) and hands that to Tessera's `ScreenPage` and `SettingsPage` as `backdrop`, and to a settings page through `SettingsPageContext`; without one the header keeps Tessera's own art.
- Reachable without a profile: `requiresProfile: false` on a bucket (or a `defineHub` def) lets its hub open while no profile is active, the way a card's `meta.requiresProfile` does, so a first run can open, say, a Data hub to create the first profile.
- One menu per hub, and only when it helps: `nav` on a bucket (or a `defineHub` def) is `'auto'` by default, which draws the side nav only while two pages or more are shown (after `devOnly`, `hosts` and `when`). With one page shown the hub draws that page alone in a scroll area (`hub__solo`), with no side nav and no hub search field; the nav comes back as soon as a rule shows a second page. `'always'` keeps the nav even for one page, and `false` never draws it, so its pages open from the menu, the palette, a link or `open`. Without the nav, Back, the history and Escape work as before: Escape closes the hub from any page and reopens it on that page, and Ctrl+K still scopes the palette to the hub. The review's `buckets` step checks a hub with no nav for the absence of the nav (`<hub>-pages`), opens each page with `open` instead of its nav entry, and its `search` step runs the hub search on the first setting found in a hub that draws a nav. On a page with a settings tab, `<hub>-<page>-row-hint` points at the first toggle row that has hints (or else the first row that has any) and passes on its pointed hint, or, for a toggle with `hints.atRest`, whose pointed hint is one of the rest lines and so stays hidden, on its current rest line (`[data-current]`); a page where no row has hints is a skipped pass.
- The bucket switch lists the buckets in config order and shows once there are two. The menu comes from the config: `entry` adds the bucket, `submenu` adds the bucket with one child per page, `hidden` adds nothing. The home bucket is the Home entry, and card screens get an entry of their own, except the ones Brock already lists (credits, about, profiles, settings). The derived entries go first among the app entries.
- Escape and Home open `config.home`. When the app has no base screen, the home bucket opens once at startup when a profile is already active.
- The base screen is `src/screens/<id>.base.tsx`, one per app at the root: `buildScreenTree` makes it a screen with `layer: 'own'`, `header: 'none'` and no menu entry (the review's `<id>-in-menu` check skips it, and any screen whose meta sets `menu: false`), `resolveScreenTree` names it as `base`, and `BrockApp` draws it under every hub as its `home` (the legacy `home` prop still wins when given). Escape closes the hub down to it, and Escape on it reopens the window closed last, or opens `config.home`. Its `meta` takes `title`, `icon`, `requiresProfile`, `devOnly` and `shortcut`. The `base-screen-file` migration (0.17.0) turns the legacy pair, a hand `defineScreen` passed through `screens` and named by `home`, into that file when the screen is only a title, an icon and a component: the file imports the component, the `defineScreen` leaves the list (the list and its export go when it is empty), and `home` and the emptied `screens` prop leave `BrockApp`. Anything else becomes a to-do naming the file.
- A sub-page is `<page>/<sub>.sub.tsx` in a folder named after its page, beside `<page>.page.tsx` or among the page's tabs. `meta.path` is its route under the page, `:name` segments being params (default: the file id), so `sessions/edit.sub.tsx` with `path: ':id/edit'` opens at `multiworld/sessions/42/edit`. The route goes into the history like a page, the nav keeps the page selected, and the page header draws the sub-page title after a Back button ("Back to <page>") that goes up to the page. With no history, Back still goes up to the page; Escape closes the window, and the next Escape reopens it on the sub-page. A page opens one with `props.openSub('edit', { id })`; the sub-page gets `sub`, `subParams` and `back()`. Sub-pages with no param in their path are in the search index under their page; a parameterised one is found through `useSearchEntries` with its full route. Pair it with `useUnsavedChanges` for an editor.
- Header actions: `meta.header` on a page, tab page meta or sub-page draws `primary` (a primary button; `open` is a sub-page path of that page, or a full route when it holds a `/`) and `search` (a filter field) in the standard page header beside the title and tabs. The field's value is screen state under the page, read with `usePageSearch()`. A page that needs more renders `<PageActions primary={{ label, icon, onClick }} search={{ value, onChange, placeholder }}>…</PageActions>` anywhere in its body: it draws nothing in place and puts the same row in the header.
- Shown per host or per profile: `hosts` (`['electron']`, `['capacitor']`, `['web']`) and `when(ctx)` on a bucket in `screens.config.ts`, or in the `meta` of a page, a tab page meta or a card, hide it where they do not hold; `ctx` is `{ profile, host, formFactor, flags }`, the active profile with its extension fields, the platform it runs on and the app's own flags. A hidden bucket, page or card has no menu entry, no nav entry, no bucket switch pill, no rail entry and no search result, its shortcut does nothing, and `open` on it shows nothing, as for a dev-only page with developer tools off. `when` runs again when the active profile, the form factor or a flag changes. The hub home (the hero, or the first page of a bucket without one) always shows: hide the bucket instead. `isShown(rule, ctx?)` and `currentShowContext()` are exported, and the review skips what is hidden: the `buckets` step evaluates each bucket's rule for the active profile with `isShown` and reports a hidden bucket as skipped passes of `<hub>-reachable` and `<hub>-pages`, with the reason.
- App flags in show rules: `<BrockApp showFlags={{ signedIn }}>` hands the app's own state to every rule as `ctx.flags`, so a page, a bucket, a card or a menu entry can show only while it holds: `when: ({ flags }) => flags.signedIn === true` in a page's `meta`. A component adds flags of its own with `useShowFlags({ ... })` while it is mounted, which is how a module contributes them (from its `Provider`); the sources merge in mount order, and the `showFlags` prop is applied last, so the app has the final say. When a flag changes, the menu, the hub nav (and so a hub that gains or loses its second page, see above), the search palette, the bucket switch, the rail, the shortcuts and an open screen all evaluate again. `ShowFlags` in `@drizztdourden08/brock-core/augment` types them: `declare module '@drizztdourden08/brock-core/augment' { interface ShowFlags { signedIn: boolean } }` makes `flags.signedIn` a `boolean | undefined` and checks the prop; without it every flag reads as `unknown`. A flag only shows or hides: it is not a permission check, so a hidden page's data still needs its own guard.

  ```tsx
  const App = () => {
    const signedIn = useAccount((s) => s.session !== null);
    return <BrockApp product={product} settings={SETTINGS} screenTree={screenTree} showFlags={{ signedIn }} />;
  };

  // src/screens/account/billing.page.tsx
  export const meta: ScreenMeta = { title: 'Billing', when: ({ flags }) => flags.signedIn === true };
  ```

- Kept mounted: `meta.keepMounted` on a hub page keeps it mounted, hidden, once it has been opened, while the hub shows another of its pages, so a running view (a game, a player, a long form) keeps its state; it unmounts with the hub. On a card screen it is the screen's `keepMounted`. A sub-page of a kept page replaces it as before.
- Menu order: `meta.menuOrder` orders a page or card in the title bar menu, falling back to `meta.order`, while the side nav keeps `order`; a bucket submenu keeps its home first and sorts the rest by it once any page sets it.
- Menu from meta: `meta.menu` on a page (or tab page meta) or a card screen places it in the title bar menu: `false` hides it (a page leaves its `submenu` bucket), an override object (`{ inMenu, hidden, label, group, order, before, after, parent }`, see Menu overrides) keeps the detected place and applies to the entry's key, `'entry'` adds it at the top among the app entries, and a path such as `'Multiworld'` or `'Multiworld/Hosting'` files it under those labels. A label that matches an entry already there joins it (a plain entry becomes a submenu that keeps the entry first); a missing one is created, with the icon of the bucket of that title or a folder. Placed entries sort by `order`, then label, after the bucket entries and before the card entries.
- Settings live in a bucket: `settings.bucket`, or the home bucket. The app's `.settings.ts` pages stay where their files are, and the built-in tabs (`settings.tabs` and module tabs) join that bucket by their group (`placeSettingsTabs`): a tab goes into the bucket's nav group whose id is its `groupId`, else the one whose label is its `group` (trimmed, any case), so an app group `{ id: 'app', label: 'App' }` and a module tab with `group: 'App'` draw one App group; inside it the app's own pages come first, in their `meta.order`, then the tabs in the order the app and the modules list them (`settings.tabs` first, then each module's). A tab that matches no group starts a new one after the app's groups, with its `groupId` as the id (else `settings-<label>`), which later tabs with the same id or label join. brock-display's Display tab has `group: 'App', groupId: 'app'`. The review's `buckets` step fails a hub whose nav shows two groups with the same label (`<id>-nav-groups`). There is no separate Settings screen then: the Settings menu entry, the palette and Mod+Comma open `settings.page` when the config names a page of that bucket, else the first settings page of that bucket, or the page a tab names. `brock structure` names a `settings.page` the bucket does not hold. App page and tab ids come first: a module tab whose id an app page or tab of that bucket already uses moves to `<moduleId>.<tabId>` (`moduleTabId`), and so does one an earlier module tab took, while an unclaimed module tab keeps its own id, so links to it keep working.
- `open('<bucket>/<page>/<tab>')` opens a hub page directly, and a menu item can name `{ bucket, page, tab }` instead of `screen`.
- The hero frame has one wiring point, `packages/react/src/screens/kinds/hero-frame.constants.ts`: `HERO_FRAME` names the Tessera `Hero` composite and builds one slot component per Hero slot. A hero page renders the slot components it needs (`<Title>`, `<Eyebrow>`, `<Backdrop>`, `<Art src alt pixelated />`, `<Actions>`, `<Tools>`, `<Facts rows />`, `<Aside>`, `<Panel>`); each hands its value to the frame, which draws one `Hero` with them. `heroPage` hands the file's `meta.hero.size` to `renderHero`, and `HeroRoot` passes it to `Hero` as `size` (left out, Tessera's `default`). The frame passes `product.icons.brand` to `Hero` as `brand` when it is a Tessera brand, so a branded app shows its brand backdrop, and a hero that renders no `<Art>` gets the brand's mascot as `<AnimatedMascot brand="auto">` (the mascot of the page's `data-palette`), which waves once on arrival and blends back into idle on Tessera's mascot state machine, or its `BrandMark` with `ground="dark"` when the brand has none (Brock's is the charcoal mark with a white outline: Brock passes no `inks`, which Tessera 0.23 removed, MIGRATION 196). `<Art kind="none" />` turns the brand art off for that hero, as `<Backdrop kind="none" />` does for the backdrop: `heroArtOf` hands the frame `null`, which `HeroRoot` passes to `Hero` as `art={null}` in place of the brand art, and records the bucket in `heroArtNone` while it is drawn, so the review's `hero` step checks that hero draws no `.hero__art` (`<id>-hero-art-none`). A hero left with no art and no backdrop (an app with no Tessera brand, or `<Art kind="none" />` with no `<Backdrop>`) shrinks to its content and sits at the top instead of keeping the full hero height: Tessera's `Hero` does that itself (`hero--bare`), so the frame adds no class or rule of its own.
- `brock structure` rejects a file with an unknown suffix (a constants file is not one: `<id>.<kind>.constants.ts`, the file the constants lint rule names for a screen file such as `library.page.tsx`, and `<name>.constants.ts` for constants several screens share sit at any level and sync skips them), a bucket folder the config does not declare, a declared bucket with no folder, two heroes in a bucket, two pages with the same id in a bucket, a tab outside a page folder, a card or layer inside a bucket, a custom page at the root, a custom page without a `searchEntries` export or with one the build cannot read, a sub-page outside a page folder or with no page beside it, a base screen inside a bucket, two base screens, a base screen named like a bucket or a screen, a misplaced or misnamed bucket backdrop, and folders deeper than `<bucket>/<group>/<page>`. It also prints the number of custom pages per bucket, so the exceptions stay visible. `screens.config.ts` may import only `defineScreens` and types, since the check loads it under Node.

### Lazy registries and the Suspense host

The registries keep the boot path small: in development every module the renderer loads costs a request, so `.brock/screens.ts`, `.brock/widgets.ts`, `.brock/title-bar.ts` and `.brock/tours.ts` load only what the shell draws at boot. The authoring convention does not change: a screen or widget file still default-exports its component beside `export const meta`.

- Meta modules: the generated files import `meta` (and a title bar item's `order`) with a plain `import { meta as x } from '../src/...'`, so TypeScript checks them against the real file. The renderer Vite plugin `brock-meta-modules` (`packages/build/src/meta-modules`, in the electron and web configs) points each such import at `<file>?brock-meta`, and serves that id as the file cut down to its `meta` and `order` exports and the top-level code and imports they reach: the default export, the component, side-effect statements and imports nothing kept reads are left out. It parses with the app's TypeScript (Brock's own when the app has none) and never runs the file. When a file cannot be cut safely (a parse error, a meta that reads the default-exported component, no TypeScript), the id loads the whole file, which is still correct. Without the plugin (a test runner) the query is ignored and the whole file loads.
- Components: `lazyComponent(load)` from brock-react returns a component that suspends until `load()` resolves, then draws the default export; it has `preload()` and `loaded`, a failed load is retried on the next render (Retry in the error box works), and a preloaded component draws with no loading state. `buildScreenTree` copies each component's `preload` onto its `ScreenDef`, hub page, tab and sub-page; a hub's `preload` loads its home page. `preloadRoute(registry, route)` preloads a screen, a hub page or a tab by route.
- Suspense host: `LazyHost` is one `Suspense` boundary with one fallback, a centred Tessera `Spinner` that fades in after a short delay (so a quick load shows nothing) and carries `data-brock-loading`; while it is drawn it holds the screenshot (see Boot). It wraps the screen content in `ScreenHost` (cards, layers, the base screen and every hub), the page body in `HubPageFrame` (so the hub header and nav stay while a page loads) and the widget body in `WidgetBody` (docked, floating and popped). A component that already loaded renders synchronously, so going back to it never flickers.
- Preloading: `AppShell` preloads the base screen and the home screen when it mounts (`useBootPreload`), and `first-frame` waits for every tracked load and every `LazyHost` fallback to finish (`lazyLoads.idle`, 30 s at most) before the window is revealed, so the first screen appears drawn. Highlighting a row that opens a screen preloads it: each title bar menu item with a route (`withPreload` on the effective menu, so a renamed or moved entry still loads the right screen), each hub nav entry (`buildHubNav`), each hub switch pill and each search palette row with a target carries Tessera's `onHighlight` (MIGRATION 241), which runs `routePreloader(registry)` on the route the item opens, after route aliases such as `settings` and `profiles` resolve. Tessera calls it when the pointer enters the item, it takes focus or the arrow keys reach it, and for the palette's active row, the first one included when the palette opens.
- Waiting for loads: `lazyLoads.track(promise)` counts a load and `lazyLoads.idle(ms)` waits until none is pending and no fallback is drawn. The review's `settle` waits on it before each capture and check, a search jump does not count its 1.5 s budget while a load runs, and `tours.load(id)` loads a lazy tour's steps (the review's `tours` step calls it before it walks a tour).
- Production: the dynamic imports become one chunk per screen and per widget beside the entry chunk. Measured on a scaffolded app the packaged start was the same as with everything in one bundle (the difference stayed inside run-to-run noise), and a large app parses and runs much less code at boot, so per-screen chunks are kept.
- Module-level code in a screen or widget file now runs when the screen or widget first loads, not at boot. Code that must run at boot goes in a boot task (`src/boot/<id>.task.ts`).

### Custom pages and layers

A custom page is `<page>.custom.tsx` inside a bucket. It keeps everything standard around it: the hub frame, the nav entry, the header with title and tabs, Escape and search. Only the content is free. It must export `searchEntries: SearchEntrySeed[]`, a literal list of `{ label, keywords?, anchor?, description?, id?, params? }`, so it never hides from search; an empty list is allowed. `id` keeps two entries with one label apart, and `params` go to `open` with the page route. An element on the page is wrapped in `<SearchAnchor anchor="<anchor>">` for the jump.

A full-bleed layer at the root (a game view, a debug canvas) is `<id>.layer.tsx`. It used to be `<id>.custom.tsx`: the `custom-layer-rename` migration renames it, and `custom` now always means a page with the standard frame.

## Widgets by convention

A widget is a file too, placed like a screen: `src/widgets/<id>.widget.tsx`, flat, one per widget. The file name is the id.

```tsx
const meta: WidgetMeta = { label: 'Players', icon: 'users', defaultVisibility: 'context-only', defaultSide: 'top', popOut: true };

const PlayersWidget = () => <SessionWidget id="players" />;

export default PlayersWidget;
export { meta };
```

- The default export is the component. `meta: WidgetMeta` is optional and holds the `defineWidget` fields other than `id` and `render`: `label` (the id in title case without it), `icon`, `order` (the Widgets menu sorts by it, then by label), `popOut`, `devOnly`, `taskbar`, `defaultVisibility` (`'context-only'` shows it only while its context is active), `context` (the name of the context it needs, a running session for example, from the context registry; it makes the widget `context-only` by default), `defaultOpen` (open on a profile's first layout and after Reset layout, on its `defaultSide`, when the layout preset does not place it), `defaultSide`, `defaultDockedSize`, `defaultFloatingSize`, `padding` (`none`, `sm` the default, or `md`: the widget body pads itself, so a widget adds no padding of its own) and `fill` (a full-height body that does not scroll, as the Logs widget uses with `padding: 'none'` and LogPanel `height="fill"`), `chrome` (Tessera's widget frame: `full` the default, `compact` or `none`, docked, floating and popped; see Widget kits), `settings`, a component drawn in the widget's options, `tools`, a component drawn in the widget's title strip, `kit`, the widget kit it belongs to (see Widget kits), and `menu`, its place in the menu (see The Widgets menu).
- The app's default layout is `src/widgets/layout.ts`, the one file there that is not a widget. It default-exports `defineLayoutPreset({ rows, sizes?, widths? })`: `rows` from top to bottom, each a list of cells from left to right, where a cell is a widget id, a list of ids tabbed in one pane, or `'main'`, the main view (with no `'main'` cell the main view takes a last row of its own). `sizes` are the row heights and `widths[row]` the cell widths, as relative weights (a missing one takes the average of the others). An unknown or repeated id is skipped. A three-row session layout is

  ```ts
  export default defineLayoutPreset({ rows: [['players', 'hints', 'room'], ['main'], ['log', 'console']], sizes: [0.34, 0.32, 0.34] });
  ```

  A profile with no saved layout starts from it, Reset layout comes back to it, and context-only widgets in it stay hidden in their place until the context is active.
- `brock sync` scans `src/widgets` and writes `.brock/widgets.ts`, which imports each file's `meta`, loads its component with `lazyComponent` on first draw (docked, floating or in its own window), and exports `appWidgets = widgetsFromFiles([{ id, component, meta }])` and `appWidgetLayout`, the default export of `src/widgets/layout.ts` or `undefined`. The file is written for every app, empty when there are no widgets, so `src/main.tsx` always imports it and passes `widgets={appWidgets}` and `widgetLayout={appWidgetLayout}` to `BrockApp`. The renderer Vite plugin rewrites it when the build starts and on every change under `src/widgets`; `brock dev` and `brock build` also rewrite it before electron-vite starts; `brock check` fails when it drifts.
- `BrockApp` adds the `widgets` prop to the module widgets and hands the list to `WidgetHost` and, in a popped window, to `WidgetWindow`, so a widget file pops out like any other widget. `defineWidget`, `registerWidgets` and `RendererModule.widgets` keep working beside it; a module still ships its widgets through its renderer entry.
- `src/widgets` holds widget files, `layout.ts` and their constants files only: `<id>.widget.constants.ts` and `layout.constants.ts`, the files the constants lint rule names, and `<name>.constants.ts` for constants several widgets share, which sync skips. `brock structure` reports a file that is none of these, a `layout.ts` with no default export, a folder, an id that is not kebab-case, a widget file with no default export, a literal `meta` with a key that is not a widget field (one of the `WidgetMeta` fields above, `context`, `tools`, `kit` and `menu` included), a literal `meta.menu` that is not `{ parent?, group?, order? }` with a non-empty `parent`, a menu group and a number, and an id Brock's own widgets use (`logs`, `performance`). A widget with parts imports them from `src/views` or the design package. `brock-lint-config` lets widget files default-export and export `meta` beside it, and `layout.ts` default-export its preset.
- Brock's built-in widgets follow the same shape inside brock-react: `packages/react/src/widgets/built-in/logs.widget.tsx` and `performance.widget.tsx`, each beside its component folder, listed by `BUILT_IN_WIDGETS` through the same `widgetsFromFiles`.
- The `widget-files` migration (0.11.0) adds `widgets={appWidgets}` and its import to `src/main.tsx`, and turns every hand-made widget (a `defineWidget` call, a `registerWidgets` call, a hand `widgets` prop) into a to-do naming `src/widgets/<id>.widget.tsx`. It moves nothing itself, because a hand definition can close over app state that a file of its own would lose.
- The `widget-layout-prop` migration (0.17.0) adds `appWidgetLayout` to the `.brock/widgets` import of `src/main.tsx` and `widgetLayout={appWidgetLayout}` beside `widgets`, unless `BrockApp` already has a `widgetLayout`.

### Widget kits

A widget kit is a group of widgets that works as one unit: a set of developer tools around a running game, an editor made of several panels, a probe with an overlay on the main view. It opens and closes as a whole, keeps a layout of its own and never mixes with the normal widgets.

```ts
// src/widgets/inspect.kit.ts
const kit: WidgetKitMeta = {
  label: 'Layout inspector',
  icon: 'layout-dashboard',
  devOnly: true,
  requires: { context: 'scene', reason: 'Open a scene to inspect it.' },
  layout: defineLayoutPreset({ rows: [['inspect-grid', 'main', 'inspect-pointer']] }),
};
export default kit;

// src/widgets/inspect-grid.widget.tsx
const meta: WidgetMeta = { label: 'Grid', kit: 'inspect', tools: InspectGridTools };

// src/widgets/inspect-grid.overlay.tsx
const meta: KitOverlayMeta = { kit: 'inspect', label: 'Grid overlay' };
```

- Files: `src/widgets/<id>.kit.ts` default-exports a `WidgetKitMeta`, the `WidgetKitDef` fields but `id` and `overlays`: `label` (the id in title case without it), `icon` (default `wrench`), `order`, `devOnly`, `requires: { context, reason }` and `layout`, a `defineLayoutPreset` for the kit's own first layout. A widget joins the kit with `kit: '<id>'` in its `meta` (or its `defineWidget` input); it is still a `<id>.widget.tsx` file with every widget field. `src/widgets/<id>.overlay.tsx` default-exports a component drawn over the main view and exports `meta: KitOverlayMeta` (`kit`, `label?`, `order?`).
- `brock sync` writes `.brock/widget-kits.ts` beside `.brock/widgets.ts`, for every app, empty when there are no kits: `appWidgetKits = widgetKitsFromFiles({ kits: [{ id, meta }], overlays: [{ id, component, meta }] })`, the overlays loaded with `lazyComponent` on first draw. `src/main.tsx` passes `widgetKits={appWidgetKits}` to `BrockApp`. Without files, `defineWidgetKit({ id, label, ..., overlays: [{ id, label, render }] })` goes in `BrockApp`'s `widgetKits`, a `RendererModule`'s `widgetKits`, or `registerWidgetKits(kits)`, which returns the remove call.
- The menu: each kit is a sub-menu of Widgets, after the widgets and before Reset layout, sorted by `order` then label: Open kit or Close kit, then the kit's widgets and overlays as checkable entries, then Reset kit layout (a `confirm` entry). A blocked kit shows its reason as the entry's description, and a `devOnly` kit sits in the Developer submenu of Widgets, which is left out while developer tools are off (see The Widgets menu). Picking a kit widget opens its kit with that widget. `widgetKits.open(id)`, `widgetKits.openWidget(id)`, `widgetKits.close()`, `widgetKits.toggle(id)`, `widgetKits.reset(id)`, `widgetKits.active()` and `widgetKits.isOpen(id)` work outside React; `useWidgetKitStore` is the store.
- One kit is open at a time. Opening a kit, from the menu, `widgetKits.open`, `widgetKits.toggle` or a kit widget, closes the open kit first, with its popped windows. While a kit is open, `WidgetHost` hands Tessera's `WidgetManager` the kit's widgets and the kit's layout in place of the normal ones: the normal docked and floating widgets step aside and the normal popped windows close (they keep their place, as a gated window does) and all come back when the kit closes. So a kit widget docks, tabs, splits beside the main view, floats over it and resizes with the same `DockLayout` drag, snap and resize as any widget, but only among the kit's widgets. Each kit widget gets its kit id as its Tessera `group` (normal widgets have none), so `WidgetManager` never lets a kit widget tab or split with a widget of another group, and a popped kit widget dragged back over the app is offered only to its kit's layout.
- Normal widgets close the kit. The normal widget entries and Reset layout stay enabled while a kit is open, shown unchecked since they are not on screen. Opening a normal widget, from the menu, a shortcut, `widgets.open`, `widgets.toggle` or `widgets.popOut`, closes the open kit first, and the normal layout comes back with that widget open (a toggle while a kit is open always opens). Reset layout closes the kit too. `widgets.close` on a normal widget and an id that is no widget leave the kit open.
- The widgets API reaches kit widgets. `widgets.open(id)` and `widgetKits.openWidget(id)` on a kit widget open its kit, closing any other, and show the widget in the kit even when the user had closed it there; one already shown stays as it is, so a list of ids opened one by one, such as an app's startup flag, opens them together. A list that mixes normal and kit widgets ends on the side of the last id, since each side closes the other. `widgets.toggle(id)` opens the kit with the widget, or closes the widget alone while its kit is open; `widgets.close(id)` closes it in its kit layout; `widgets.popOut(id)` opens its kit with the widget in its own window; `widgets.isVisible(id)` is true while its kit is open and holds it.
- Pop-out: a kit widget with `popOut` pops out into its own window like a normal widget, from its title strip, its options or `widgets.popOut`. The window belongs to the kit layout: closing the kit by any route (Close kit, the kit bar, `widgetKits.close()`, another kit, a normal widget, a profile switch, the gate) closes its windows, and they keep their place in the kit layout, so reopening the kit brings them back popped or docked as they were left. The kit's popped windows also close while the gate holds the kit on its reason card. Their frame (opacity, visibility) is shared with the windows like a normal widget's.
- Pages: while a page is open (Home or any screen), the open kit steps aside like a context-only widget: its docked and floating widgets, its overlays and its kit bar are hidden, the kit stays open and its layout is untouched, and it comes back as it was when the page closes. Its popped windows follow the normal popped rule: a context-only one closes and keeps its place, the others stay.
- Closing: Close kit in the menu, `widgetKits.close()` and the close button of the kit bar close the whole kit at once. The kit bar is a small strip at the top centre of the main view with the kit's icon, its label and that button. Each widget keeps its own close button, which closes that widget alone, and the kit stays open (its overlays and bar too) until it is closed.
- Overlays: while the kit is open, each overlay the user has not hidden is drawn in its own layer over the main view, under the kit's floating widgets, and unmounts when the kit closes. The layer lets the pointer through (`pointer-events: none`), so an overlay that wants the pointer sets `pointer-events: auto` on its own parts; one that only reads it listens on `window`. Hiding an overlay from the menu is saved with the kit.
- The gate: `requires: { context, reason }` names a context from the context registry (see Widgets above). While that context is inactive the open kit draws none of its widgets or overlays: a card over the main view gives the kit's name, the reason and a Close kit button, and the kit bar stays. When the context turns active the kit draws as it was left, and when it turns inactive again the card comes back. Unlike a context-only widget, the kit gate reads the registry also on a review launch, so the review can check the reason.
- Layout per kit: each kit keeps its own `{ layout, hidden }` (the kit's dock tree and floating rects, and the overlays the user hid), saved per profile in `ui-views.json` under `profile:<id>` as `widgetKits.<kit id>`, written 250 ms after a change like the widget layout and read when a profile becomes active; a stored entry that is not an object, or has no layout, is dropped, and its popped list is kept (without window groups), so a kit that was closed with a popped widget opens with it popped again. A kit opens on its saved layout, else on its `layout` preset, else with every widget open on its `defaultSide` (a kit widget is `defaultOpen` unless it says `defaultOpen: false`). Reset kit layout goes back to that first layout. A profile switch closes the open kit.
- Title bar tools: a widget's `tools` (a component in `meta`, or `() => ReactNode` in `defineWidget`) is drawn in its title strip before Tessera's own buttons, through `WidgetManager`'s `widgetActions` and, in a popped window, `Widget`'s `titleBarActions`, with the widget id around it so `useWidgetState` works there. It holds `size="xs"` buttons. This works for every widget, in a kit or not.
- `brock structure` reports a kit file without a default export, a kit key that is not a kit field, a literal `menu` that is not a placement (see The Widgets menu), an overlay without a default export or a `meta`, an overlay key that is not an overlay field, and a widget or overlay whose `meta.kit` names no kit file. `<id>.kit.constants.ts` and `<id>.overlay.constants.ts` are constants files there.
- The `widget-kits-prop` migration (0.54.0) adds `widgetKits={appWidgetKits}` and its import from `../.brock/widget-kits` to `src/main.tsx`.
- The template ships a small kit, `inspect` (Layout inspector, `devOnly`), whose two widgets use `chrome: 'compact'`: a Grid widget with a size slider, a centre lines switch and a reset tool in its title strip, a Pointer widget that reads the pointer over the main view, and a grid overlay drawn over the main view, sharing `src/stores/useInspectStore.ts`.
- Frames and snapping: a widget's `chrome` (`meta.chrome` or `defineWidget`'s `chrome`) is Tessera's `full` (the default), `compact` (a 21 px title strip) or `none` (no strip; the buttons and a grip show on hover or focus). `WidgetManager` passes it to docked and floating widgets and `WidgetWindow` to the popped `<Widget mode="out">`, kit or not. `WidgetHost` passes `floatSnap` (10 px) to every widget, kit or not, so a floating widget snaps to the stage edges, the main view and the other floating widgets with guide lines.
- Kits stay exclusive (BQ-06): Tessera's groups would let normal widgets sit beside an open kit, but a kit still replaces the normal widgets while it is open.

### The Widgets menu

The Widgets section of the menu lists the widgets sorted by `order`, then label, then each kit as its own sub-menu, then a Developer sub-menu, then Reset layout. Developer (key `widgets-developer`, icon `braces`) collects every `devOnly` widget and every `devOnly` kit, so a developer kit reads Widgets > Developer > its label > Open kit, its widgets, its overlays, Reset kit layout. It shows only while developer tools are on, the rule that hides any `devOnly` entry, and it is left out when nothing goes in it, so there is never an empty sub-menu.

```ts
// src/widgets/tuner.widget.tsx: into a sub-menu of its own, made when no entry has that key
const meta: WidgetMeta = { label: 'Tuner', menu: { parent: 'audio-tools' } };

// src/widgets/paint.kit.ts: a kit that is not devOnly, filed under Developer anyway
const kit: WidgetKitMeta = { label: 'Paint', menu: { parent: 'widgets-developer' } };
```

- Placement: `menu?: { parent?, group?, order? }` on `WidgetMeta` and `WidgetKitMeta` (and on `defineWidget` and `defineWidgetKit`, the `WidgetMenuPlacement` type) places the entry like the same fields of `product.menu.entries` (see Menu overrides): `parent` names a sub-menu by key, `group` lifts the entry to a group of the menu and `order` sorts it in the list it lands in. `menu.order` is the menu config's order; the widget's own `order` still sorts it among the widgets. `useWidgetMenuEntries` turns the placement into the entry's own `parent`, `group` and `order`, and the config wins field by field.
- A missing parent is made: when a `widget-<id>` entry, a `kit-<id>` entry (or one of a kit's own rows) or `widgets-developer` names, in its meta or in `product.menu.entries`, a `parent` that no entry has, `resolveMenu` (through its `grows` input, `widgetMenuGrows`) plants a sub-menu with that key where the first entry naming it sat, labelled from the key (`audio-tools` reads Audio tools, with the folder icon), and files the entries into it. `product.menu.entries['audio-tools']` renames or moves it like any entry. A `parent` that already exists, an app sub-menu, a kit sub-menu or Developer, takes the entry as before. Other entries do not make sub-menus: a `parent` no entry has still leaves them in place with an issue.
- The Developer sub-menu: an entry goes in it when its `parent`, from `product.menu.entries` first, then its meta, is `widgets-developer`, or when it has no `parent` and is `devOnly`. `parent: null` in the config keeps a `devOnly` entry out of it. Whatever sits in it hides with it while developer tools are off, a widget that is not `devOnly` included. `product.menu.entries['widgets-developer']` renames it (`label`), moves it (`parent`, which may make a new sub-menu, `group`, `order`, `before`, `after`) or hides it. Brock always knows the key, so naming it while developer tools are off reports nothing. `arrangeWidgetMenu` builds it, and `resolveShellMenu` counts the sub-menus made from the unfiltered menu as known keys, so a config entry for a sub-menu that only `devOnly` widgets make reports nothing either.
- The search palette lists the widgets with the sub-menus as their path (Developer > Probe), and the review follows the drawn menu: the `kits` step registers a `devOnly` widget and a `devOnly` kit and checks that Widgets > Developer lists both (`widgets-developer-shown`) and that the kit is a sub-menu there with Open kit (`widgets-developer-kit`, captured as `widgets-developer-menu`). It drives developer tools through a binding of its own, so a development run checks both states too: it opens the dev widget and the dev kit, turns developer tools off, checks that both closed (`widgets-developer-closes`) and that Developer is gone (`widgets-developer-hidden`), then turns them on and checks that Developer is back with the widget and kit still closed (`widgets-developer-back`). The `widget-windows` step does the same for a popped `devOnly` widget: its window opens with developer tools on (`gate-dev-only-opens`), closes with the widget when they go off (`gate-dev-only-closed`) and stays closed when they come back (`gate-dev-only-stays-closed`). Each `devOnly` app kit with no placement of its own also gets `app-kit-<id>-in-developer`.

## Tours by convention

A guided tour is a file too: `src/tours/<id>.tour.ts`, flat, one per tour, default-exporting `defineTour({ id, title, description?, steps, trigger? })`. The file name is the id; `brock structure` reports a literal `id` that differs. Tessera draws the tour (`GuidedTour` and `useGuidedTour`, MIGRATION 178): the lit part keeps a rounded hole with a primary glow while the rest dims and blurs, the hole glides from step to step, a bubble explains it and the mascot walks on `MascotStage` to present it. Brock wires it into the app.

```ts
export default defineTour({
  id: 'welcome',
  title: 'Welcome',
  trigger: 'first-run',
  steps: [
    { id: 'menu', target: { shell: 'menu' }, title: 'The menu', body: 'Every screen is here.', mascot: 'wave' },
    { id: 'notes', widget: 'notes', advanceOn: { click: { widget: 'notes' } }, title: 'Notes', body: 'Click it to write.' },
    { id: 'settings', open: 'settings', target: { shell: 'screen' }, title: 'Settings', body: 'Saved with your profile.' },
  ],
});
```

- A step is `{ id, title, body, target?, placement?, mascot?, hint?, open?, widget?, context?, before?, advanceOn? }`. `target` is Tessera's `TourTarget` (`{ tour }` for `[data-tour]`, `{ selector }`, a ref) or a Brock one: `{ shell: 'menu' | 'search' | 'report-bug' | 'title-bar' | 'screen' }` (the hamburger, the Search and Report a bug bar items, the bar, the open screen's card), `{ widget: '<id>' }` or `{ setting: '<key>' }` (a settings row, `[data-setting-key]`). Brock hands Tessera a ref whose `current` resolves the target each time Tessera looks for it, so a part a step opens is found once it draws. `placement` is the side Tessera tries first for the bubble; Tessera places it (MIGRATION 195): it flips to a side that fits, keeps 12 px from the window edges, and sits inside the hole near its foot when no side fits, as beside a tall widget or a card that fills the window. `mascot` is a Tessera `TourStepMascot`: a `MascotClip` played where the mascot stands, or `{ walk?: 'move' | 'move-wobble', arrive }` to walk to the bubble with `walk` and play `arrive` there; Tessera keeps the mascot off the lit part, or hides it for that step. The mascot is the app's brand mascot (`mascot="auto"`, from the page's `data-palette`). `hint` replaces the line under the body on a click or wait step.
- Before a step shows, Brock runs its preparation as Tessera's `onEnter`, which the step awaits: `open` goes to a screen, a hub page or a sub-page route (`nav.open`), `widget` opens that widget when it is not on screen, `context` sets a context in the registry (`'session'` or `{ name, active?, data? }`), then `before(ctx)` runs and may return a promise. `ctx` is `{ tourId, stepId, index, profileId, signal, open, close, openWidget, setContext }`; `signal` is Tessera's `AbortSignal`, aborted when the user moves on or closes the tour before the step shows, so a long `before` can stop early. A step aborted before it starts prepares nothing, and an aborted step is never shown. Back runs the preparation of the step it returns to again, so it must be safe to run twice.
- `advanceOn` makes the user act to go on. `{ click: target }` becomes Tessera's `advance: 'click'`: Next hides, the lit part stays reachable and a click on it goes on after the app's own handler ran. With no `target` of its own the step lights the clicked part; with one, the click target is Tessera's `clickTarget`, reachable beside the lit part (one entry of a lit menu, say). `{ event: '<name>' }` (sent with `tours.emit('<name>')`) and `{ context: '<name>', active? }` (the context turning active, or inactive with `active: false`) become `advance: 'wait'`: Next hides, the lit part stays reachable, the bubble asks the user to do what the step says (or shows `hint`), and Brock calls the tour's `next()` when the event or the context comes. A step whose target is absent shows its bubble in the middle; when it is a click step and its click target is absent too, `TourHost` gives it Next (`advance: 'next'` for that step while it is shown), so the tour never stops on a part that is not drawn.
- The runtime is `tours` (`start(id, at?)`, `stop()`, `next()`, `back()`, `goTo(i)`, `emit(name)`, `list()`, `isOpen()`, `isCompleted(id)`) and `useTour()` (`{ active, tour, step, tours, start, stop, next, back, isCompleted }`), over one zustand store. `TourHost`, mounted by `AppShell` in the main window, draws the open tour with Tessera's `GuidedTour` controlled through `step` and `open`. Its `onStepShown` keeps the drawn step (`{ id, index, step, target }`) in the store as `shown`, which the review reads, and `onStepLeave` clears it.
- Tour state belongs to the app, not to a profile. Progress is kept app-wide in `app.json`, beside `lastProfileId`, as `tours`: `{ completed, started, last }`, written through brock-core's `updateAppState`, which runs one change after another so a profile switch never loses it. `start(id)` resumes an unfinished tour at its last step and restarts a finished one at the first; Next on the last step marks it completed, for every profile.
- First use: `app.json` also holds `firstRun`, the app's one marker of first-time use. When `TourHost` mounts (with the app shell, before the boot tasks finish) and finds no marker, it sets `pending` on a fresh install and `done` when the install already has profiles or anything in `ui-views.json`, so an install upgraded from a version without the marker is never on its first use, and a first-run tour an app adds in a later version never starts by itself there (it is under Take the tour and in search). `trigger: 'first-run'` starts the first such tour the app has never started, once, while the marker is `pending`, after the boot is `ready` (the splash is gone), the state has loaded and a profile is active (on a fresh install, the one the user makes on the setup screen), whichever profile it is. That turn sets the marker to `done`, whether or not the app has a first-run tour, so a profile made later never starts one again. Quitting before any profile is active keeps the first use open for the next launch. An automation launch never starts one and never ends the first use.
- Upgrade: the same mount moves the per-profile progress of earlier versions (`profile:<id>.tours` in `ui-views.json`) into the app-wide record, keeping every tour any profile started or finished (a resume step from `app.json` wins over one from a profile), writes `app.json` first and then drops the `tours` keys from `ui-views.json`, so it runs once and a crash between the two writes only merges again. It is a data migration at runtime; no source migration is needed.
- Menu > Take the tour (`compass`) starts the only tour, or lists every tour in a sub-menu. It sits in the Help section when an app or module menu entry uses `section: 'help'`, else in Advanced. The search palette has one action per tour, Take the tour: <title>.
- Keys: Tessera's, in the capture phase ahead of the app's handlers (Right or Enter goes on, Left goes back, Escape closes; Right and Enter do nothing on a click or wait step). Escape closes the tour through the escape stack at `menu`, so a menu or popover opened during a step closes first, and the shell, which stands down while anything above `screen` is on the stack, never closes the screen under it. While a tour is open the shell shortcuts keep working (Ctrl+K, Alt+Enter, screen shortcuts, Back); the shell handler holds only Escape, with or without a modifier, so it never closes a screen under the tour, and the plain keys the open step moves on (Left on every step, Right and Enter too on a Next step), in case Tessera passes one on, as Enter on a focused button.
- Layers and focus: Tessera's tour layer sits in the portal root above the screens and the widgets, makes the rest of the page inert and moves focus to the bubble. `TourHost` passes `keep={[{ selector: '.window-title-bar' }]}`: Tessera leaves the title bar live (it makes inert only the siblings along its path) and cuts a plain hole over it in the veil, so the bar is neither dimmed nor blurred, also when the lit part is inside it; the glow ring sits in the top layer above it. Brock adds no inert handling and no lift of its own. The veil and ring are Tessera's `.tour-spotlight__veil` and `.tour-spotlight__ring`.
- A widget popped into its own window: the main window's step has no target there, so its bubble sits in the middle of the main window, and the lit part is drawn in the widget window. While a step is shown and its lit part is a popped widget (`{ widget }`, or a `{ selector }` or `{ tour }` target of a step whose `widget` is popped), `TourHost` keeps `spot: { widget, selector }` in the tour store (for a whole widget, its content, `.widget__content`, so the ring shows inside the window under the kept widget title bar) and relays it to the widget windows (the `tour-spot` slice, sent at once and again when a window subscribes); `WidgetWindow` draws Tessera's `<TourSpot target={{ selector }} keep={[widget title bar]} />` while the spot names its widget, and drops it when the step or the tour ends. A click step whose click target is in a popped widget (its `advanceOn.click`, which is also the lit part when the step has no `target`: a `{ widget }`, or a selector, `{ selector }` or `{ tour }` of a step whose `widget` is popped) becomes a Tessera `advance: 'wait'` step, so Next hides, the hint line shows (the step's `hint`, else Tessera's click words), and Tessera adds no click listener in the main window: a click on a lit part there, such as the step's own `target`, never moves it on. A click target in the main document stays `advance: 'click'` with `clickTarget`. `TourHost` keeps `clickRelay: { widget, selector, step }` in the tour store, `step` being `<tour>:<index>`, and relays it (the `tour-click` slice). The widget window it names listens for a click inside that target, matched as Tessera matches in the main window and after the app's own handler, and sends `advanceWidgetTour(step)` once (`widget:tourAdvance`); main hands it to the main window (`widget:tourAdvanced`, `onWidgetTourAdvance`), where `TourHost` calls the tour's `next()` when `step` is still the shown step, so a late or second click does nothing. The listener goes when the step changes, the tour closes or the widget docks back, as the slice changes or empties.
- `RendererModule.tours` adds a module's tours after the app's; a repeated id is dropped with a warning in the app log.
- `brock sync` scans `src/tours` and writes `.brock/tours.ts`, `appTours = toursFromFiles([{ id, tour }])` in id order (a tour whose `title`, `description` and `trigger` are literals is listed by those alone, `lazyTour(shell, load)`, and its steps load when it starts; any other tour is imported whole), which `src/main.tsx` passes as `<BrockApp tours={appTours}>`. The renderer Vite plugin rewrites it on every change under `src/tours`, `brock dev` and `brock build` before electron-vite starts, and `brock check` fails when it drifts. `brock structure` reports a file that is neither `<id>.tour.ts` nor a constants file, a folder, an id that is not kebab-case and a file with no default export. A tour's own constants (a selector it lights, say) go beside it in `<id>.tour.constants.ts`, the file the constants lint rule names, and constants several tours share in `<name>.constants.ts`; sync skips both. The `tour-files` migration (0.27.0) adds the prop and its import to `src/main.tsx`.
- The review's `tours` step runs every tour headless end to end: it starts it at the first step, waits for the step `onStepShown` reported (and its target and lit ring when the step has a target; a step whose target is absent counts as shown, centred, with a passing `<step>-centred` check in place of `<step>-lit`, and goes on with Next), checks on every step that the title bar is live and not under the veil, that the bubble is inside the window and that the mascot does not touch the lit part, captures `tour-<id>-<NN>-<step>`, then goes on as the user would (a click on the click target, sent into the widget window with `reviewWidgetProbe({ kind: 'click', id, selector })` when it is popped, the Next button, `tours.emit` for an event, `tours.next()` for a context), and checks the tour ends kept as completed. Then Escape closes a tour opened over the home screen and leaves the screen open, and a review-only step lights the first `popOut` widget in its own window: the widget window must draw a lit `TourSpot` (probed with `reviewWidgetProbe({ kind: 'tourSpot', id })`), captured as `tour-popped-widget` beside `tour-popped-widget-main`; the bubble must hide Next and show the click hint, a real click in the widget window (the `click` probe: main finds the selector's centre and sends a mouse down and up with `sendInputEvent`) must move the tour to its next step, and the spot must go when the tour closes.

Where every other kind of app code goes is in [app-structure.md](app-structure.md).

## Search

The global palette and each hub's search read one index. Every entry has one shape: `{ id, kind, label, keywords, breadcrumb, target: { route, anchor? }, icon }`, with `breadcrumb` the labels of bucket, group, page and tab. A hub searches the same index filtered to its bucket. Both rank with `rankEntries`; `rankInScope(entries, query, bucket)` splits that one ranking into the open hub's entries and the rest, which is how the palette puts the hub first.

| What is found | Where it comes from | When |
|---|---|---|
| Buckets, pages, tabs, cards | the screen files and their `meta` (title, icon, keywords) | build: `.brock/search.ts` |
| Settings sections and rows | `.settings.ts` sections (title, label, description, keywords) | build |
| Custom page contents | the page's `searchEntries` | build |
| Module screens and settings tabs | the module registries | runtime, when the module loads |
| Widgets, menu entries, actions | the widget registry, the derived menu, `registerSearchActions` | runtime |
| Data a page shows | `useSearchEntries(entries)` | live, while the page or provider is mounted |

- The build never loads a page to read it. `.brock/search.ts` imports only `screens.config.ts` and `buildSearchIndex`: `brock sync` and the Vite plugin read `meta`, the sections and `searchEntries` from the source text as literals, so page code stays lazy and runs nowhere at build time. A value that is not a literal (a call, a reference to an import) is skipped; settings rows the build cannot read are still indexed at runtime from the settings tab. Keywords are folded once at build time: lower case, no accents, split into words.
- `useSearchEntries(entries, route?)` adds entries while the calling component is mounted and removes them on unmount. They point at the page that was open when it mounted, or at `route`. A page's entries exist while that page is shown; a module Provider mounted for the whole session passes its `route`. Pass a stable list (`useMemo`). Each seed is `{ label, keywords?, anchor?, description?, id?, params? }`: `id` is the key, so entries with the same label stay apart (one per preset, say), and `params` are passed to `open` when the entry is picked.
- Picking a result calls `nav.open(route)`, the same deep link as `open('game/tracker/map')`, then scrolls to the element whose `data-setting-key`, `data-section` or `data-search-anchor` matches `anchor` and flashes it with `search-hit`.
- A hub search shows its matches in SideNavLayout's results slot through Tessera's SearchResults, grouped by page, the groups in the order of their best hit in the shared ranking (pages with no ranked hit follow in page order). A settings page (a `HubPage` with `settingsTab`) shows its live rows that match, under their section titles and editable in place, filtered by the same `resolveSections` the page uses, so the count is the rows drawn. Any other page shows link hits from the index that jump to the page and row. A page heading opens the page, and the pages the ranking finds are offered as jumps. A hub given `search.index` keeps its own index.

## Build

```ts
defineBrockViteConfig(rootDir, overrides?)   // electron-vite: main electron/main.ts, preload electron/preload.ts, renderer src/ with index.html, the splash preload entry, the splash plugin (splash.html from the product config and the look), React plugin, dedupe react, externalizeDeps excluding @drizztdourden08/*
createBuilderConfig(product, { rootDir })    // electron-builder: appId, productName, icons, artifact names, file associations, asarUnpack for Velopack, the afterPack hook
```

`build` in `brock.config.ts` sets what the managed Vite configs take, so `electron.vite.config.ts` and `vite.web.config.ts` stay one line: `aliases` (import prefixes beside `@app`, folders relative to the app, for main, preload, the renderer, its workers and the web build, and added to the managed `tsconfig.json` paths; an app moving into one folder keeps its older aliases there while their code moves) and `nodePolyfills` (`true` or the options of `vite-plugin-node-polyfills`, which the app installs, in the renderer and in each worker build). Workers always build as ES modules, so a worker takes static and dynamic imports, and a renderer Web Worker imported with `?worker` (for port-kit's `runAssetWebWorkerJob`) builds as its own chunk, and a main process worker imported with `?modulePath` (`import workerPath from './job.worker?modulePath'`, for `new Worker(workerPath)` or port-kit's `runAssetWorkerJob`) builds as its own file beside `main.js`, since the main config names `electron/main.ts` as a build input, not a library entry; and `public/` (with a `public/wasm/` folder) is served at the page root and copied as it is. `devOnlyPlugin` sits first on every side: a production build has no dev-only screen or handler group (see Screens by convention and Main process). The options are in `packages/build/README.md`, brock.config.ts.

The renderer dev server pre-bundles what Brock can find before the first page loads, so a cold start runs Vite's dep optimizer once instead of discovering dependencies as the page asks for them, re-running it and reloading. `defineBrockViteConfig` sets `optimizeDeps.include` on the dev server only: React and `react-dom/client`, the renderer entries of Tessera and of each Brock package the app installs in `node_modules` (a linked package is source, never pre-bundled), and every package import of the files under `src/` and of the linked workspace packages they reach, read as text (a deep import such as `@iconify-icons/<set>/<icon>`, and the imports of worker files, which Vite's scanner does not follow). An import a linked package resolves from its own `node_modules` is written `<linked> > <dep>`. `build.optimizeDeps` adds `include`, `exclude` (also dropped from the computed list), `entries` and `worker`, the dependencies only a renderer Web Worker imports that the read cannot see, such as Node built-ins served through `nodePolyfills`. The list is sorted, so the optimizer hash only changes when an import does. Under `electron-vite dev` the read starts when the config loads and runs while main and preload build.

In dev, main keeps Chromium's HTTP cache across boots while the optimizer hash in `node_modules/.vite/deps/_metadata.json` (named by the dev server in `BROCK_DEV_DEPS_METADATA`) matches the one of the last dev boot, so the pre-bundled chunks, served as immutable under versioned URLs, are not downloaded again. A new hash clears it once, and `BROCK_DEV_CLEAR_CACHE=1` clears it on every dev boot. Vite serves source modules and `public/` files with `no-cache`, so an edit always shows on the next load.

`build.define` names globals the build replaces in main, preload, the renderer, its workers and the web build (`__APP_BUILD__: '2026.10'`). Each value is a JSON value that Brock turns into the expression Vite's `define` takes, so the code reads it as written; the app declares each name in a `.d.ts` of its own. `tsconfig.compilerOptions` in `brock.config.ts` merges over the managed `tsconfig.json`, key by key, `paths` entry by entry beside `@app` and the aliases (`{ noUncheckedIndexedAccess: false }` while an app works through those errors); without it the file is the managed one, byte for byte. `brock check` compares the merged file, so the options live in the config, never in a hand edit.

The managed `electron.vite.config.ts` and `vite.web.config.ts` pass `import.meta.dirname`, which a CommonJS package leaves empty, so an app's `package.json` must say `"type": "module"`; `brock sync` and `brock check` say so while it does not, and `brock check` fails. electron-vite adds a CommonJS shim (`__dirname`, `require`) to an ES main or preload chunk after the last text that looks like an import, which can be an import line inside a template literal; `esmShimPlacement`, on main and preload, moves the shim after the last import statement of the chunk, so the literal keeps its text.

`gate` in `brock.config.ts` lists the app's own checks: `scripts` (package scripts, from the app's `package.json`, else the workspace root's) and `clangFormat` (C source folders, relative to the repo root, checked against the managed `.clang-format` that sync writes there, in the house C style). `brock gate` runs the C check, then each script, all of them, and fails when one did; the managed CI `quality` job of each app runs it after the release note check, and `<repo> upgrade` after the gate scripts of each app. `brock clang-format` rewrites the C sources to the style. The clang-format they run is pinned in the app or the repo as an exact `clang-format-node` dev dependency (current LLVM binaries built from source for Windows, macOS and Linux), so CI and every machine format alike; `BROCK_CLANG_FORMAT` names another binary, and with neither the C check fails and names the package to add.

When `tessera.config.json` sets `guide.parts` (at the root or in an `apps` entry), `brock sync` then runs `tessera guide`, which writes the part names into `TesseraApps`; a fresh app sets it to `.brock/tessera-parts.ts`, which the `.brock` knip entry and the tsconfig include `.brock/*.ts` already cover. The include names the files, not the folder: TypeScript skips dot folders when it expands a folder entry, so `".brock"` matched nothing and a `.brock` file no other file imports (as `tessera-parts.ts`) never reached the program; the `brock-dir-type-checked` migration (0.34.0) rewrites that entry in every `tsconfig*.json` of an app. `tessera guide` reads the `tessera.config.json` of the app, or of the workspace above it, and runs where Tessera is installed: the config folder when it has Tessera, else the first workspace package outside every `apps` entry that has it (the design package, which reads the whole config as the root would), else each `apps` entry with Tessera. Tessera refuses a repo root that does not list it, and run in an `apps` folder it puts every part folder of the merged config in that app's `guide.parts` file, so a sync from `apps/desktop` never runs it there while another package has Tessera. A guide that reports problems only warns; `brock tessera check` lists them. The guide folder it writes (`guide/` beside `tessera.config.json`, or `guide.out`) is generated output: a fresh app ignores it in git (`/guide/`), `brock dev`, `brock build` and `brock start` run `tessera guide` first when it is missing, and the `guide-folder-ignored` migration (0.22.0) adds the ignore line and makes a tracked copy a to-do. `brock migrate` runs `brock sync` again when a Brock migration changed the app, so a file a migration adds (such as `session.base.tsx`) reaches `.brock`.

A `declare module '@drizztdourden08/tessera'` block, such as the `guide.parts` module or an app tree module, adds to the Tessera entry file only when that file is already in the program: TypeScript resolves the name of an augmentation but never adds the file it names, so with nothing else importing the root it fails with TS2664 ("Invalid module name in augmentation"). App parts reach Tessera through subpaths (`/primitives`, `/composites`) and Brock's packages do the same, and in an app scaffolded with `--local` the Brock packages are links whose imports resolve to Brock's own Tessera copy, at another real path than the app's; so the app's own entry file may not be loaded at all. `brock sync` therefore writes `.brock/tessera.ts`, `import type {} from '@drizztdourden08/tessera';`, for every app that lists or holds Tessera (and removes it otherwise): the tsconfig include `.brock/*.ts` puts it in the program, so the entry the app itself resolves is always there for any augmentation.

`brock sync` also writes `.brock/handlers.main.ts` from `electron/handlers/<subject>-handlers.ts`, `.brock/review.ts` from `src/review/seed.ts` and `src/review/<id>.step.ts`, and `.brock/tours.ts` from `src/tours/<id>.tour.ts`.

`brock sync` and `brock check` run from an app root, or from a repo root with `brock.workspace.mjs`: there they find the app folders from the workspace's electron targets (then from the `pnpm-workspace.yaml` globs) and run once per app.

`brock` CLI: `sync [--check]`, `gate`, `clang-format [--check]`, `add <id | spec>`, `dev` (electron-vite dev), `build` (electron-vite build), `sync --if-stale` (syncs only when `.brock/manifest.json` is missing or older than `brock.config.ts`, `package.json`, `src/screens`, `src/widgets`, `src/title-bar`, `src/tours`, `src/boot`, `electron/boot`, `electron/handlers` or `src/review`), `icons [--force]` (copies the Tessera brand set into `build/` and `public/logos/`, draws the bot variant and, for an app that ships to Windows, the Setup splash; `dev` and `build` run the copy first), `start [-- args]` (runs `dist/electron/main.js` with Electron, after the same stale check and a half-build check; automation args pass through, so `brock start -- --no-focus --muted --user-data=<dir>` is the headless smoke test), `package [--full] [--channel <name>]`, `release-notes check [version]` (see Release notes).

`dev`, `build` (and so `package`), `start` and the repo command's `launch` run `brock sync` first when `.brock` is missing or stale, since a fresh checkout may ignore it, and touch the manifest after. `dev` and `build` then check that every `../.brock/*` file `src/main.tsx` imports exists, and stop with a message naming the missing file instead of starting a renderer that would error and hang.

A dev launch (`brock dev`, or the repo command's `launch` without `--prod`, which the review uses) builds main and preload into `dist/` and serves the renderer, so it leaves `dist/electron/main.js` without a matching `dist/renderer/index.html`. A full build writes main first and the renderer last, so main newer than the renderer, or no renderer, marks that half build. `brock start` then runs `brock build` first and says why; `launchAppForTest` (and `assertLaunchable`) from `@drizztdourden08/brock-build/testing` throws with the reason instead of opening a blank window; and `launch --prod` runs `brock build --if-stale` first. `--if-stale` builds when an output is missing, when the build is a half build, or when a source is newer than `dist/renderer/index.html`: the app's `brock.config.ts`, `package.json`, `tsconfig.json`, `electron.vite.config.ts`, `src`, `electron` and `public`, and every file of the workspace packages the app depends on (through its dependencies, transitively), outside `node_modules`, `dist`, `release`, `out`, `coverage` and dot folders; files only, so a deleted file alone does not count. A prod review (`launch main none --prod --review`) therefore always reviews the current sources, never a stale `dist`; a change to the installed Brock packages alone is not seen, so run `brock build` after an upgrade. When that build fails, `launch --prod` refuses with the reason.

## Ports

`product.ports = { base, strict? }` in `brock.config.ts` gives the app a block of local ports. The dev renderer serves on `base + 0`. Offsets `+1` to `+9` are reserved for the app's tools (a site, an API, a static server); `portFor(base, slot, offset)` from `@drizztdourden08/brock-build` computes one.

The main checkout is slot 0. `<repo> worktree create` gives each thread worktree the lowest free slot from 1 and writes it to `.brock-port-slot` at the worktree root, kept out of git through `.git/info/exclude`. `launch` writes it too for a worktree made before slots existed. Slot N moves the whole block to `base + 10 x N`, up to slot 19. `BROCK_PORT_SLOT` in the environment wins over the file.

`defineBrockViteConfig` sets the renderer `server.port` to that port and `strictPort` to `ports.strict`, true by default, so a port in use is an error, never a silent move to the next one.

Without `ports`, the base comes from the app id: an FNV-1a hash of the id picks one of 140 bases from 20000 to 47800 in steps of 200, below the Windows dynamic range. `create-brock` writes that base into `brock.config.ts`, so it is visible and can be changed.

## Sites

Brock supports desktop, mobile and web versions of an app, and a mix of them in one repo; every one of them draws with Tessera. The default setup is the app alone. `brock site add <name>` adds a site: a separate single-page web app at `apps/<name>` in the same pnpm workspace, such as a community site or a store beside the desktop app. The layout, the config and each step are in [app-structure.md](app-structure.md), A site.

```ts
// apps/store/brock.site.ts
export default defineBrockSite({
  site: { id: 'store', name: 'Store', brand: 'brock' },  // brand: your Tessera brand
  ports: { offset: 3 },                       // a tool port of the repo's block, in this checkout's slot
  api: { portOffset: 4 },                     // /api -> http://localhost:<same block and slot + 4>; or api: 'https://...'
  build: { nodePolyfills: true, aliases: {} },
});
```

- The template frames every page with Tessera's `SiteHeader` (brand, links, the profile as the title bar's dropdown action) and `SiteFooter`, routes by path, and ships a sign-in page as a `Card` on the brand gradient; the pages inside use the app parts.
- `defineBrockSiteConfig(siteDir)` (`@drizztdourden08/brock-build/vite-site`, the managed `vite.config.ts`) builds `src/index.html` into `dist` with a `/` base, React, the `brock-site` plugin (`data-palette` and the title from the config, the Tessera brand icon as favicon), the node polyfills when asked, `@app` and `build.aliases`, the shared singletons deduplicated, the port with `strictPort` and the `/api` proxy, and `server.fs.allow` over the workspace and every linked package.
- A site is not a Brock app: no `brock.config.ts`, so `brock sync` never writes Electron files there, the release layout does not count it (a repo with one app and two sites keeps `ci.yml`, `release.yml` and `v<version>` tags), and it has no release workflow. Its managed files are `vite.config.ts`, `tsconfig.json` and `.github/workflows/ci-<name>.yml`, written by `brock sync` from the repo root, any app or the site, and checked by `brock check`.
- Brock provides no server kit, no cloud functions, no hosting deploy and no sign-in or session layer for a site, and will not: those stay the app's own packages. The proxy target is any process the app runs on that port or URL.
- The dev server serves `src` and `public` at the page root, so a folder `src/api` (the first segment of `api.path`) would send its own module requests to the proxy and leave a blank page; `brock site add`, `brock sync` and `brock check` name such a folder.
- `site add` names the views after the site (`store` gets `StoreShell`, `StoreHome` and `StoreSignIn`, with the classes `store-shell` and so on), so two sites of one repo pass Tessera's duplicate-part check.
- `brock.site.ts` takes `tsconfig.compilerOptions` (merged over the managed site `tsconfig.json` as for an app) and `build.define`. The managed site tsconfig allows `.ts` imports, so `brock.site.ts` can import a shared constant of the repo, such as the tool port offsets the API server reads too: `import { TOOL_PORTS } from '../../ports.constants.ts'`, with the extension, since Node loads the file.

## Packaging and releases

Velopack installs and updates every app, and GitHub Releases hosts the feed.

`brock package` is its own command because it is a release step, not part of the build loop: it needs electron-builder and the `vpk` .NET tool, and it takes minutes. It runs:

1. `brock build`.
2. The icons: `brock package` copies the brand set again (`brock icons`, which the build also runs) and checks that the icon electron-builder takes on this platform exists, `build/icons/icon.ico` on Windows, `build/icons/icon.png` on macOS and `build/icons/linux/` on Linux, a folder of `<size>x<size>.png` files, the names electron-builder reads from an icon folder (it ignored the `icon-<size>.png` names of `build/icons/png/`, fell back to Electron's icon and crashed building the `.deb`). It stops with the path when one is missing, so a package never ships Electron's icon. `build/icons` stays generated and ignored by git, so a fresh CI checkout gets it here.
3. electron-builder with `--dir` on Windows, `--dir` and `deb` on Linux, and `--mac` on macOS (dmg and zip). The `afterPack` hook removes the Velopack bindings for other platforms, drops `dxcompiler.dll` and `dxil.dll` on Windows, and stamps the app icon and the version info on the exe with rcedit, since `signAndEditExecutable` is off: `CompanyName` from `product.author.name`, `ProductName` and `FileDescription` from `product.name` (Task Manager shows the file description), `LegalCopyright` from `product.copyright`, else `Copyright (C) <year> <author>`, `Comments` from `product.description`, the exe name, and the app version as the file and product version. The same copyright goes to electron-builder's `copyright`. The `.deb` needs a homepage and a maintainer, so the builder config sets `author` (through `extraMetadata`, `{ name, email }` from `product.author`, so the app's `package.json` need not repeat it), `homepage` (the same way) to `https://github.com/<owner>/<name>` from `product.repo`, `linux.maintainer` to `Name <email>` from `product.author` (the name alone without an email), `linux.vendor` to the author's name, `linux.synopsis` and `linux.description` to `product.description`, and `linux.category` to `product.linuxCategory` (a main freedesktop category such as `Game`, `Utility` or `Development`, checked by `defineProduct`), which the AppImage's own desktop entry carries too as `Categories`, beside `Comment` from the description; no app writes them by hand. `packaging` in `brock.config.ts` adds what the product does not say: `extraResources` (`{ from, to, filter? }`, from the app folder, after the module resources), `afterPack` (a module of the app whose default export gets the electron-builder context after Brock's own hook), `fileAssociations` (per extension of `product.fileAssociations`, a macOS `role` and an `icon` in place of the product's, which the Windows file icons follow) and `velopackIcons` (`{ windows, linux }`, the icon `vpk pack` takes in place of the app icon).
4. On Windows, `build/installer-splash.png`, the image Velopack's Setup shows while it installs. It is drawn on the ground of the boot splash: the palette's dark gradient (`gradientDarkFrom` to `gradientDarkTo` of the palette's dark set in the Tessera `tokens.json`, the same values as `--c-gradient-dark-from` and `--c-gradient-dark-to`), or for an app with colours of its own the `--look-dark-from` and `--look-dark-to` pair from `darkPair`, then a dark pair `theme.css` sets, at the look's angle. On it sit the mark in its dark ground colours (`brand/dark-ground/<brand>/mark/mark-256.png`, else the app's own mark, else `brand/dark-ground/<brand>.svg`) and the app name in the palette's dark `text`, which must hold 4.5:1 at both ends of the gradient, else white or black, whichever reads better. The name is set in the boot splash's title font, Tessera's Chakra Petch 600: resvg reads no WOFF2, so it loads the TrueType copy Tessera ships beside it (`fonts/chakra-petch/chakra-petch-latin-600-normal.ttf`) with the system fonts, by the family the file declares, `Chakra Petch SemiBold`. When the font can't be read, the name is set in Segoe UI and `brock` says so once. With `product.icons.wordmark`, the dark ground image (`public/` plus `wordmark.dark`) takes the name's place, fitted into a 384 by 48 box centred under the mark (narrower on a narrow splash), and `brock` stops when the file is missing. An SVG wordmark is rasterised on its own first, 768 pixels wide with the system fonts, because resvg draws an SVG nested in an `<image>` without fonts and would drop its text. There is no glow and no shadow behind the mark. `brock icons` draws it too for an app that ships to Windows, so it can be looked at before a release. Velopack draws its progress bar over the bottom edge in the accent.
5. `vpk pack` into `release/velopack`, with the pack id, title, author and icon from the product, `release-notes/v<version>.md` as the notes when it exists (app root, then repo root; its comment lines dropped into `release/release-notes.md`, so Velopack's `NotesMarkdown` carries the note as markdown), and `product.updateChannel` or `--channel` as the channel. On Windows it also passes the Setup splash, the accent as the progress colour, `--shortcuts` from `product.installer.shortcuts` and `--instLicense` from `product.installer.licence`. A routine release is the update package and the delta only; `--full` adds the Velopack setup as `<prefix>windows-payload.exe` and the portable build as `<prefix>windows-directory.zip`. Linux gets `<prefix>linux.AppImage`.
6. On Windows, with `product.repo` set, the small installer: `installer-stub/` (C++ and Win32, about 600 KB) compiled with the Visual Studio C++ tools after `product.h` is written from the config, saved as `<prefix>windows-setup.exe`. It is built on every release, so `releases/latest/download/<prefix>windows-setup.exe` always resolves.
7. `install.json`, the recipe the stub reads from `releases/latest/download/install.json`: the stub generation, the version, and the URL and SHA-256 of the stub, the payload (run with `--silent`) and the directory zip. An entry this release does not carry is taken from the previous manifest, so a routine release still points at the last full one; the first release has to be `--full`.

### The installer template

The installer is two programs: the small downloader window and Velopack's Setup. Brock builds both for every app from config alone, so a new app ships the full installer with no files of its own.

The downloader reads everything from `product.h`, which `brock package` writes on each run:

- Colours: `BROCK_C_BG`, `_SURFACE`, `_HAIRLINE`, `_TEXT`, `_DIM`, `_FAINT`, `_ACCENT`, `_ON_ACCENT`, `_TRACK`, `_STAMP` and `_HEADER_INK`. They come from Tessera's resolved dark theme (`theme.dark` in the Tessera package `tokens.json`; `border` draws the outlines and `textMuted` the quiet lines when Tessera has them) and the accent from `resolveLook`. The ink on the accent is Tessera's `onPrimary` when the accent is Tessera's primary, else the most readable of `onPrimary` and `text`. The header ink is the look's `ink`, the text colour that reads on the gradient. Without `tokens.json` the stub keeps its built-in warm dark colours and `brock package` says so once.
- The look: `BROCK_LOOK_FROM`, `_VIA`, `_TO` and `_ANGLE`, the same gradient the splash uses. A GDI+ `LinearGradientBrush` paints it across the top of the window, and a veil fades it into the background by the first line of text, so no label sits on the gradient.
- The mark, without its tile: Tessera's `brand/<brand>/mark/mark-256.png` (`brand/<rim>-rim/<brand>/mark/mark-256.png` with `icons.rim`) when the app keeps the default `product.logos.mark`, else `public/logos/mark.svg` (or the mark the app names) or the Tessera brand SVG from the same tree, rasterised to 256 px with resvg. It is embedded as a resource. The exe and the shortcuts keep the tiled icon.
- `product.installer`: `scope` (`user` by default, `machine` makes the main button install for everyone with elevation), `shortcuts` (`desktop` and `startMenu`, both on), `launchAfterInstall` (on; off shows a done screen with Start and Close), `licence` (a `.md` or `.txt` file; the stub shows a licence screen before any install and the text goes to vpk) and `folderName` (the product name; the folder a chosen install goes into).
- The name, the description as the welcome line, the pack id and the main exe, as before.

Layout numbers stay in the C++ sources. An app that wants more than config can put `build/installer/header.png` (replaces the rendered mark) or `build/installer/splash.png` (replaces the Setup splash). `brock structure` rejects any other file in that folder.

`brock package --render-installer` builds the stub and writes its screens to `release/installer-preview/` without installing anything: `checking`, `welcome`, `licence` (with a licence), `location`, `location-portable`, `progress`, `done`, `error` and `handoff`, at twice the size. It also writes `mark.png` and `setup-splash.png`. The stub's own `--render-png=<file> --screen=<name> [--scale=<n>]` mode does the drawing. Without the Visual Studio C++ tools it still writes the two images and exits 1.

### Platforms

`targets` in `brock.config.ts` lists platform ids (`windows`, `macos`, `linux`, `android`, `web`; `ios` is reserved and choosing it says it is not supported yet) and bundles (`desktop` is Windows, macOS and Linux; `mobile` is Android today and gains iOS later with no config change). Brock expands them. Each platform is a Strategy in `packages/build/src/platforms/<id>/` built with `definePlatform`: `doctor` checks this machine (Node 24 and pnpm for every app; .NET 8, vpk and the MSVC tools for Windows; .NET 8 and vpk for Linux, plus libusb and pkg-config when the input module is there; Xcode tools for macOS; JDK 21, `ANDROID_HOME` and the SDK packages for Android, plus the NDK and CMake when the input module is there) and prints the install command for what is missing, never installing it. `scaffold` sets the platform up, one step per file. `ciJob` and `releaseJob` are the platform's jobs in the two workflows, and `secrets` lists what the release job reads. `create-brock` asks for the platforms (`--platforms a,b` without a terminal), and `<app> platform add | remove | list` changes them later through the same strategies. `<app> doctor [platform]` runs the checks alone.

- Android back gesture: the scaffold step `Back gesture edge in MainActivity` (after `cap add android`, and on a later `platform add android`) replaces Capacitor's empty `MainActivity` with one whose `OnBackPressedCallback` reads the swipe edge (`BackEventCompat`) and dispatches `brock:back` to the WebView, and sets `android:enableOnBackInvokedCallback` in the manifest so Android 14 reports the edge. An activity with code of its own is left alone and the step says to add the dispatch by hand.
- Android: `capacitor.config.json` at the app root (managed: `appId` from the product as a valid Java package, `appName`, `webDir: dist/web`, `android.path: mobile/android`; there is no `.ts` config, and `platform add android` fails while a `capacitor.config.ts` or `.js` that Capacitor would read first sits beside it, see [upgrading-an-app.md](upgrading-an-app.md), Android), `cap add android`, the launcher icons and splash from the brand set through `@capacitor/assets`, and `mobile/android/app/build.gradle` patched to sign from `BROCK_KEYSTORE_*` and to read `versionCode` and `versionName` from `package.json`. The modules in `modules` that ship an Android side (input, display) reach the Gradle project through `cap sync` and `cap update`: `cap add android` wires them on the first scaffold, a later `platform add android` runs `cap update android` when `capacitor.settings.gradle` lacks one, and `mobile build` syncs on every build. A built-in module that is installed but not in `modules` stays out: `capacitor.config.json` then carries `android.includePlugins`, every package the app declares but those. `<app> mobile build [--release]` builds the APK beside the debug `mobile push`; `<app> mobile keystore` makes the release keystore with `keytool` once you agree and prints the `gh secret set` lines for `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_ALIAS`.
- Web: the managed `vite.web.config.ts` builds the renderer alone with a relative base into `dist/web` and writes a web app manifest from the product (`web: { manifest: false }` drops it). The release carries it as a zip; there is no deploy job.
- Linux: `build/linux/deb-postinst.sh` (managed) installs each module's `udevRules` (the input module's controller rules) and runs the app's own `build/linux/after-install.sh`; electron-builder runs it after `dpkg -i`.
- Linux test VM: `<app> linux push` sits beside `mobile push`. It builds the AppImage in a VirtualBox VM (or in WSL), installs its desktop entry and launches it on the VM's desktop; `<app> linux doctor` checks the ssh client, VirtualBox, the VM, key-only SSH access, the Guest Additions and the build tools (in WSL too when it builds there). The VM name and its address live per machine in `~/.brock/linux/<repo>.json`, never a password: every call is key-only (`BatchMode=yes`). The details are in `packages/thread/README.md`, Linux push.

### Workflows

Both workflows are managed files: `brock sync` composes them from the chosen platforms, and `brock check` fails when they drift. A standalone app gets them at its root. In a repo with `brock.workspace.mjs` they sit at the repo root with `APP_DIR` set to the app's folder, so `brock sync` and `brock check` from the app or the repo root keep them; a pnpm workspace without `brock.workspace.mjs` (Brock's own repo) gets none. A workspace with one Brock app (alone, or with its sites and functions beside it) keeps the plain `ci.yml` and `release.yml`, tags `v<version>` and notes in `release-notes/` at the repo root. A workspace with several Brock apps gives each app its own `ci-<app>.yml` and `release-<app>.yml` (`<app>` is its folder name), tags `<releaseTagPrefix><version>` and notes in `<app folder>/release-notes/`, and the first app also writes `ci.yml` with one `workspace` job for the checks that cover the repo (`brock check`, lint, markdown, structure, tests). There each app must set `product.releaseTagPrefix` (`'desktop-v'`), which the updater reads to keep to its own releases; `brock sync` stops with the line to add while one is missing. Each `ci-<app>.yml` opens with a `changes` job that runs `brock affected <app folder> origin/<base>`: true when the pull request touches the app's own files, a workspace package it depends on (through its `dependencies`, `devDependencies` or `peerDependencies`), or a file outside every package; the app's jobs run only then, and always from the Actions tab. Deploy workflows for sites and functions are a separate decision; they would sit beside these as `deploy-<target>.yml` and reuse `brock affected`. `ci.yml` runs on pull requests, on a push to the default branch (`base` of `brock.workspace.mjs`, else `main`), since a release commits its version there and release notes land there straight, and from the Actions tab; a newer run cancels an older one of the same pull request only, never a run on the default branch. It has a `quality` job (install, `brock build` in the app, then at the repo root `brock check`, the release note check and `brock gate` in the app, lint and typecheck, markdown, structure, tests) and a `review` job. Every Linux job of the managed workflows (`changes`, `quality`, `review`, `web`, the workspace and site CI jobs, `prepare`, `build-linux`, which builds the `.deb` and the AppImage, `build-android`, `build-web` and `release`) runs on `ubuntu-24.04`, never `ubuntu-latest` (which moves to Ubuntu 26 from 19 October 2026): the review's apparmor step, the linux screenshot baselines and the Linux packages depend on the image, so the image changes only with a Brock release that moves them all. It runs `<app> launch main none --prod --review` under xvfb and keeps the report from `.user-data/Data/review/` at the repo root, where `launch` writes its data whatever folder the app is in (its captures held to the `linux` screenshot baselines when `review.baselines` is on, see Screenshot baselines), then each platform's CI job (`web` builds the web app). A module's manifest `ci` steps run before the install on the runners whose `os` matches (see App steps below). `brock adopt` writes `release.yml` once for a repo with `apps/<app>`; the next `brock sync` takes it over. `brock release [version] [--latest | --prerelease] [--full] [--app <name>]` checks the note, then dispatches it; `--app` picks `release-<name>.yml` and the notes of `apps/<name>`.

`release.yml` runs on `workflow_dispatch` with `version`, `full`, `prerelease` and `set_latest`:

- `prepare` refuses `prerelease` with `set_latest`, a missing `release-notes/v<version>.md` and an existing tag, then installs, runs `brock release-notes check <tag>` in the app and the root `lint`. It tags nothing and pushes nothing: it outputs the commit it checked (`sha`), and every build job checks that commit out and sets the version in the app's `package.json` itself. It outputs `full`: the input, or on by itself while the repo has no latest release (`gh api repos/<repo>/releases/latest` fails), because the small installer reads its payload from the latest release's `install.json` and a first release has nothing to carry forward. That holds for a first pre-release too.
- One build job per platform: `build-windows`, `build-macos` and `build-linux` run `brock package` (`--full` from `prepare`), Windows and Linux after `vpk download` fetched the latest release for the delta (nothing to fetch on a first release, which is not an error); `build-android` signs the APK from the secrets; `build-web` zips `dist/web`.
- `release` runs only once every build succeeded. It commits the version bump to the app's `package.json` on the built commit, tags it, pushes the tag and moves the default branch (`base` of `brock.workspace.mjs`, else `main`, not GitHub's default branch, so a repo that releases from an integration branch moves that branch) to it (when the branch moved during the builds, the bump is put on top of it instead), then writes the body: the note without its comment lines, then `## Downloads` with every platform's files, and creates the GitHub release named after the note's title with every artifact attached. `set_latest` publishes it as the latest. `prerelease` publishes it as a pre-release, so its files download at once and it never becomes the latest. Neither leaves a draft.

The Windows download on a stable release is the small installer through `releases/latest/download`, so the link always gives the current one. The small installer always installs what `install.json` on the latest release names, the latest stable version, so a pre-release links its own Velopack setup (`<prefix>windows-payload.exe`) when it was built full, and otherwise keeps the small installer with a line saying it installs the latest stable release.

A pre-release and the updater: the GitHub release is marked a pre-release, and `brock-updater` reads releases from the GitHub API with pre-releases only when the user turned on "Include pre-releases" (`updater/prefs.json`, off by default). Users who left it off are never offered a pre-release, whatever the channel; the channel (`win`, `linux`, `osx`, or `product.updateChannel`) is the same for both. The pre-release feed lists the latest stable release and itself, since `vpk download` fetches the latest stable release. Each release's feed is only a snapshot of what existed when it was packed, so a later stable hotfix's feed leaves out an earlier pre-release: the version list reads every listed release's own feed and keeps only that release's entries, and a check offers the first version of that list newer than the installed one, so the check, the badge and the install target agree. Velopack's own check looks at one GitHub release and is not used for it.

Two apps of one repo that both update themselves on Windows would also share `releases/latest` (the small installer's `install.json`) and the Velopack feed names; Brock does not split those yet, so a workspace with several self-updating desktop apps is an open decision.

#### App steps

An app adds its own steps to the managed workflows in `brock.config.ts`, so `brock sync`, `brock build` and `platform add` keep them instead of overwriting a hand edit:

```ts
workflows: {
  steps: {
    ci: {
      beforeInstall: [{ name: 'Set up the toolchain', uses: 'owner/setup-toolchain@v3', with: { version: '4.0.10' } }],
      beforeBuild: [{ name: 'Build the core', run: 'pnpm run core:build' }],
      beforeTest: [{ name: 'Fetch the test data', run: 'pnpm run data:fetch', secrets: ['DATA_TOKEN'] }],
    },
    release: {
      beforePackage: [{ name: 'Build the addon', run: 'pnpm run addon:build', os: 'windows' }],
      afterPackage: [{ name: 'Ship the data file', run: 'cp "$APP_DIR/out/data.bin" upload/', platforms: ['windows', 'linux'] }],
    },
  },
},
```

| Point | Where it runs |
|---|---|
| `ci.beforeInstall` | every job of the CI workflow, after the checkout and the module steps, before pnpm and the install |
| `ci.beforeBuild` | `quality`, `review` and the `web` job, after the install, before the build |
| `ci.afterBuild` | the same jobs, after the build |
| `ci.beforeTest` | `quality` only, after the build, before its checks (release note, gate, lint, tests) |
| `release.beforeInstall` | `prepare` and every build job, before pnpm and the install |
| `release.beforePackage` | each build job before it packs: after the Velopack setup and the delta fetch on the desktop, before the APK or the web build |
| `release.afterPackage` | each build job after it collects its files into `upload/`, before the upload: a file copied into `upload/` ships with the release |

A step takes `name` and either `run` (with `shell` if it needs one) or `uses` (with `with`), and `env`, `if`, `secrets`, `os` and `platforms`. `secrets` names the repository secrets it reads; each becomes an environment variable of the step with the same name (`DATA_TOKEN: ${{ secrets.DATA_TOKEN }}`). GitHub gives a pull request from a fork no secrets, so a step that needs one should check for it. `os` (`windows`, `linux`, `macos`, one or a list) keeps the step to those runners; `platforms` keeps it to the jobs of those platforms (the release build jobs and the `web` CI job), so a step with `platforms` never runs in `quality`, `review` or `prepare`. `$APP_DIR` is the app folder from the repo root. Each step point runs the steps of the modules (`brock.workflows` of their manifest, the same shape), then those of the repo command's plugins (`definePlugin({ workflows })`, which `brock sync` loads as the repo command does), then the app's; a module's manifest `ci` steps stay the steps before the install of every job. A `uses` step of the same action, version and inputs runs once per job, whichever sources declare it. `brock sync` checks every step and names the source and the step of a mistake.

In a repo of several apps the workspace `ci.yml` is shared: its `workspace` job runs the plugins' `ci.beforeInstall` and `ci.beforeTest` steps once, then those of every app (its modules' and its own) in the order the workspace lists the apps, each named `<app>: <step>`, and a shell step runs with `working-directory` and `APP_DIR` set to its app. The module `ci` steps of every app run there once each. Each app's own `ci-<app>.yml` and `release-<app>.yml` carry its steps unnamed, as a single app's files do.

An app that has to own a workflow whole sets `workflows: { ci: 'own' }` or `{ release: 'own' }`: `brock sync` then never writes that file and `brock check` never compares it (the default is `'managed'`). In a repo of several apps that setting covers the app's own files only; the shared `ci.yml` follows `workflows: { ci: 'own' }` in `brock.workspace.mjs` (a `release` key there is checked the same way; no release workflow is shared today). In a repo of one app its `ci.yml` and `release.yml` are its own files and follow its own setting. An owned workflow gives up every later Brock fix to it: new action majors, the review runner pin, the release order of builds, tags and notes, the Velopack delta fetch and the small installer, so it is for a workflow the app steps cannot express, and the app follows the changelog by hand.

The release side needs no app step for Velopack: each Windows and Linux build job installs `vpk` at the version of the app's `velopack` package and runs `vpk download github` before it packs, so the release carries a delta from the latest release, and `brock package` builds the small installer on every Windows release. Both read the latest GitHub release whatever branch the run is on, so a repo that releases from its `base` branch gets the same deltas.

The setup steps install pnpm with `pnpm/action-setup` and no `version`: the version is `packageManager` in the root `package.json` (`pnpm@<version>`), since naming it in both places fails the step. `brock adopt` and `create-brock` write `packageManager` from the pnpm in use, the `pnpm-package-manager` migration (0.37.0) adds it to an existing repo, and `brock check` fails while it is missing. The actions are on their Node 24 majors: `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`, `actions/setup-java@v6`, `actions/setup-dotnet@v6`, `pnpm/action-setup@v6`, `android-actions/setup-android@v4` and `softprops/action-gh-release@v3`; their inputs did not change for these workflows.

The workflows sit under `.github/`, which the `.*/` rule of the standard `.gitignore` hides, so a commit would leave them out. `brock adopt` and `brock sync` keep `!.github/` right after the rule that hides it in the repo's `.gitignore` (sync reports the file as drifted in check mode), the `workflows-tracked` migration (0.37.0) adds it to an existing repo, and `brock check` fails while git ignores a managed workflow it does not track, naming `git check-ignore -v` to find the rule.

The workflows install the `@drizztdourden08` packages from GitHub Packages with `secrets.PACKAGES_TOKEN`, else the workflow's own `GITHUB_TOKEN` (`packages: read`). The Brock, Tessera and standards packages are public, which the workflow token can read from any repo, so an app repo needs no secret. If they ever turn private, either give the app repo read access in each package's settings (Manage Actions access) or add a `PACKAGES_TOKEN` secret holding a classic token with `read:packages`.

### Release notes

Every release of every repo of the family has a release note, in one standard that `@drizztdourden08/standards` defines and checks (`docs/release-notes.md` there), so it binds Brock, its apps, Tessera and standards alike:

- `release-notes/v<version>.md` at the repo root, one per version, pre-releases included (`v0.9.0-beta.1.md`).
- The first line is `# <Product> v<version>`, the version the file's. For a Brock app the product is `product.name`.
- A one-paragraph summary, then `##` sections from New, Changes, View, Settings, Around the app, Platforms, Under the hood, Upgrading and Fixes (each once, Fixes last), plus the sections a repo adds with `options.releaseNotes.sections` in `standards.config.mjs` or an extension's `releaseNotes` facet. `Downloads` is reserved for the workflow.
- Dash bullets, one level deep, each a sentence for users: a capital to open, a period to close, no commit hash, no `#123`, no `feat:` prefix, no changelog heading, no raw HTML, and the writing gate with the repo's words. Comment lines may sit above the title; they never reach a release body or the updater.

`brock release-notes check [version]` runs it for an app, from the app or the repo root: with a version, that note must exist and pass; without one, the app's own version once the repo has any note at or below it. `ci.yml` runs it without a version, `release.yml` with the version being released, and `brock release` before it dispatches. The checker is the one of `@drizztdourden08/standards/release-notes` (standards ^0.8.0): `brock-thread` re-exports its `checkReleaseNote`, and `checkNoteFile` runs its `checkRepoNotes` with the version named, so that note must exist and pass, and so must every newer note.

Libraries released with changesets follow the same standard through the reusable `release.yml` of standards: with the release note command installed, the version pull request carries a draft `release-notes/v<version>.md` written from the changelogs, the run after the merge refuses to publish while it is still a draft or malformed, and the GitHub release `v<version>` takes the note as its body in place of one changeset release per package. Brock's own `release.yml` passes `release-notes: pnpm exec standards release-notes` to it, so a `v0` tag of standards older than 0.8.0 fails the run in place of falling back to one release per package. Brock's packages share one version, so there is one note per Brock version, `release-notes/v<version>.md` at the repo root, titled `# Brock v<version>` after the root package name; `pnpm release-notes current` prints the version and `pnpm release-notes check` runs the check locally. The steps for whoever releases Brock are in the README, Releasing Brock.

The updater shows the note of the chosen version (Velopack's `NotesMarkdown`, else the GitHub release body) in `ReleaseNotesPanel` with `markdown` on. The panel draws it with Tessera's `Markdown` composite (Tessera 0.28), `<Markdown size="sm" headingOffset={2} hideTitle onLink={onOpenLink}>`: the `#` title is left out since the panel names the notes, the `##` sections are h4 under the panel's h3 title, raw HTML and comment lines are dropped, and a link calls `onOpenLink`, `openExternal` unless the app gives its own, which opens it in the system browser through the main process allow list. The update dialog passes `openExternal`.

moves the app's edge and the other widget's; a widget snapped onto the app forms a cluster, dragging it moves the app by the same amount and dragging the app back takes it along; cluster maximize scales the app and a widget into the work area, every member inside it, and restore puts them back, on the real work area and on a simulated 1024x720 one; cluster full screen opens the black backdrop and squares every member, and leaving it removes both; a Ctrl move takes the widget out of the cluster alone; the guide is drawn in the widget window being moved, beside the pointer the probe passes, and not in the app, turns snapping off with Ctrl while resizing, moves to the app when the app moves and hides after; `review:captureGroup` composes the windows and the backdrop into one capture for the grid and the full screen group), and each hero home rendering the Hero composite with its title and slots (and no art when it sets `<Art kind="none" />`), then every guided tour run end to end with a capture per step (see Tours by convention). The app's own content is toured too: the files under `src/review/fixtures/` are copied into the app data folder at the same paths, then `src/review/seed.ts` runs, both as the `seed` step right after the profile step and before the menu, so the screens and widgets that follow are captured with data, and each `src/review/<id>.step.ts` runs as step `<id>` after the built-in steps, with the same click, capture and check helpers, into the same report ([review-steps.md](review-steps.md)). The boot step checks that the app window holds no loading overlay. Main adds the global checks: the tour finished, the splash window closed before the first capture, the app window stayed hidden until the last boot task, the app version is not the Electron version, no renderer console errors, no failed loads, no main log errors, and a resolved window icon.

Main writes `Data/review/<name>/report.json` and `report.md` with the steps and their screenshots (`NN-<step>.png`), every check with pass or fail and a reason, and the console errors, failed loads and main log warnings seen during the run. It prints the `report.json` path and exits 0 when every check passes, 1 otherwise. Main starts the watchdog at launch: when no tour progress (a capture or a check) arrives within 60 s, for example because the renderer failed to load, or the tour later makes no progress for 30 s, a partial report is written and the process exits 1; the first case adds a failed `tour-started` check. Main exits 5 s after the report even when something holds the quit. The tour code is its own chunk, loaded only on a review launch.

### Screenshot baselines

The review can hold every capture to a stored image, so a change that moves a pixel fails it. `--review-bless` stores the run's captures as the baselines; `--review-baselines` compares the captures with them. Both only act beside `--review`: `<app> launch main none --review --review-bless`, then `<app> launch main none --review --review-baselines`.

- **Where they live.** In the app repo, committed: `tests/baselines/<platform>/<capture>.png`, one set per platform (`windows`, `macos`, `linux`), with the optional rules in `tests/baselines/baselines.json`. `--review-baselines=<dir>` (or `--review-bless=<dir>`) names another folder, relative to the folder the app is launched from (the app root for `launch` and `start`). A capture is named after its step without the number, `screen-settings.png` for `05-screen-settings.png`, so adding a step does not rename the rest; a step name that comes back gets `--2`, `--3`.
- **Bless.** Copies each capture into the set for this platform and removes the baselines the run no longer captured, when the tour finished. It refuses while any other check of the run failed (the tour stopping counts): it writes nothing, and the `baselines` check fails and names each failed check, as `<id> (<step>)`, in both reports. `--review-bless --force` blesses anyway. On success the `baselines` check says what was written and removed.
- **Compare.** Each capture is decoded and compared pixel by pixel with its baseline. Any differing pixel fails, unless a rule allows it. A failure is one `baseline` check on the step that took the capture, with the count, the share of the compared pixels and a diff image at `diffs/<NN-step>.png` in the report folder: unchanged pixels faded to grey, differing ones red, masked ones blue. A capture with no baseline, a size that changed and a baseline no capture used (when the tour finished) fail too. `report.json` carries every result under `baselines` (`match`, `differs`, `size`, `missing`, `unused`), `report.md` lists the failures in a Baselines section, and the summary `baselines` check fails when anything failed or nothing was compared.
- **Rules.** `baselines.json` holds `tolerance` (the share of the compared pixels allowed to differ, 0 to 1, default 0), `threshold` (the largest channel difference still counted as equal, 0 to 255, default 0) and `masks`, for every capture, and the same three per capture under `captures.<name>`. A mask is a rectangle in capture pixels, `{ "x", "y", "width", "height" }`, or `{ "selector": "<css>" }`, measured in the captured window just before the capture. Any element with `data-review-mask` is always masked (`REVIEW_MASK` from `@drizztdourden08/brock-core/review` spreads it in JSX): the clock, a live chart, a value that changes by itself. Brock marks the text it writes that changes on every run: the performance widget's tiles, gauges, activity and details, the profiles' last-used time, the job dialog's line, and (by selector, since the title bar draws a plain string) the job status in the title bar; it also masks the sizes and the path on the Storage page and the time column of the logs widget. The logs one reads Tessera's class `.log-panel__gutter`; drop it once Brock moves to the Tessera release that sets `data-review-mask` on LogPanel time cells itself.

```json
{
  "masks": [{ "selector": ".session-clock" }],
  "captures": {
    "screen-dashboard": { "tolerance": 0.001, "masks": [{ "x": 0, "y": 680, "width": 320, "height": 40 }] }
  }
}
```

A baseline run pins what it can so the same code draws the same pixels: the window opens at the product's default size with no saved geometry, at a device scale of 1, with hardware acceleration off and WebGL on SwiftShader, one raster thread, no LCD text, the sRGB colour profile, reduced motion (Tessera's motion and the mascot respect it) and no text caret. Before each capture main finishes every running CSS animation and transition, holds infinite ones at their first frame, waits two frames, and captures until two captures in a row are equal (up to 8 tries); a capture that never settled says so in its failure. A group capture of several windows hides the masked elements instead, since its windows are scaled into one image. A worktree's instance name and logo are left out of the drawing, so a set blessed on the main checkout holds in a worktree. `launch` gives a baseline run an emptied data folder beside the usual one, `.user-data-review`, every time, so a first run and the next one start the same; `brock start` takes whatever `--user-data` it is given.

What still differs between machines, and why there is one set per platform:

- **Fonts.** Tessera's fonts are bundled, but each OS rasterises them differently (DirectWrite, CoreText, FreeType), and a glyph none of them carries falls back to a system font. Linux also depends on the FreeType and fontconfig versions of the image.
- **GPU.** Hardware acceleration is off for baseline runs, so the GPU and its driver do not take part; Skia draws on the CPU the same way on any machine of one OS.
- **DPI.** The device scale is forced to 1, so a 150% display captures the same pixels as a 100% one. Cluster maximize and full screen lay out on a fixed 1920 by 1080 area in a baseline run, not the real display, so the group captures have the same geometry on every machine.
- **CI.** The `linux` set should come from the CI runner, not a desktop Linux: blessed on the same image (`ubuntu-24.04`), with the same 1920x1080 24-bit xvfb screen. A runner image update can change font rendering; bless again then. The `windows` and `macos` sets come from a developer machine of that OS and only hold where it is set up the same way.

Two captures of a fresh app moved between runs on Windows. `cluster-fullscreen` differs by a few hundred pixels at most, each channel by 1 to 6, only at the SVG icons and the `icon-glow` drop shadow of the main window: Chromium rasterises them a little differently after the full screen resize. The layout is the same in every run, to 1/32 px, a forced full repaint before the capture does not change it, and the same window at its launch size captures the same every time. Brock therefore ships one built-in rule, for that capture only: `threshold` 8 and `tolerance` 0, so every pixel must stay within 8 per channel and a real change still fails. An app's `captures.cluster-fullscreen` in `baselines.json` overrides it field by field (`{ "threshold": 0 }` tightens it back); the app's global `tolerance` and `threshold` do not. `tour-welcome-04-settings` (the template's tour) moved because Tessera's GuidedTour measured its target before a font loaded; Tessera's next release measures again when the fonts are ready, on resize and after each step.

With `review: { baselines: true }` in `brock.config.ts`, `brock sync` writes the CI review job for it: on `ubuntu-24.04`, under `xvfb-run -s "-screen 0 1920x1080x24"`, with `--review-baselines`, and the report upload reads `.user-data-review`. Running CI from the Actions tab with the `bless` input checked runs the review with `--review-bless` instead and uploads `tests/baselines/linux` as the `review-baselines` artifact, to commit into the repo. In a workspace with several apps the option is per app: each app that sets it gets the job in its own `ci-<app>.yml`, with the `bless` input there and the artifact `review-baselines-<app>`, from `<app folder>/tests/baselines/linux`; a manual run always runs the app's jobs, whatever `brock affected` says. `launch` reviews the target whose app folder holds the folder it runs from, so `pnpm --dir <app folder> exec brock launch main none --review` reviews that app; from the repo root it takes the first target, or `--target`.

App-specific end-to-end tests use `launchAppForTest` from `@drizztdourden08/brock-build/testing`. A flow the review can drive belongs in a review step, so it lands in the one report; this helper is for what needs Playwright, such as a second launch or the file system after quit. It checks `dist/electron/main.js` first and refuses, with the list, when the built main imports a package or a file Node cannot find. The check tokenizes each built file and reads `import`, `export ... from`, `import()` and `require()` from the code only, so a specifier inside a string, template text, a comment or a regular expression (a workflow template bundled into main, say) does not count. It then starts the built app with Playwright's `_electron`, `--no-focus --muted` and a fresh temporary `--user-data`, waits for the window that loads the renderer index (never `splash.html` or a widget window) and for the splash to close, which happens once every boot task resolved and the app window is revealed, and returns that window as `page` in `{ app, page, userData, close }`; `close()` quits the app and removes the folder. `userData` starts the app on a profile of its own instead (a folder with the test's fixtures), which `close()` leaves in place. `waitForAppPage(app, timeoutMs?)` is the same wait for a test that launches the app itself, and `pageKindOf(url)` tells `splash`, `widget` and `app` windows apart, so a test never takes the splash from `firstWindow()`. Playwright is an optional peer: the app adds `playwright-core` as a dev dependency when it writes such tests. `readDockLayout(page)` returns the widget layout from brock-react's layout store (`layout`, the `docked`, `floating` and `popped` ids, the main view's own rect and each drawn widget's rect, both in window terms; `main` is the main view's leaf of the dock laid out at rest, without the panes beside it that do not make room, offset by the dock's place in the window) through a reader the renderer installs on automation launches only, and `widgetWindows(app)` returns every popped widget window from main with its id, bounds, visibility, focus, minimized and always-on-top state. Neither reads Tessera's class names.

An app lists its kept end-to-end tests, with the rest of its kept tests, in `tests/COVERAGE.md`, and writes the hand-run cases for its launch verbs in `tests/launch-suite.md` ([launch-suite.md](launch-suite.md)).

## What Brock gives an app

- The shell: title bar, menu, profiles, settings hub, About, search palette, bug report, toasts, the widget dock with its pop-out windows, the logs widget and the performance widget, and guided tours presented by the brand mascot.
- The updater module, with the title bar update action and the update dialog, which shows each version's release note.
- The release note standard: `release-notes/v<version>.md`, `brock release-notes check`, and the managed `ci.yml` and `release.yml` that check it, publish it as the release body and pack it for the updater, for a standalone app and every app of a Brock workspace.
- The automated review, `--review`, with a report and screenshots, and screenshot baselines to bless and compare.
- A port block per app and per thread worktree, with `strictPort` (see Ports).
- Sites on request: `brock site add` for a Tessera web app beside the desktop app, on the same port block, with its own CI (see Sites).
- `brock check` and `brock sync` at an app root or a workspace root.
- `brock adopt` for a repo: lint configs, knip entries (`brock.workspace.mjs`, `brock-thread` ignored when linked), `.gitignore` lines for the dot-folder rule (`.*/` plus a `!` line per tracked dot-folder) and every generated output (`build/icons`, `build/splash`, `build/installer-splash.png`, the generated `public/logos` files, `.brock/profile-config.json`, `.brock-port-slot`), and the repo command. It writes no splash or logo markup and names any app page that carries a hand-written one.
- `launchAppForTest`, `waitForAppPage`, `pageKindOf`, `readDockLayout` and `widgetWindows` for app-specific e2e tests.
- `confirmAction`, `useNow`, `useCopyText`, `useKeyedGuard` in brock-react, `redactSecrets` in brock-core, and `lanAddresses()` with the `network:lanAddresses` channel in brock-electron.
- The Storage page, the data domain file API (`ctx.storage`, `dataDomain`), the zip and folder export and import of chosen domains, long jobs with `ctx.job`, `JobDialog` and the title bar job status, app title bar items, settings row actions, `confirmDelete` and the main-side `openExternal`.

## Acceptance for a blank app

1. `pnpm create @drizztdourden08/brock my-app --local X:\brock --yes` writes the skeleton with `link:` dependency specs into the checkout, a `pnpm-workspace.yaml` holding the catalog of the versions the template uses, and `.npmrc`.
2. `pnpm install`, `pnpm lint` (tsc + eslint + stylelint) green.
3. `pnpm build` produces `dist/`.
4. `pnpm brock start -- --no-focus --muted --user-data=<tmp>` boots, writes `<tmp>/Data/app.json` and `profiles/`, and exits on `--screenshot=boot` or a timeout.
5. The owner launches it visibly from a handed-over command and sees the profiles screen, creates a profile, opens settings and about.

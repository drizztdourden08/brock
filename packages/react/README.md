# @drizztdourden08/brock-react

The renderer layer of Brock: `BrockApp`, the platform provider and its hosts, the stores kit, the screen registry, the settings engine and the shell views. Everything in JSX is a Tessera primitive or composite; every stylesheet takes its values from Tessera tokens.

## Using it

```tsx
import '@drizztdourden08/tessera/tokens.css';
import '../.brock/palette.css';
import './theme.css';
import { BrockApp } from '@drizztdourden08/brock-react';
import { product } from './product';
import { DEFAULT_SETTINGS } from './settings.constants';
import { rendererModules } from '../.brock/modules.renderer';
import { screenTree } from '../.brock/screens';

<BrockApp product={product} settings={{ defaults: DEFAULT_SETTINGS }} screenTree={screenTree} modules={rendererModules} />
```

`screenTree` comes from the files in `src/screens` (see Screens by convention). An app not yet converted passes `screens`, `home`, `menu` and `settings.tabs` as before.

`BrockApp` composes, outermost first: `PlatformProvider` (host factories plus module ports), the app context, the screen registry, the settings store, the module Providers, then the shell: Tessera's `WindowTitleBar` where the host has window chrome, `ScreenHost` (the home screen with the open screen over it) and `ConfirmDialog`. Nothing inside the app window shows loading: the splash window does. Built-in screens `profiles`, `settings` and `about` are registered unless the app supplies one with the same id, plus `credits` when the `credits` prop is given.

`AppShell` runs the renderer boot tasks once: `profiles` (the pinned instance profile, an unknown name fails loudly, else the only profile, else the last one used, else the `profiles` screen), `settings` (waits until the active profile's settings are hydrated), `fonts` (the `--font-sans` and `--font-title` stacks loaded), `images` (the app logo decoded, and the instance logo on an instance launch), module `bootTasks`, the `bootTasks` prop (`.brock/boot.renderer.ts`), then `first-frame`, which sets the boot phase to `painting` and resolves two frames after the shell commits. Progress goes to main on `boot:progress` with a heartbeat every second, then `boot:ready` or `boot:failed`. `defineBootTask` types a renderer task; `useBootStore` exposes the phase. A task that fills a session store runs `after: ['settings']`, since the profile hydration resets every session store before `settings` resolves; in development the boot warns in the app log when that reset wipes a filled store and names the tasks that can run before `settings`.

## Layout: menu or rail

`layout` picks where the screens are listed. The default, `menu`, keeps them in the title-bar dropdown. `rail` draws Tessera's `SideNav` in its `rail` variant down the left edge of the screen host: every registered screen, grouped by `ScreenDef.group` (ungrouped screens first, then groups in first-seen order), with its `icon` and `title`. The title bar then keeps only the window controls, the instance badge and the menu entries that are not screens. `screenGroups` gives a label per group id; a group without one shows its id. A `devOnly` screen is listed only with developer tools on and a `requiresProfile` screen is disabled until a profile is active. Picking the home screen closes the open one.

```tsx
<BrockApp
  layout="rail"
  screenGroups={[{ id: 'library', label: 'Library' }]}
  screens={[home, library]}
  home="home"
/>
```

`useRailEntries(screens, home, groups?)` is exported on its own: it returns the `SideNav` config, the active id and the select handler the rail uses.

## Screens

```ts
defineScreen({
  id, title, icon, render(ctx), layer?: 'fullscreen' | 'own', header?: 'page' | 'own' | 'none', keepMounted?, devOnly?,
  group?, shortcut?: 'Mod+Comma', requiresProfile?, subtitle?(ctx), extra?(ctx), floating?(ctx),
});
```

`ctx` carries `params`, `profile`, `open` and `close`. Every screen has an `icon` and a `title`. A fullscreen screen draws inside `ScreenLayer`, the reference frame: a card at 90% of the window over a scrim, one header with the icon, the title, `subtitle`, `extra` controls and the close button, and `floating` overhanging the top edge. Under that one header the screen's content sits straight in the window body, which scrolls and is padded, with no inner card; `header: 'own'` leaves the content to draw its own headers, as a hub does for its pages, and `header: 'none'` marks a screen with no page header at all, as About is; the review then checks that none shows. `ScreenLayer` takes `square` for a window shown fullscreen, and `BrockApp` sets it while the window's snap cluster is in full screen. It enters over 0.2 s, with no entrance while the app boots. An own screen draws its own frame. Every screen with a shortcut toggles on it. Header Back and close buttons are Tessera's standard `md` size, 39 px like a `md` Button (Tessera 0.22, MIGRATION 194), so the ScreenLayer header row is 39 px tall. The page header's Back (Tessera's `ContentHeader` in `ScreenPage`, `SettingsPage` and a hub page, so Back to Saves on a sub-page) is a `md` Button too, 39 px, or a 39 px arrow once folded (Tessera 0.23, MIGRATION 196); Brock never makes a header button `sm`. Dense rows (settings rows, list rows) keep their `sm` or `xs` buttons, widget title bar buttons are `xs`, 20 px (Tessera 0.24, MIGRATION 198), and the window title bar keeps its `sm` actions, 28 px. Since Tessera 0.24 a screen follows its own window, not the viewport: `ScreenWindow` is a `screen-window` container, so content inside a screen fits itself with `@container screen-window`, and anything there positioned against the viewport now positions against the window, so a layer that must cover the whole app renders outside the screen or in a portal.

## Hubs

`defineHub` returns a fullscreen screen, so a hub sits in the same card as every other screen: the hub title with the profile name as subtitle, the active page's tabs in the header, the section nav and the page inside. `HubDef.icon` and `HubPage.icon` are required. Each page draws under a page header with its icon and label: a settings page in Tessera's `SettingsPage`, with its section anchors, and any other page in `ScreenPage`. A page with `fullBleed: true`, such as a bucket's hero home, fills the pane itself. With two hubs or more, a hub switch overhangs the top edge of the card and moves between them. A hub home hidden by `devOnly`, `hosts` or `when` stays out of the side nav like any hidden page, and the hub still opens on it by route; with no other page shown, the home stays in the nav.

## Screens by convention

An app lists its buckets in `src/screens/screens.config.ts` with `defineScreens({ buckets, home, settings? })` and drops one file per screen under `src/screens`. `brock sync` and the dev server write `.brock/screens.ts`, which calls `buildScreenTree(config, entries)`; `BrockApp` takes the result as `screenTree`.

- A bucket folder is one hub. `<id>.hero.tsx` is its home and gets `HeroProps`: the page props plus `slots` (`Title`, `Eyebrow`, `Backdrop`, `Shade`, `Art`, `Actions`, `Tools`, `Facts`, `Aside`, `Panel`), one per slot of the Tessera `Hero` composite; `Facts` takes `rows` of `{ label, value, mono? }` facts; `Art` takes Tessera's `HeroArt`, `kind: 'image'` with `src`, `alt` and `pixelated` or `kind: 'node'` with `node` and `label`, or `kind: 'none'` for no art, and without it a branded app's hero draws the brand mascot; `Backdrop` takes Tessera's `Backdrop` (`kind: 'node'`, `'image'` or `'color'`), or `kind: 'none'` for no backdrop, and without it the hero draws the brand gradient; `Shade` takes `value`, `fade`, `scrim` or `none`; `meta.hero.size` (`'compact'`, `'default'` or `'tall'`) sets the Hero height. `<bucket>.backdrop.tsx` default-exports a component drawn behind every page header of its bucket. `<id>.page.tsx` is a page and gets `PageProps` (`params`, `profile`, `open`, `close`, `bucket`, `page`, `tab`). A folder of `<tab>.tab.tsx` files is one page with header tabs. `<id>.settings.ts` default-exports sections and becomes a settings page. A subfolder without tabs is a nav group.
- `top` on a bucket in `screens.config.ts` (or on a `defineHub` def) is a list of page ids for the top group of the hub side nav: `top: ['sessions']` puts Sessions under Home, in that order, with Tessera's single divider after the block. A page in `top` leaves its regular group, and a group left empty is not drawn. A hidden or unknown id is skipped.
- `<page>.custom.tsx` in a bucket is a custom page: the hub frame, nav entry, header, Escape and search stay standard and the content is free. It gets `PageProps` and must export `searchEntries: SearchEntrySeed[]`, a literal list the build reads.
- `header` on a bucket (or a `defineHub` def) is `{ render(ctx), actions?(ctx) }`, drawn in the hub header row in place of the profile subtitle. `ctx` is the `HubRenderContext` (hub, page, tab, sub, `params`, `open`, `close`, profile), so the header follows the open page and the route params. `actions` draws after it, in its own area on the right of the content. A hub with no `header` keeps the profile subtitle. The hub publishes its context to `useHubContextStore`, which the header reads.
- `params` on a bucket (or a `defineHub` def) is a list of route param names that stay with the hub, for example `params: ['subject', 'pin']`. Opening another page of the hub (the nav, a tab, `open('bucket/page')`, a sub-page going up, Back with no history) keeps the current value of each one the new route does not name. A route that names one sets it, and `{ subject: undefined }` clears it. They come back with Back, Forward and a restored session because the history and the saved navigation hold the full params. Leaving the hub and opening it on a page restores them from where it was left; the menu Home (`fresh`) starts clean. `HubTarget.params` lets `ctx.open` set them. `ShowContext.params` carries the sticky values of the open hub, so a `when` rule reads `ctx.params.subject`. The context is rebuilt only when a sticky value changes, so a `useMemo` on it does not run again for a plain page change.
- `nav: 'rail'` on a bucket (or a `defineHub` def) draws the hub nav as Tessera's icon-only `rail`, with no nav search, so a fill page can draw its own tree as the main left column. It shows once two pages are shown, like `'auto'`.
- `ScreensConfig.aliases` maps an old route name to its new one, `aliases: { asset: 'properties', app: 'options' }`. The alias keeps the params and deep links: `open('asset/summary')` opens `properties/summary`. `BrockApp` registers each one in `routeAliases`. `brock` throws at start when an alias has the id of a bucket or points at no bucket or screen.
- Every Brock string that names the settings bucket reads its title: the menu entry, the palette breadcrumb and the review tour say Options when the bucket is titled Options. Without a settings bucket (a plain `settings` tab list) it says Settings.
- At the root, `<id>.card.tsx` is a card screen and `<id>.layer.tsx` draws its own full-bleed layer; both get `CardProps`. A card or layer with a side nav is `export default defineWindow({ groups: [{ id, label, items: [{ id, label, icon, render }] }] })`, with `fill: true` in its `meta` so the window draws the nav and the pane under one header (see `docs/app-structure.md`, A window with a side nav). The `nav` route param opens an item, the nav folds to a bar in a narrow window, and `defineWindow` throws on an empty, repeated or unknown item. `bare: true` in a card's `meta` draws it as the Home hub window: no title row, hub padding, the corner close and lock, no switcher, movable, on the shared `HUB_WINDOW_KEY` storage key (exported). Its title and icon show in a small chip at the top left corner.
- `meta: ScreenMeta` sets `title`, `icon`, `order`, `shortcut`, `devOnly`, `requiresProfile` and `keywords`.
- `resolveScreenTree(tree, builtInTabs)` runs inside `BrockApp`: it adds the built-in and module settings tabs to the settings bucket, turns each hub into a screen with `defineHub`, derives the menu with `deriveMenu` and points the `settings` route at the settings bucket, so no separate Settings screen is registered.
- The menu reads `BucketDef.menu`: `entry` for one entry, `submenu` for one child per page, `hidden` for none. `BucketDef.switcher: false` keeps a bucket out of the top hub switcher while its menu entry, shortcut and `open('bucket/page')` still work. The home bucket is already the Home entry. `MenuItem` takes `{ bucket, page, tab }` as a target, and `open('game/tracker/map')` opens that bucket, page and tab.
- A module can bring a whole bucket: `RendererModule.buckets` is a list of `{ bucket, entries }`, the `BucketDef` and the same `BucketEntry` shapes the generated `.brock/screens.ts` holds (`page`, `live`, `tab`, `sub`, `custom`, each with its `meta`; `lazyComponent` keeps the pages lazy). `BrockApp` adds each one to the app's screen tree before `resolveScreenTree`: the bucket, its hub and its search entries. A bucket id the app already declares throws at start. An app with no `screenTree` gets the hubs as module screens, so the bucket still opens. With `menu: 'hidden'` and `switcher: false` the bucket adds no menu entry and no switcher tab; a module menu entry whose `screen` is the bucket id (for example in the Advanced section) places it.
- The hero slots come from `screens/kinds/hero-frame.constants.ts`, the one place the Tessera Hero composite plugs in. The page renders the slots it fills and the frame draws one `Hero` with them.

## Widgets by convention

An app drops one file per widget in `src/widgets`: `<id>.widget.tsx`, whose default export is the component and whose optional `meta: WidgetMeta` holds the `defineWidget` fields but `id` and `render` (`label`, `icon`, `popOut`, `devOnly`, `taskbar`, `defaultVisibility`, `defaultSide`, `defaultDockedSize`, `dockWeight` (docked widgets of an edge are sized by weight, 1 when unset), `defaultFloatingSize`) plus `settings`, a component for the options panel. `brock sync` and the dev server write `.brock/widgets.ts`, which calls `widgetsFromFiles([{ id, component, meta }])`; `BrockApp` takes the result as `widgets` and adds it to the module widgets, in the main window and in a popped widget window. A widget without `label` is named after its id in title case. `defineWidget`, `registerWidgets` and `RendererModule.widgets` still work. A widget kit (`src/widgets/<id>.kit.ts`, its widgets with `kit` in `meta`, and `<id>.overlay.tsx` overlays) opens and closes as one unit with its own saved layout; `.brock/widget-kits.ts` gives `appWidgetKits` for `BrockApp`'s `widgetKits`, and `defineWidgetKit`, `registerWidgetKits`, `RendererModule.widgetKits` and `widgetKits.open/close` cover the rest (see Widget kits in docs/architecture.md).

A widget that sets `context: 'session'` in its definition or `meta` shows only while that context is active (`contexts.set('session', { active, data, label })`, `useSetAppContext`). The optional `label` is a short string, such as the name of a session tab: every widget bound to that context shows it as a muted sublabel after the title (`Players` then `Sunday run`), docked, floating and popped, and it follows a changed label. A blank or missing label shows no sublabel.

Brock's own widgets have the same shape: `src/widgets/built-in/logs.widget.tsx` and `performance.widget.tsx` beside their component folders, listed in `built-in-widgets.constants.ts` through `widgetsFromFiles`.

## Layout presets

`src/widgets/layout.ts` default-exports `defineLayoutPreset({ rows, sizes?, widths?, revision?, onRevision? })`, the layout a profile starts from and Reset layout returns to. `rows` run top to bottom; a row is a list of cells from left to right, and a cell is a widget id, a list of ids tabbed in one pane, `'main'` (the main view), or a column.

```ts
export default defineLayoutPreset({
  revision: 2,
  rows: [
    [['network', 'room'], 'main', { column: ['players', 'hints'], sizes: [0.6, 0.4] }],
    [['log', 'console', 'spoiler']],
  ],
  sizes: [0.7, 0.3],
  widths: [[0.22, 0.56, 0.22]],
});
```

- Column: `{ column: [pane, ...], sizes? }` stacks panes top to bottom in one cell. Each member is an id or a list of ids tabbed in one pane. `sizes` are relative weights; a member without one takes the `dockWeight` of its widgets, then the average. A column left with one pane is that pane.
- Under the main view: write the row as `{ cells: [...], under: 'main' }`. It is not stacked full width. It sits under the main view only, so the cells beside the main view keep the full height. Its `sizes` entry is its share of the main view's height as a fraction (default 0.3); the main view keeps the rest, at least 0.1. Several under rows stack in order.
- Revision: `revision` is a whole number, 1 when unset. A profile stores the revision its saved layout was built from (`widgetLayoutRevision` in its views); a saved layout with none counts as revision 1. Raise `revision` when the default layout changes in a way existing profiles should get.
- A profile whose saved revision is lower than the preset's gets a toast once: "The default layout has a new version." with a Reset button. Reset puts the layout back to the preset. Closing the toast keeps the profile's layout and stores the new revision, so it does not ask again. Reset layout from the Widgets menu also stores the current revision.
- `onRevision: 'apply'` skips the toast and resets the profile to the new layout at load. The default is `'offer'`.
- A profile with no saved layout starts from the preset and stores its revision with the first save.

## Toolbars

An app registers docked toolbars with `defineToolbar` (one file per toolbar in `src/toolbars`, passed as `toolbars`). By default `BrockApp` wraps the widget host in the toolbar dock. An app that wants its toolbars around its own work area, such as a canvas page, passes `toolbarPlacement="app"` and mounts `<ToolbarHost>` where it wants them. `BrockApp` then registers the toolbars and loads the saved layout but draws no dock itself, and `ToolbarHost` draws the registered toolbars around its children.

```tsx
<BrockApp toolbars={appToolbars} toolbarPlacement="app" ... />

const CanvasPage = () => <ToolbarHost><Canvas /></ToolbarHost>;
```

Only one `ToolbarHost` draws the toolbars. A second one logs a warning once and renders only its children. A host that mounts late, inside a page, still gets the layout saved for the profile. A docked toolbar is its own F6 stop, even inside the main area.

A right click, Shift+F10 or the Menu key on a docked toolbar opens a context menu with Show labels, Move to (Top, Bottom, Left, Right) and Hide toolbar. They are the commands `toolbar.labels`, `toolbar.moveTo` and `toolbar.hide`, which take the toolbar id (and the side) as `args`, and the Toolbars menu holds the same entries for each shown toolbar. The labels flag and the side are saved in the toolbar layout. Pass `slot.labels` to Tessera's `Toolbar` as `labels` so the toggle takes effect.

## Widgets and toolbars API

`widgets` and `toolbars` are plain facades over the layout stores, for code that drives the layout without a mouse, such as an assistant over MCP. Every list is a plain snapshot, every id is checked, and an unknown id throws an `Error` that names the known ids. They add no store.

```ts
widgets.list();                                    // WidgetSnapshot[]
widgets.dock('notes', { side: 'left', size: 320, index: 0 });
widgets.float('notes', { x: 80, y: 60, width: 420, height: 300 });
widgets.resize('notes', 360);                      // docked: pixels; floating: { width, height, x?, y? }
widgets.focus('notes');                            // opens it if closed, then makes it the active tab or the top window
widgets.presets();                                 // ['default', ...registered names]
widgets.applyPreset('review');
const stop = widgets.subscribe((snapshot) => {});  // fires when a snapshot differs from the last one

toolbars.list();                                   // ToolbarSnapshot[]
toolbars.show('tools');
toolbars.hide('tools');
toolbars.moveToSide('tools', 'left', 0);           // row is optional
toolbars.labels('tools', false);
toolbars.reset();
const stopBars = toolbars.subscribe((snapshot) => {});
```

- `WidgetSnapshot`: `id`, `label`, `visible` (open in the layout), `placement` (`'docked'`, `'floating'`, `'popped'` or `null`), `side` (`'left'`, `'right'`, `'top'`, `'bottom'` or `null`), `size` (pixels across the edge, the width on the left and right, the height on the top and bottom), `index` (the pane's place among the panes on that side, first is 0), `tab` (the place inside a tabbed pane), `rect` (the floating rectangle in pixels, else `null`), `popped`, `context` and `available` (the widget shows now: its context is active, or it is always visible). `side`, `size`, `index` and `tab` are `null` unless docked.
- `dock(id, { side, size?, index? })` docks the widget, opening it if it was closed, floating or popped. `size` is in pixels across the edge. `index` puts the widget's pane before the pane at that place on the side, and a number past the end means last. `float(id, rect)` floats it; `x` and `y` are optional and default to the main area's corner. `resize(id, size | rect)` takes a number for a docked widget and a rect for a floating one, and rejects a closed or popped widget. `focus(id)` has no effect on a popped widget, which keeps its own window.
- Presets: the app's own `layout` preset is named `default`. `widgets.registerPresets({ name: defineLayoutPreset(...) })` adds named presets and returns a function that removes them. `applyPreset(name)` replaces the layout, as Reset layout does for `default`, and throws on an unknown name. `registerPresets` rejects `default`.
- `ToolbarSnapshot`: `id`, `label`, `shown`, `side`, `row` (the lane on that side), `index` (the place in the row) and `labels`; the placement fields are `null` while hidden. `show` and `moveToSide` throw when the side has no room. `moveToSide` shows a hidden toolbar first.
- These calls reach the normal layout. A widget of a widget kit is not listed, and a call naming one throws; use `widgetKits` for it. A call on a normal widget closes an open kit first, like `widgets.open`.
- `subscribe` is called with the new snapshot only when it differs from the last one sent. Widget snapshots follow the layout and the contexts; a pure window resize does not fire one.

## Performance widget

The built-in `performance` widget is the debug view for a bug report. It starts closed and sits in the Widgets menu for everyone, developer tools or not (in the Developer group of that menu while developer tools are on), and it pops out like any widget. It is built from Tessera's chart parts:

- **Tiles:** a `StatTile` each for frame rate, CPU, memory and event loop lag, with the latest value, the change since the previous sample and its trend, and a `Sparkline` of the last 60 samples (a low frame rate band, a lag band above 50 ms).
- **Gauges:** the app's CPU, its share of system memory and the JS heap against its limit, each a `Gauge` with warning and danger zones. They take the largest size that fits side by side.
- **Memory by process:** a `StackedBar` of the working set of main, the renderer, the GPU, utility processes, widget windows and anything else, with a legend and the total against system memory.
- **Activity:** long tasks since the widget opened, and the errors and warnings since start (counted by the app log bus; a popped window counts the relayed log).
- **Details:** collapsed by default (kept with `useWidgetPref`); every reading as Tessera `StatRow`s in three groups. Renderer: frame rate and average and worst frame time (`requestAnimationFrame`), long tasks and their total time (`PerformanceObserver` `longtask`), event loop lag (the worst drift of a 100 ms timer), the JS heap and its limit where `performance.memory` exists, the DOM node count. Processes, from `diagnostics:getProcesses` in main: the process count with total CPU and memory, the system memory, the main process memory and heap, uptime, the window count, IPC calls per second and in total, the Electron, Chrome and Node versions, GPU compositing, then one row per process (CPU, working set, the window it draws) and one per widget window. App: version, screen and route, profile, the open widgets, the active modules and the log counts. In a browser preview there is no main process and the Processes parts stay out.

A container query lays it out: docked (280 to 360 px) two tiles a row with the panels stacked, from 560 px four tiles a row with the gauges beside memory and activity. The widget body is Tessera's slim `ScrollArea`, so the widget adds no scroll box of its own.

The options panel (`PerformanceSettings`) sets the refresh, 0.5, 1, 2 or 5 s (1 s by default), and which sections show (Renderer, Processes, App), both kept with `useWidgetPref`. Nothing is sampled while the widget is off screen: an `IntersectionObserver` on its root and the page visibility gate the frame loop, the observers, the lag timer and the IPC poll, so a closed, tabbed-away or minimized widget costs nothing, and a hidden section is neither drawn nor sampled. Each sample is one state update, and the chart parts update their elements in place. Copy snapshot copies every reading as text, under a dated title. The review's `performance` step opens it from the Widgets menu, checks that it samples, that the four tiles, their sparklines, the CPU and memory gauges and memory by process (main and renderer at least) render, that sparklines and tiles move within 2.5 s and that the panel adds no scroll box inside the widget body, captures it docked, then pops it out and captures it narrow and wide.

## Search

The palette and every hub search read one index of `SearchEntry { id, kind, label, keywords, breadcrumb, target: { route, anchor? }, icon }`.

- `meta.keywords` find a page of any kind in search. `meta.searchRows: { label, keywords?, anchor? }[]` adds rows of the page's own: each opens the page and, with an `anchor`, scrolls to the element wrapped in `<SearchAnchor anchor="...">`. Both must be literals.
- `.brock/search.ts` calls `buildSearchIndex(config, seeds)` with seeds the build read from the screen files: buckets, pages, tabs, cards, settings sections and rows, and each custom page's `searchEntries`. It imports no screen file, so page code stays lazy. `screens.ts` hands the result to `buildScreenTree` and it reaches `BrockApp` as `screenTree.search`.
- `useSearchIndex(enabled, menu, actions)` merges it with the live sources: module screens and settings tabs, the widget registry, the menu, the registered actions and the `useSearchEntries` entries. Entries with the same id or the same target appear once, the build index first.
- `useSearchEntries(entries, route?)` adds `SearchEntrySeed` entries while the caller is mounted, pointing at the page open when it mounted (or `route`). Pass a stable list.
- `rankEntries(entries, query)` folds case and accents and needs every word to match the label, a keyword, the description, the hint or the breadcrumb. `entriesInBucket(entries, id)` keeps what one hub shows.
- `openSearchTarget(target)` opens the route through `nav.open` and scrolls to the element whose `data-setting-key`, `data-section` or `data-search-anchor` equals `anchor`, flashing it with `search-hit`.
- A generated hub has search on: SideNavLayout's results slot shows Tessera's `SearchResults`, one group per page, and a hit jumps to its page and row. Ctrl+K (Mod+K) inside an open hub focuses its search; elsewhere it opens the palette.
- The product brand's mascot (Flint for `brock`, Pelago for `archipelia`, Sentri for `rotp`) sits in the palette's input row, as Tessera's `CommandPalette` `mascot="auto"`, and in every hub search, drawn as `<AnimatedMascot brand="auto">`, which picks the mascot of the `data-palette` Brock sets on the page root from `product.icons.brand`. It runs on Tessera's mascot state machine: it scans while the field is empty; when nothing matches it cuts in with `alert` on each new query and settles into `worried` once the clip ends, blending between states with no remount. A brand without a mascot, or no brand, shows the plain search icon and no mascot.
- The same brand mascot walks along the bottom of the main app viewport while a screen window is open. It starts with a long walk toward a random side, then Tessera's autonomous stage chooses more walks and animation states. It stays mounted while screen windows change, steps beside the command palette to offer a search hint, and leaves when the window closes so the game is clear.

## Accessibility

`BrockApp` draws the title bar as a `banner` and the screen host as the one `main`, and mounts a polite and an assertive live region. F6 and Shift+F6 (commands `brock.region.next` and `brock.region.previous`, rebindable in the keymap) cycle focus through the regions: the banner, the main area, labelled `nav`, `complementary` and `region` elements, toolbars (a docked toolbar is a stop of its own even inside the main area), and any element an app marks with `focusRegion(id, label, { role? })`, whose role defaults to `region`. Focus returns to the control that had it last in the region.

```tsx
import { announce, focusRegion } from '@drizztdourden08/brock-react';

announce('Saved hero');
announce('Connection lost', { politeness: 'assertive' });

<div tabIndex={0} {...focusRegion('canvas', 'Sprite canvas')} />;
```

`announce` repeats a message reliably and ignores a blank one. The architecture guide, Accessibility, has the rules.

## Commands

Every shortcut and menu action is a `CommandDef` in one registry. Besides `id`, `label`, `chord`, `scope`, `zone` and `run`, a command can set:

- `when()`: the gate. Returning `false` turns the command off everywhere it shows (chord, menus, palette, keymap list) and `commands.run` refuses it with `why: 'gated'`. Apps use it for a profile, a mode, a dev-only switch or a missing document.
- `reason()`: why the command is unavailable right now, as a plain sentence, or `null` when it is fine. A `when` that returns `false` reports it as the reason of the refusal (a default sentence if there is none). A `reason` that returns a string while `when` allows the command makes it `disabled`: menus show it greyed out and `commands.run` refuses it with `why: 'disabled'`.
- `meta`: plain, serialisable app data (an args schema, the effect of the command). Brock never reads it; `commands.list()` hands it back as set.
- `run(context?)` may return a promise.

`commands.describe(id)` returns `{ enabled, reason, checked }` with the gates applied (an unknown id is not enabled and says so). `commands.run(id, context?)` returns `Promise<{ ok: true } | { ok: false, why: 'unknown' | 'disabled' | 'gated', reason }>` and resolves after a promise from `run` settles; the command itself starts synchronously, so a caller that ignores the result behaves as before. The context `trigger` is `'pointer'`, `'keyboard'`, `'longpress'` or `'assistant'`, the last for a command an assistant runs for the user. Scope and zone only pick which chord fires; `commands.run` does not check them.

## Context menu

`useContextMenu(id, source)` gives an element or a command zone a menu built from registered commands, and `{...contextMenuZone(id, { data?, typing?, focusable? })}` marks the element the app already renders, with no wrapper. An entry is a command id, `'separator'`, `{ command, label?, args? }`, a plain `{ label, run }`, or a sub-menu `{ label, items }`. The label, icon, shortcut (the current chord), enabled state and action come from the command, and `checked`, `hidden`, `disabled`, `reason` and `kind` can be set on the entry. The builder runs once per open and gets `{ point, target, trigger, data }`; so does `CommandDef.run(context?)` when the menu runs it. A config adds `anchor`, `shouldOpen`, `openOn`, `beforeOpen`, `label` and `inherit: 'parent'`. Right click, long press, Shift+F10 and the Menu key open it, the keys through the rebindable command `brock.context-menu`. The browser menu stays where no menu is declared, in a `data-native-menu` element and in a text field, unless the field is marked `typing: true`.

```tsx
import { commandZone, contextMenuZone, useContextMenu } from '@drizztdourden08/brock-react';

useContextMenu('canvas', { entries: () => ['canvas.copy', 'separator', { command: 'canvas.grid', checked: gridOn }] });

<div tabIndex={0} {...commandZone('canvas')} {...contextMenuZone('canvas')} />;
```

`openContextMenu(id, data)`, `listContextMenus()` and `blockContextMenus(flag)` serve tests and the app's drag state. `listContextMenus()` lists every registered menu with `mounted: boolean`, including menus whose component has unmounted; `defineContextMenu(id, source)` registers one at module scope so a test sees it before any zone mounts (it lists the menu and does not open it). An entry takes `tone: 'danger'` for a destructive action. A `reason` on an entry is also its `aria-description`, and each drawn item carries `data-menu-entry` (the command id, else the label). For a Tessera part that reports its own right click, such as `DocumentTabs` `onTabContextMenu(tabId, event)` or `StatusBar` `onItemContextMenu(itemId, event)`, `contextMenuHandler(zone, data?)` returns the handler that opens the zone with the part's data: `onTabContextMenu={(tabId, event) => contextMenuHandler('tabs', { tabId })(event)}`. The architecture guide, Context menus, has the rules.

## Escape and home

Escape closes the innermost thing. Tessera's escape stack (`useEscapeStack`) handles every surface above a screen: a drag, a popover or confirm ask, a menu or the tour, a dialog (the confirm dialog, the bug report, the shortcuts help, the update dialog) and the search palette. The shell takes Escape only while nothing above `screen` is on that stack and no control consumed the key with `preventDefault`, and then closes an open escape layer, then the open screen, going up a hub level first. With nothing open it opens the home screen, the Home menu entry's target. With a `screenTree` that is `config.home`; otherwise `product.homeScreen` names it (`settings` by default). The `homeScreen` prop overrides both. A surface the app draws registers with Tessera's `useEscapeStack({ level, onEscape, active })`; one whose state lives in a store can register with Brock's `useEscapeLayer({ isOpen, close })` or `escapeLayers.add`, closed by the shell ahead of the screen, the last one registered that reports open first. An app shortcut bound to Escape reads `useEscapeStack().depth()` and stands down while it is above 0.

## Menu

The built-in order is Home, Profiles, Settings (left out when it is home), the app entries, the sections, then the module entries, Credits, About and Quit. Every built-in entry has an icon; `icon` takes a Tessera icon name or any node. An entry with `section` goes into that submenu: `widgets` and `advanced` come first, any other id becomes a section named after it. `devOnly` entries show only with developer tools, which are on in development or when the `developerToolsEnabled` setting is true; the built-in Dev Console in Advanced is one of them. Widgets holds the `useWidgetMenuEntries()` toggles and Advanced always holds Report a bug. Toolbars is a level 1 menu right after Widgets (`useToolbarMenuEntries()`, key `toolbars`). `product.menu.home: false` leaves the Home entry out. `product.menu.profiles: false` leaves the Profiles entry out of the main menu; profiles still work through the profile switcher, the palette and the shortcuts. The search palette and the bug report dialog close on Escape through Tessera's escape stack. Credits shows when a `credits` screen exists, which the `credits` prop registers.

## Settings

A tab is `{ id, label, navIcon, group, sections(settings) | render(ctx), source?, icon?, mobileOnly?, moduleId? }`; `mergeModules` sets `moduleId` on each module tab, and a module tab whose id an app page or tab already holds moves to `moduleTabId(moduleId, id)`. Sections hold items keyed by settings key (dotted paths allowed). `SettingsHub` wires the tabs into Tessera's `SideNavLayout` and `SearchResults`; `SettingsLayout` feeds one tab's sections, with per-section reset and lock overlays, as one Tessera `SettingsSection` per section inside `SettingsPage`. The settings store hydrates per profile, patches, runs effects `(patch, next, prev)` and saves 300 ms after the last change. The `settings` prop of `BrockApp` also carries the control hooks the hub forwards to every tab: `renderControl` for non-boolean keys, `isDisabled`, `lockCauseOf` and `lockOverlay`; a tab that needs its own layout still uses `TabDef.render`.

## App shell

- `BrockApp` is the composition root: it resolves the modules once, creates the log bus, the settings store and the screen registry, installs the api shim on hosts without a bridge, then wraps the shell in the platform, settings and module providers. Module Providers nest with the first module outermost. The title bar is drawn only where the host reports the `windowChrome` capability.
- Palette: the app's entry imports `.brock/palette.css`, which `brock sync` writes with the one Tessera palette of `product.icons.brand` (`@drizztdourden08/tessera/palettes/<brand>.css`, in the `ds.palette` layer; nothing when Tessera has no palette for the brand), and `BrockApp` sets `data-palette` on the document root to `product.icons.brand`, in the main window and in every popped widget window, so the app shows its brand's colours. The shell imports no palette itself, so an app ships only its own brand's. The app's `src/theme.css` is unlayered, so any seed it sets wins; the starter's theme sets none.
- Props: `home` is the screen id drawn as the base layer once a profile is active; `homeScreen` overrides `product.homeScreen`; `titleBarMenu: { label, icon, id? }` folds the `titleBar` items into one dropdown button in the title bar, keeping each item's chord and `disabledReason`; `menu` holds the app's title-bar entries, placed as described under Menu (a built-in entry is skipped when the app or a module already names that screen); `credits` is the content of the Credits screen; `settings.effects` run on every patch and receive the patch and both states; `profileHooks` carry the app-specific profile fields and patchable keys; `dataDomains` (the list `bootstrapApp` takes) lets the Storage page sum the data folders on a phone, where there is no main process; `legalText` is the licence and attribution copy. The title bar and the about screen show `product.logos.app`, and a named instance shows `product.logos.instance`; a Tessera brand draws in the About panel as its app icon, or as its bare mark with `product.icons.rim`.
- Startup order: the pinned instance profile (matched by id, then by name; an unknown name logs an error and opens the profiles screen instead of running on the wrong data), else the only profile, else the last one used, else the profiles screen. `settled` turns true in a `finally` block so every exit path, a failed boot included, still ends with a visible window.
- The `first-frame` task waits for the shell to commit with the boot phase `painting`, then for two animation frames: the first commits the layout, the second proves it painted. The frame request is not cancelled on effect cleanup, because a strict-mode double invoke would cancel the only scheduled signal.
- Keyboard: Escape follows the order under Escape and home; F11 and Alt+Enter toggle fullscreen (a command from the app or a module with the same default chord takes Alt+Enter, and fullscreen keeps F11); a screen's shortcut toggles it, a `requiresProfile` screen waits for a profile, a `devOnly` screen only responds with developer tools on; while an input, textarea or contenteditable is focused, screen shortcuts fire only with Ctrl or Meta held. A shortcut string is tokens joined by `+` (`Mod` matches Ctrl or the platform's command key; aliases `Comma`, `Period`, `Space`, `Esc`, `Return`).
- Bug report: `BrockApp`'s `bugReport` prop (`{ transport, label? }`) sends the dialog's payload through the app; with none, the dialog asks main for its transport each time it opens, then falls back to the GitHub issue and the clipboard. `useDebugText` returns the host facts as `system` beside the text, which the payload carries.
- Links and files the OS hands the app reach `appOpen`: `BrockApp` takes what main held since launch (`app:takeOpens`) and listens on `app:open`. A request that arrives before any handler is held for the first one; `useAppOpen(handler)` subscribes for the life of a component and always calls the latest handler.
- When the active profile changes, every session store resets and the settings store loads that profile's config; with no profile the settings return to the defaults. Log entries main sends over IPC are forwarded into the renderer's log bus; an unknown channel lands on `ipc` and an unknown level reads as `info`.
- Background: `<BrockApp background={<Surround />} />` draws one node behind every panel: above the window background, below the rail, the toolbar dock, the widget host, its docked panels and the main view. The layer ignores pointer events (an element inside it sets `pointer-events: auto` if it needs them) and is hidden from assistive tech. It works with both `toolbarPlacement` values and both `layout` modes. Popped widget windows do not draw it.

## Host, log and profiles

- The preload installs `window.api` before the renderer runs; a web or mobile host has none unless the app installs the shim, so `hostApi()` returns null instead of throwing at module load, and `requireHostApi()` is for call sites that only run on a host with a bridge. Both take the app's own maps as a type argument and add their methods to the base ones, so an app reaches its channels without a cast: `hostApi<{ invoke: typeof APP_INVOKE_MAP; events: typeof APP_EVENT_MAP }>()`. Without one they return the base `IpcApi`.
- `exposeHostNamespace(id, value)` puts a module's API on `window.api.<id>` when the host has no such namespace, as on Android, where the module answers from its Capacitor plugin. It never replaces a preload namespace and does nothing before `window.api` exists.
- `instanceName` and `instanceProfile` read the launch identity flags from the preload bridge at call time. A named instance is an automated launch running beside the person's own window: marked on screen, booted into its own profile, never writing the files every launch shares. `isAutomationLaunch` is true for any automated launch, named or not.
- There is one log bus per app, created by `BrockApp` with the module channels; plain modules reach it through `getAppLog()`. In development `__logEntries` and `__logSubscribe` are exposed on `window` so an automation harness can read them.
- The renderer profile store wraps the core store bound to the platform `FileStore`; `configureProfileStore` must run before the first store call and resets the cached store. `setLastProfile` is a no-op on an automated launch, gated at this single seam so no call site can forget that an automated run never repoints the shared `app.json`.

## Platform

- The `Platform` facade is resolved once on first use so hooks (through the provider) and plain modules (through `getPlatform`) share one instance; `setPlatformPorts` must run before the first `getPlatform()` and throws afterwards. Module ports are registered before the facade resolves. The `platform-mobile` class is reflected on the document root because portaled surfaces sit outside the app subtree.
- Every Electron port delegates to the preload bridge so the renderer never touches Node or Electron directly; the device port is inert because the desktop window handles sleep and backgrounding itself. The web factory is also the fallback when no host matches: no window chrome, no persistent storage, a file picker built on an input element and a download link; a browser cannot tell whether a download finished, so a started download counts as saved. In a phone's browser (a coarse pointer and a narrow viewport) it reports `formFactor: 'mobile'` and `input: 'touch'`, and `PlatformProvider` follows the media queries, so the info changes when the viewport does.
- The api shim is a boot-safe `window.api` stub for hosts without a preload, built from the channel maps so every method exists: events return a no-op unsubscribe, sends do nothing, invokes resolve to an empty value (an array for `listMethods`, a shaped value for those in `returns`, else null). It is a no-op when a real bridge is present; an app with extended maps installs its own shim before rendering.

## Screens and menus

- The home screen is the base layer and the open screen draws over it. A fullscreen screen gets the shell's `ScreenLayer`, an own screen draws its own frame. The mounted set is the active screen plus every `keepMounted` screen opened once this session; those stay mounted hidden so their scroll and local state survive being closed. `defineScreen` defaults: layer fullscreen, `keepMounted` false, `devOnly` false, `requiresProfile` true. An app screen with the same id replaces a built-in one; the profiles screen needs no profile because it is the setup screen when none exists.
- `ScreenLayer`: `back` is Tessera's `BackAction`, `{ onSelect, label? }`, where `label` is the page it goes back to, so the arrow reads Back to and the label; `extra` holds controls in the header line before the close button; `floating` overhangs the top edge of the card; `hidden` keeps the layer mounted but out of sight.
- A menu item either opens a screen by id or runs its own `onClick`; the title bar menu resolves `screen` through navigation so app and module menus stay plain data. Every pick closes the menu first; separators inside a submenu are dropped because the dropdown draws them at the top level only. Modules are flattened in module order, ports merged per host with later modules winning on the same key, log channels deduplicated.
- `nav` is the imperative navigation surface for callers outside React; `toggle` opens when closed or another screen shows and closes when that screen is already open.

## Settings engine

- A section holds either flat `items` or named `subsections`, never both. Each item is `{ key, label, hint?, description | noDescription: true, keywords?, link?, control? }`, the same shape as Tessera's `SettingsItem`: the typecheck fails on an item without a `description` or an explicit `noDescription: true`; a missing or empty `hint` draws no hint line and no gap (Tessera 0.53), and Brock passes it as it is. Each item draws as a Tessera `SettingsRow`, the description under the title at rest and the hint in its place while the control is pointed at or focused; a `choice` option can carry its own `hint`, and `disabled` (`true`, or a string that says why): the option goes to Tessera's `SettingsOption.disabled` as it is (Tessera 0.33, MIGRATION 224), so a choice, select, radio or multi-choice draws its own control with that option greyed, not pickable and skipped by the keys, and the reason as a pointer tooltip and an `aria-description`; a disabled value is never set. `visible(settings)` on an item leaves the row out while it returns `false`, on the page, in the hub search and in the palette. `control` picks the input: `choice` (`options`, `look?: 'segmented' | 'select' | 'radio'`; a select above three options, a segmented control otherwise), `select` (`options`, `searchable?`), `radio`, `range` (a slider), `number` (`min?`, `max?`, `step?`, `unit?`), `text` and `password` (`placeholder?`) and `tags` (`suggestions?`, `placeholder?`), each the SettingsRow input of the same name, `path` (`pick?: 'file' | 'folder' | 'any'`, `accept?` endings such as `'.yaml'`, `placeholder?`), a Tessera `PathField` on a string setting: typing, a drop from the desktop (the path comes from the platform's `filePicker.pathOf`, Electron's `webUtils.getPathForFile` through the preload) and Browse, which opens the native dialog through `filePicker.pickPath` (`dialog:pickPath`; a host without it has no Browse); an empty path is saved as `''`, `color`, Tessera's colour row (the hex value beside a swatch that opens `ColorPickerPopover`) on a string setting, `multi` (`options`), Tessera's multi-choice row (a `ToggleGroup`) on a list of strings, and `json` (`shape?: 'object' | 'array' | 'any'`, typed `SettingJsonShape`), a Tessera `CodeBlock` with `editable` and `language="json"` over the value as indented JSON: each edit goes through `JSON.parse` and the shape check, and the parsed value is saved only while the text parses, so a typo never reaches the settings; while it does not, the field is `invalid`, the line read from the parse message (`/line (\d+)/`) is its `problemLine`, and the message shows under it; a boolean with no control is a toggle. In development a row that resolves to no control logs one warning naming its key, instead of drawing nothing in silence. Keys may be dotted paths into a nested settings object (`haptics.intensity`). The hub search matches the label, the description, the hint, the option labels and hints and `keywords`, extra words a search matches on; the palette and the build-time search seeds match the label, the description, the hint and `keywords`; `link` is an external URL shown beside the description of a boolean item. `SettingLockCause` is the app's own vocabulary and null means unlocked. Omitting `defaults` hides the per-section reset; `renderControl` returning null falls back to the boolean toggle; `lockOverlay` defaults to a disabled overlay naming the cause. A tab's `navIcon` is the line icon for nav and header, `icon` a short mark for search rows; tabs sharing a `group` sit together in first-seen order; `groupId` gives the group a stable id, and a tab joins the group with its `groupId`, else the one with its `group` label (any case). In the settings bucket a module tab joins the app's nav group the same way, after the app's own pages.
- Custom setting rows: an item drawn by `renderControl` keeps its title, description, hint, row actions and lock, and the custom node sits in the control slot like a built-in control. `layout: 'wide'` draws it at the full width of the row below the title and description; `chrome: false` gives the whole row back to `renderControl`, as before. Returning `null` falls through to the item's `control`.
- Value sources: a settings page or a section can name a `source`, an object `{ get(key), set(key, value), subscribe?(listener) }` the app provides, so its rows read and write app values (app-wide config kept in main through a channel, say) instead of the profile settings. `source` on a `Section` binds that section; `source` on a `TabDef` (`meta.source` of a `.settings.ts` page) binds every section that names none, and a section's own source wins. The keys of the section's items are read with `get` on each render, `visible`, `renderControl`, `isDisabled` and `lockCauseOf` get those values in place of the profile settings, and a change calls `set(key, value)` once per key. `subscribe` returns an unsubscribe function and tells the page to read again; without it the page reads again once every `set` has settled, so an async `set` shows its new value when the promise resolves. Keep the object stable (build it once, outside the component). `set` handles its own errors: the page does not catch a rejection. A source section has no reset, since there are no profile defaults for it. Search finds the rows the same way (hub search, the build-time seeds and the palette), and the palette toggle of a boolean row flips the source. A row's key is its palette id (`setting:<key>`), so keep keys unique across the app. Profile settings stay the default.
- Settings preview: `TabDef.preview(settings)` (or `meta.preview` of a `.settings.ts` page) draws a preview beside the page's rows, with `previewPlacement: 'end'` (default) or `'start'`. When the page content is at least 56rem wide the preview takes a second column; narrower, it stacks above the rows. The breakpoint is a container query on the page, so it follows the space the page has, not the window. Search results and `render` pages show no preview. `SettingsPreviewLayout` (props `preview`, `placement`, `label`, `rowsLabel`, `children`) is exported for pages outside settings. The preview column is a `complementary` landmark named "Preview" and the rows column a `region` named "Settings", both F6 stops; `previewLabel` (on `TabDef`, `meta` and `SettingsLayout`) and `label` rename the preview.
- `SettingsHub`: while the search field has focus or holds text, no tab is selected and the pane shows matching settings from every tab; picking a tab from the nav or a result clears the search. `activeTab` is a controlled active tab (the hub keeps its own when left out); `homeTabId` is pinned above the groups and defaults to the first tab; `backdrop` is drawn behind every page header; `mobileOnly` tabs are listed only on a mobile form factor. Per-tab match counts use the same filter as the pages (`resolveSections`), so a count always equals the rows drawn.
- `SettingsLayout` reads the page context: `page` draws a full Tessera `SettingsPage` whose header links to each section; `results` draws only the rows matching the (lowercased, trimmed) query, bare, so a search pane can stack every tab's matches, or null when none match; no context draws the bare sections. A section with subsections yields one titled group per subsection; a flat section yields one untitled group anchored on the section itself. Empty groups and sections are dropped so a search that matches nothing leaves no stray heading.
- Locks: items are split into contiguous runs by lock cause so neighbouring rows locked for the same reason share one overlay; runs with different causes never merge. Reset: a key counts as changed only when the defaults know it, the row is not locked, and the stored value differs (compared by JSON serialization); a nested field is written through a copy of the live parent object so sibling fields the section never listed survive. A search narrows a section to the rows it still shows, and the per-section reset follows that: it resets exactly the settings in front of the reader.
- Row reset: when `defaults` are given, a row gets `changed` (the stored value differs from its default, compared by JSON serialization) and `onReset` (restores only that key, a nested key through a copy of the live parent so siblings stay) through the same `onChange` patch as any other edit, so effects, undo and the debounced save behave the same. A locked row, a row whose key the defaults do not know, and a row of a section with a `source` get neither. The section reset stays as it was.
- The settings store: `patch` merges a partial, runs the effects with `(patch, next, prev)` and schedules a debounced save (default 300 ms). Hydrating a new profile flushes the pending save for the old one first, so a quick switch never writes one profile's settings into another's file; a hydration token discards a stale load. `reset` returns to the defaults with no profile and saves nothing; `flush` writes any pending change now. `BrockApp` creates one store from the app's defaults and `useSettings` reads it typed as the app's own settings shape.

## Shell views and stores

- Title bar: the shell renders Tessera's `WindowTitleBar`, which draws the hamburger and the menu from `toMenuGroups(menu, { openScreen })`, with the trailing Quit in its own group, and reports every button to one `onControl`; it takes `actions`: `STANDARD_TITLE_BAR_ACTIONS` (Search with Ctrl+K, Report a bug) then each module's `titleBarActions`, a `WindowTitleBarAction` or a `TitleBarActionHook` that returns one; every action is also an item of the hamburger, beside the View sub-menu with the pin and full screen, and replaces the menu entry whose key is its id; `product.window.titleBar.controls` turns the fullscreen, pin, minimize and maximize buttons off; an empty menu hides the hamburger; the shell conceals the bar when the `windowMode` setting is `borderless` or `fullscreen`, read by key, so no module import is needed, and the bar peeks while the pointer is in the 40 px strip along the top edge; a normal launch shows no instance badge. The instance badge shows the name verbatim because the name is the identifier.
- About: the About screen is Tessera's `InfoScreen`, with no page header, holding Brock's `AboutPanel`, which shows the logo and the app name, with the rows from `useAboutInfo` and the legal text in the screen footer; the version comes from the bridge's `getAppVersion` and falls back to `0.0.0` without a bridge; the copy button is Tessera's `CopyButton`, putting the debug text on the clipboard; a product whose `icons.brand` is the Tessera brand of the same name shows that brand's app icon and wordmark.
- `ProfilesScreen` doubles as the setup screen when no profile exists (the form is forced open); it wires Brock's `ProfilesPanel` to `useProfiles`: pressing a profile makes it active and closes the screen, renaming edits the name in the row, deleting asks once in the row and then removes it, and `createOptions()` is merged into the create request. Enter in the name field submits, `canSubmit: false` blocks submit while an extra field is incomplete, and `extraFields` render between the name and the actions. A failed create shows its message in the form, a failed rename above the list. `WorkspaceSwitch.label` is the accessible name for the whole switch.
- Profiles store: `rename(id, name)` on the store, and `useProfiles().rename(profile, name)`, write the new name and refresh the list; renaming the active profile updates `active` too.
- Profiles store: selecting a profile records it as the default for the next launch (skipped on an automated launch) and bumps its last-played time; `loaded` is true once the first refresh finished. `useProfiles().remove` asks first through the confirm dialog, and when the active profile is deleted the profiles screen opens so the app is never left without one.
- `confirmAction(options)` is the promise form: it resolves `true` on confirm and `false` on cancel, Escape or a newer dialog.
- `confirmChoice({ ..., choices, initial, look?, searchable? })` resolves the picked value, or `null` on cancel. `look: 'select'` draws the choices with Tessera's `Select` (with its search box when `searchable`) in place of the radio group. `facts: { label, value }[]` on any confirm dialog draws rows under the message.
- `alternate: { label, onSelect, tone?, closes? }` on `confirmAction` and `confirmChoice` adds a third button. `tone` is `'neutral'` (the default, a secondary button) or `'danger'`. The dialog stays open after `onSelect` unless `closes` is true, which closes it and resolves `false` (`confirmAction`) or `null` (`confirmChoice`), like a cancel.
- Start-up prompts (`defineStartupPrompt`, `src/startup/<id>.prompt.ts`) run once per launch, one at a time, after the window reveal, with a profile active and the first-run tour over; never on an automation launch. See architecture.md, Start-up prompts by convention.
- A tour step lights a shell part with `target: { shell }`: `'menu'`, `'search'`, `'report-bug'`, `'title-bar'`, `'screen'` (the open screen's card with its sidebar), `'page'` (the screen host alone), `'rail'` (the screens rail), `'hero'` (the Home hero, else the open hub's hero) or `'tabs'` (the page tab strip), `'primary'` (the primary button of the open screen header), `'back'` (the Back button of a sub page header) or `'menu-panel'` (the open root app menu panel). `{ shell: 'rail', entry: 'Games' }` lights one sidebar entry of the open screen by its label, and plain `{ shell: 'rail' }` keeps lighting the screens rail. `reset: true` on a step clears the screen it shows before the target is lit, so a tour always starts from a clean view; `reset: { search: true, tab: true }` clears only the parts named (`search`, `filters`, `tab`, `selection`). The screen is the one the step opens, else the open screen. Screen state kept with `useScreenState` is cleared by Brock: the hub page search, the hub tab and the window section need nothing, and `useScreenState(key, initial, 'filters')` (the third argument is `'search'`, `'filters'`, `'tab'` or `'selection'`) tells Brock which part a key holds. State that lives outside that store (a `useState` search box) registers `useTourReset((parts) => { if (parts.search) setQuery(''); })`, which receives all four flags as booleans and runs for the screen that owns the component. A screen with nothing to reset is left alone and nothing is logged. `openMenu: 'menu'` on a step opens the app menu (or a title bar action menu by id) first, and `target: { menuEntry: 'Take the tour' }` lights an entry inside it (Take the tour is a top level entry). An entry in a submenu is named by its path, `{ menuEntry: ['Advanced', 'Report a bug'] }`, and a plain label is searched for in the submenus too; Brock opens the parents and closes them when the step ends. A part that is not on screen leaves the step centred. `intro: true` turns a step into Tessera's wide welcome panel. Its `art` is a node, `'product-mark'` (the product's brand mark or logo, for a `.tour.ts` file with no JSX) or `{ icon: '<name>' }`. `reveal` runs before Tessera looks for a target that may not be drawn yet.
- The shell shows one confirm dialog at a time; `dialogs` is the imperative surface for code outside React; `confirmAction` is the one confirmation API, and `dialogs.confirmDelete` is deprecated: a thin call to `confirmAction` with a red Delete button that runs `onConfirm` on confirm; `dismiss` runs the config's `onCancel`.
- Every store made with `createSessionStore` is tracked, and `resetAllSessionStores()` returns each to its initial state when a new profile is selected. Widget preference values must survive a JSON round-trip; the widget-pref store is a session store, so a new profile starts empty and the host hydrates it from disk and saves on change.

## Assistant control

Plain functions for code outside React, such as an MCP server that lets an assistant drive the app. They work once `BrockApp` is mounted and return empty or `not-ready` results before that. Details are in `docs/architecture.md`.

- `settingsCatalog()` (also `settings.catalog()`) lists every registered settings tab with its sections, subsections and items: key, label, description, control kind and choices (or `min`, `max`, `step`), the value source (`'app'` or `'custom'`), whether it can be set, whether it is visible now, and the current value (not for a password).
- `settings.set(key, value)` writes one app setting after checking it. It returns `{ ok: true }` or `{ ok: false, why: 'not-ready' | 'unknown' | 'scope' | 'invalid', reason }`. An unknown key, a key from a custom value source, a choice that is not offered or is disabled, a number outside its range or a value of the wrong type is refused and nothing changes.
- `nav.routes()` lists the screens, hubs, hub pages, tabs and sub-page patterns that `nav.open` accepts, as `{ route, title, kind, screen, section, tab }`. Hidden and developer-only entries are left out.
- `dialogs.current()` returns the open Brock confirm dialog as `{ id, title, message, variant, selected?, choices }`, or null. Each choice is `{ id, label, kind }` with ids `confirm`, `cancel`, `alternate` (when the dialog has one) and `option:<value>` for the options of `confirmChoice`.
- `dialogs.answer(choice)` answers it as if the user clicked that button and returns `{ ok: true, id, choice }`, or `{ ok: false, why: 'none' | 'unknown', reason }`. An unknown choice is refused and the dialog stays open. Native OS dialogs are not covered.

## Compounds

Brock's own compounds sit in `src/compounds/<Name>/`, the `parts.compounds` folders of the root `tessera.config.json`. Each was made with `brock tessera new compound` and carries a `<Name>.usage.ts` that says when to use it; `brock structure` fails without it, and `brock tessera check` checks the sentences, the example and the props hash.

- `AboutPanel`: the body of an About screen. `title`, `brand` and `heading` (`wordmark` or `title`) draw the app icon and the wordmark of a Tessera brand, or `logo` and the title for any other app; `wordmark` draws an image as the heading instead, fitted to the panel width and at most `--size-48` high, and `wordmarkRendering: 'pixelated'` scales it with hard pixel edges; `rows` are `StatRow` facts; `copyText` shows a copy button (null while it is gathered, left out to hide it) and `copyLabel` names it; `legal` is a dim paragraph at the bottom. It goes in as the children of `InfoScreen`.
- `ReleaseNotesPanel`: release notes in a box with a titled bar (`title`, default Release notes, an h3), plain text keeping its line breaks, scrolling past a fixed height. With `markdown`, a string note is drawn by Tessera's `Markdown` (`size="sm"`, `headingOffset={2}`, `hideTitle`), and its links call `onOpenLink`, `openExternal` by default. It fits the details of a `UtilityScreen` or the body of a dialog; the updater dialog uses it.
- `ProfilesPanel`: a premade profile list that replaces Tessera's `ProfilePicker`, drawn by Tessera's `ItemList` under a `SectionHeader` with `title`. `profiles`, `selectedId` (the active profile) and `onSelect` draw and switch: `onSelect` is the list's `onActivate`, so a click, Enter or Space on a row calls it, while the arrow keys, Home and End only move focus, and moving through the list never switches profile. The rows are one Tab stop, and Tab from the focused row reaches its rename and delete. Rename and delete are on every row (`actionVisibility: 'hover'`): always shown on the active row, and on the others under the pointer or while the row holds focus. `onCreate(name)`, `onRename(id, name)` and `onDelete(id)` turn on New and the create form (an `InlineCreateForm` in ItemList's `create` slot, at the top of the list), the rename field in the row (or F2) and the delete question. `onCreate` and `onRename` return a promise: the create form closes when it resolves and shows the message of a rejection; a failed rename shows its message above the list. Focus goes to the name field when the form opens, back to New on Escape or Cancel, and to the new row after a create that selects it. `createOpen` keeps the create form open with no Cancel, and Escape leaves it open; `extraFields`, `canSubmit`, `placeholder` and `newLabel` shape it.

## Hooks

- A mobile shell running edge to edge forwards the display cutout sizes as custom properties on the document root (`--sai-top`, `--sai-right`, `--sai-bottom`, `--sai-left`, in CSS px) and fires the `safeareainsets` window event when they change; hosts that set none read as zero. `applyNotchMode` toggles `notch-fill` or `notch-safe` on the document root.
- `useWidgetPref` is a `useState` drop-in whose value belongs to the profile: with a widget id the value survives unmount, a profile switch and a restart; with null it degrades to plain local state. The stored value is cast to the caller's type without validation; a value written by an older build with another shape lands there and the next write corrects it.

- `useNow(intervalMs, active = true)` returns the current time and ticks every `intervalMs` while `active`.
- `useCopyText(resetMs = COPIED_RESET_MS)` returns `{ copied, error, copy(text) }`. `copy` writes to the clipboard and resolves true or false; `copied` resets after `resetMs`. A button that only copies is Tessera's `CopyButton`.
- `useKeyedGuard()` guards async work per key: `guard(key, work)` returns the work's result, or undefined when it threw. `isBusy(key?)` with no key asks whether any key is busy. `errorOf(key)` and `clearError(key?)` read and clear the recorded message. `keyedGuardReducer` is the pure state machine behind it.

## Automated review

On a `--review` launch `BrockApp` loads `review/run-review` as a separate chunk once startup settles; a normal launch never loads it. The tour drives the shell like a person, from the registries and the product config: title bar, first-run profile form, menu, every screen (through its menu entry when one exists, else `nav.open`), Escape to home, the palette, search from both the palette and a hub (with the brand mascot in the palette and in the hub search before typing and with no match), the bug report dialog, About, the logs widget docking, a pop-out widget opening in its own window, and the hero homes. Each step sends its checks and a screenshot request to main, which writes the report. Run it with `brock start -- --review --no-focus --muted --user-data=<dir>` after a build; the report is `Data/review/<name>/report.md`.

An app review step can list `sizes` (`'narrow'`, the shell's own 600 by 720 window, or `{ name, width, height }`). The step runs once per size through the same main window probe the narrow screen captures use, restores the window after, and ends each capture and check id with the size name. See `docs/review-steps.md`.

# Brock v0.113.0

One paragraph for the people who use Brock: what this release changes for them.

## Changes

- Typed drag and drop between widgets, and state kept per project or document. Drag and drop: `dnd.type<T>(name)` makes a drag type, `dnd.source(element, { type, payload })` makes an element draggable, and `dnd.target(element, { accepts, onDrop, canDrop?, feedback?, index? })` takes the drop. The payload is passed as it is and typed by the drag type. A target gets `enter`, `over`, `leave` and `drop` feedback and a `data-drop` attribute, and `index` reports a position for list-like targets. `useDragSource`, `useDropTarget` and `useDragSession` are the React forms. A target that accepts `dnd.files` also takes files dropped from the desktop: the renderer sends the paths to main (`document:vetDrop`), main checks them with the folder-grant rules and grants what passes, and the app only sees the paths main answered. It works between docked and floating widgets, which share a window; a popped widget window is another renderer and is not covered. `dnd.dragOut(paths)` is a seam that answers false until the main process side lands. Scoped state: `uiViews.scope(key, { maxKeys? })` keeps named values per project or document in the ui views, with a size cap (200 names per scope and 50 scopes by default, `uiViews.scopeLimits` changes them) that drops the oldest. `useWidgetState(key, initial, { scope })` keeps a widget value in a scope, and `useWidgetStateReady(scope)` says when it has loaded. The `scope:` key prefix is now reserved for scopes.
- Commands can hide on a surface, hold a key, take bound arguments and be opened from the palette with a query. Menus now read a command's gates. - `CommandDef.visible()` hides a command that does not apply here. It does not fire, it is left out of `commands.list()` (pass `{ includeHidden: true }` to keep it), the palette search, the app menu and the context menu, and `commands.describe(id)` reports `visible: false`. `CommandDef.only` names the surface; two commands on one chord with different `only` values are no longer a conflict, and the Keyboard page shows both meanings and keeps a hidden command that has `only` so it can be rebound. - A `MenuItem.command` entry is disabled with the command's reason as its description, and is dropped when hidden. A context menu command entry takes its description from the command's reason and drops a hidden command. - `CommandDef.hold: { release, tapMs? }` runs on key down, ignores key repeat and calls `release` once on key up, on a lost modifier, on blur, on a hidden window and when the listeners go. The Keyboard page marks such a command. `commands.heldModifiers()` reads the modifiers now held, for a pointer drag. - `CommandDef.args` is an argument schema. `commands.run` refuses bad arguments with `why: 'invalid'`. `commands.bind`, `unbind` and `bindings` bind a chord to fixed arguments; the binding is saved in the keymap setting and shows as its own row. A menu command with a missing option value opens a value picker in the palette. - `palette.open({ query, scope })` and `palette.pick({ title, options, onPick })`. - Context menus take a `selection` (a set of keys) from `openContextMenu`, from the new `contextMenu.openAt(element, data, options)` or from the config, and pass it to the command in the context. Upgrade: `commands.run` can now resolve with `why: 'hidden'` or `why: 'invalid'`, and `CommandDescription` has a `visible` field. A `switch` over `why` that must cover every case (a `never` check) stops compiling until it handles `'hidden'` and `'invalid'`. A command with no `visible` is never hidden, so nothing changes at run time for an existing app.
- Hubs and routes grow three things an app can use. A bucket can set `header: { render(ctx), actions?(ctx) }`, drawn in the hub header row in place of the profile subtitle, with the hub render context and an area for actions on the right. A bucket can set `params: ['subject']`, a list of route params that stay when the page changes inside the hub, come back with Back and a restored session, and show up as `ctx.params` in every `when` rule (`ShowContext` has a new `params` field, so a hand-made context needs `params: {}`). `nav: 'rail'` draws the hub nav as an icon rail with no search. `ScreensConfig.aliases` maps an old route name to a new one, deep links included, and the Settings menu entry, palette breadcrumb and review tour now read the title of the settings bucket.
- Widgets and toolbars can follow the app's state, and layouts can be kept per workspace. Nothing existing changes. - `defineWidget` takes `when` (a `ShowRule`) and `contexts` (a list) beside `context`. A widget with any of them is context-only and is available when one of its contexts is active and its rule passes. `widgets.list()` reports it in `available`. - `defineToolbar` takes `when`. A toolbar whose rule fails is not drawn and is left out of the Toolbars menu, and the user's layout and hidden list are not touched. `toolbars.list()` has a new `available` field. - `widgets.setTitle(id, text)` sets a dynamic title such as a count. `defineWidget` takes `empty`, drawn when a forced widget has no context. - `defineWidget` takes `prefs`, setting items kept as widget prefs. They show in the widget's own options menu and in one Widgets tab of Settings, with the same value in both. - `defineToolbar` takes `contextEntries(itemId)`. Mark an item with `toolbarItemZone(itemId)` and its menu shows those entries above Brock's. - Workspaces: `defineWorkspace`, `registerWorkspaces` and the `workspaces` facade. A workspace with a `when` rule turns on by itself, keeps its own widget and toolbar layout in the profile views, and has Reset. The Widgets menu gets a Workspace sub-menu. The standard layout keeps its saved keys, so no profile data moves and no migration is needed. Widget kits take `when` too. - `layout.focusMode(on)` hides every widget, toolbar and open kit and restores them. The command `brock.focus_mode` toggles it. The hidden state is never saved. Not built: per-item toolbar visibility and `columns` in the toolbar layout, which wait for a Tessera `ToolbarLayout` change.

- The built-in review no longer fails on a loaded machine because a clock window ran out. Waits in the review now end on the signal they wait for: a change in the page, a layout that has stopped moving, a store change, or a window event from main for popped widget windows (new `review:windows` event). Each wait keeps one generous ceiling of 30 s, used only to fail a stuck check, and the failure now says what it waited for. This replaces the 3 s `waitFor`, the 8 s popped window wait, the fixed pauses before captures (settle, tour steps, performance samples, popped widget paint, widget options, the dev gate quiet period) and the 1 s capture prepare limit of the baseline run. The mascot still check counts frames instead of polling. The review idle watchdog now hears from every wait and step (new `review:alive` message), so only a silent step trips it, and its limit is 45 s. The review start limit follows boot progress: main tasks, the renderer boot, the page loading and each request the page finishes restart the 60 s silence window, so a first dev launch that is warming Vite no longer fails. A boot that makes no progress at all still stops at 60 s, and a hard ceiling of 5 minutes stays. The frame check of the review now reads the title of a bare cornerTitle window from `aria-labelledby` or the corner chip when the header and `aria-label` give none. A review step can now declare `timeoutMs` on `defineReviewStep` for a long silent operation such as an engine setup or an install: it replaces the idle limit for that step only and main caps it at 30 minutes.
